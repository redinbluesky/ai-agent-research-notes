# 운영·관측성과 개선 루프

## 목적

운영 지표와 인시던트에서 얻은 신호를 감지·분석·승인·개선으로 연결하고, 결과를 다음 `intent.md`와 eval에 환류하는 방법을 정리한다.

## 출처에서 확인한 내용

- 운영 단계에서는 CI 테스트 실패율, 배포 뒤 5xx 비율, PR 리드타임처럼 기준선을 만들 수 있는 지표를 선택해 이상 신호를 감지할 수 있다.[5]
- 감지는 결정론적 규칙으로 유지하고, 이상 수준에 따라 기록·읽기 전용 진단·PR 또는 사전 승인된 runbook 실행을 단계적으로 나눌 수 있다.[5]
- 에이전트의 진단 결과는 영향·근거·예상 결과·미해결 질문을 담은 새 `intent.md`로 기록해 SDLC를 다시 시작할 수 있다.[5]
- 인시던트 수정이 배포된 뒤에는 해당 사례를 eval로 추가해 같은 종류의 문제가 재발하지 않도록 할 수 있다.[5]

## 실무 가이드

### 1. 관측 지표를 적게 시작한다

초기에는 서비스와 개발 흐름을 함께 볼 수 있는 지표 1~3개를 고른다.

- 배포 후 오류율·5xx 비율
- 지연 시간·성능 저하
- CI 테스트 실패율
- PR 리드타임·병합 대기 시간

각 지표에는 기준선, 관찰 기간, 알림 조건, 담당자를 명시한다.

### 2. 탐지와 판단을 분리한다

탐지는 임계치·통계 규칙처럼 재현 가능한 방식으로 처리한다. 에이전트는 탐지 결과 뒤에 로그·코드·최근 변경을 읽어 원인 가설과 수정안을 제안한다. 고위험 조치와 운영 변경은 사람의 승인 뒤에 실행한다.

### 3. 대응 수준을 정의한다

| 수준 | 대응 | 에이전트 권한 |
|---|---|---|
| 관찰 | 기록과 추세 확인 | 로그·지표 읽기 |
| 경고 | 원인 분석과 보고서 초안 | 읽기 전용 진단 |
| 심각 | PR 생성 또는 사전 승인된 runbook 제안 | 제한된 도구 호출, 승인 필요 |

### 4. 인시던트를 학습 자산으로 남긴다

각 인시던트에는 감지 근거, 영향 범위, 원인, 조치, 롤백 여부, 재발 방지 검증을 남긴다. 범위가 작은 수정은 PR로, 더 큰 개선은 새 `intent.md`로 시작한다. 배포된 수정은 regression test 또는 eval에 반영한다.

## 권장 지표

- 이상 감지부터 triage 항목 생성까지 걸린 시간
- triage 항목 중 실제 병합된 수정 비율
- 같은 유형의 재발 인시던트 수
- 인시던트에서 eval 추가까지 걸린 시간

## 점검 목록

- [ ] 기준선이 있는 운영·개발 지표를 선택했는가?
- [ ] 감지 규칙과 에이전트의 진단 역할을 분리했는가?
- [ ] 대응 수준별 권한과 승인자가 정해져 있는가?
- [ ] 인시던트 결과가 PR 또는 `intent.md`로 이어지는가?
- [ ] 재발 방지 테스트 또는 eval이 추가되는가?
