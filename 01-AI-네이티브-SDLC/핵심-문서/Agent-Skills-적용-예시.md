# Addy Osmani Agent Skills로 실행하는 AI 네이티브 SDLC

## 목적

이 문서는 `addyosmani/agent-skills`를 이용해 이 저장소의 **Intent → Spec → Plan → 구현·검증 → 배포·운영** 흐름을 실제 변경 작업으로 실행하는 예시다. Agent Skills는 개발 단계별 워크플로와 품질 게이트를 스킬로 제공하며, 기본 흐름을 Define → Plan → Build → Verify → Review → Ship으로 설명한다.[1]

이 문서의 목표는 upstream 저장소의 파일명·명령·문서 구조를 그대로 복제하는 것이 아니다. 이 프로젝트의 `intent.md`, `spec.md`, `plan.md`와 검증·배포 기록을 정본으로 유지하면서, 에이전트가 각 단계에서 수행할 질문·작업·검증을 명확히 하는 데 있다.

## 적용 경계

- Agent Skills를 매 세션에 전부 로드하지 않는다. 현재 단계와 작업 성격에 맞는 스킬만 선택한다.[2]
- `/spec`, `/plan`, `/build`, `/test`, `/review`, `/ship`은 upstream이 설명하는 라이프사이클 명칭이다. 실제 호출 문법·플러그인 설치·스킬 탐색 위치는 Claude Code, Codex, Gemini CLI 등 호스트마다 다르므로 `03-에이전트-설정`의 제품별 가이드를 따른다.[1]
- upstream 예시의 `SPEC.md`나 `tasks/` 경로를 새 정본으로 만들지 않는다. 이 주제의 `산출물/intent.md`, `산출물/spec.md`, `산출물/plan.md`와 관련 기록 양식을 사용한다.
- 스킬의 자동 적용이나 완료 보고는 권한 통제가 아니다. 원격 push, 운영 배포, 기능 플래그 활성화, 데이터 마이그레이션은 별도 최소 권한·CI·사람 승인 정책을 따른다.
- 오탈자·한 줄 수정처럼 요구와 영향이 명확한 작업에는 전체 절차를 강제하지 않는다. 이 문서는 여러 파일·모듈·사용자 흐름에 영향을 주는 변경을 대상으로 한다.[6]

## 단계별 매핑

| 현재 SDLC 단계 | 저장소 산출물 | 우선 적용할 Agent Skills | 에이전트의 책임 | 사람의 책임 |
|---|---|---|---|---|
| 의도 정리 | `intent.md` | `interview-me`, `idea-refine` | 모호함을 질문으로 드러내고 문제·성공 기준·제약·미해결 질문을 초안화 | 문제, 우선순위, 범위 승인 |
| 요구사항·설계 | `spec.md` | `spec-driven-development` | 목표·비목표·수용 기준·설계 경계·위험을 구조화 | 요구사항, 아키텍처, 고위험 결정 승인 |
| 구현 계획 | `plan.md` | 계획·작업 분해 워크플로 | 변경 파일, 의존성, 세로 Slice, 검증 명령, 롤백을 계획 | 순서, 위험 수용 여부, 실행 범위 승인 |
| 구현 | `구현-변경-기록.md` | `incremental-implementation`, `test-driven-development` | 작은 Slice를 구현하고 테스트·실행 검증·기록 | 범위 외 변경과 설계 이탈 판단 |
| 검증 | `테스트-검증-기록.md` | `test-driven-development`, 필요 시 브라우저 검증 | 수용 기준별 근거, 실패·통과 결과, 미검증 위험 기록 | 출시 가능성과 잔여 위험 판단 |
| 리뷰 | 기존 PR 및 검증 기록 | `code-review-and-quality` | 정확성·가독성·아키텍처·보안·성능 5축 검토 | Critical·Required 이슈 해소 여부 승인 |
| 배포 | `배포-롤백-기록.md` | `shipping-and-launch`, `ci-cd-and-automation` | 단계적 롤아웃·관측·롤백 준비를 점검 | 운영 배포와 롤백 실행 승인 |
| 운영 | `운영-인시던트-기록.md` | 관측성·디버깅 워크플로 | 지표·로그를 근거로 원인 가설·수정안·후속 eval 초안 작성 | 실제 조치와 후속 작업 우선순위 결정 |

`spec-driven-development`는 큰 변경을 명세 → 계획 → 작업 분해 → 구현으로 진행하고, 각 단계의 검토를 요구한다.[6] `incremental-implementation`은 다중 파일 변경을 한 번에 완성하지 않고, 매 Slice마다 구현 → 테스트 → 검증 → 커밋을 반복해 시스템을 작동 가능한 상태로 유지하도록 안내한다.[3]

## 적용 예시: 프로젝트별 알림 수신 설정

### 변경 목표

사용자가 프로젝트별 이메일 알림을 켜거나 끄고, 서버가 설정을 저장하며, 운영자가 설정 변경 실패를 관측할 수 있는 기능을 추가한다고 가정한다. 이 예시는 데이터·API·권한·UI·관측성에 걸쳐 있어 단일 프롬프트로 구현을 요청하지 않고 아래의 단계로 진행한다.

### 1. Define — 질문을 통해 intent를 확정한다

1. `interview-me` 또는 동등한 질문 워크플로로 누락 조건을 확인한다.
2. `산출물/intent.md`를 복사해 작업용 `intent.md`를 만든다.
3. 다음 질문에 답하고 제품 책임자 또는 지정 승인자가 승인한다.

| 확인할 질문 | `intent.md`에 남길 내용 |
|---|---|
| 누가 설정을 바꿀 수 있는가? | 프로젝트 멤버 역할과 권한 경계 |
| 기본값은 무엇인가? | 신규 프로젝트·기존 사용자별 기본 동작 |
| 어떤 알림이 대상인가? | 이메일만인지, 인앱·웹훅까지 포함하는지 |
| 성공을 어떻게 판정하는가? | 설정 저장 성공률, 알림 오발송·누락률, 사용자 피드백 |
| 이번 변경에서 하지 않을 일은 무엇인가? | 전사 알림 재설계, 알림 템플릿 개편 등 |

이 단계의 완료 조건은 “에이전트가 구현할 수 있다”가 아니라 **문제, 성공 기준, 영향 범위, 제약, 미해결 질문이 기록되고 승인되었다**는 것이다.

### 2. Specify — 수용 기준과 경계를 `spec.md`에 고정한다

1. `spec-driven-development`를 적용해 `intent.md`를 읽고 `산출물/spec.md` 형식의 작업용 `spec.md` 초안을 만든다.
2. 목표·비목표, 사용자 흐름, API·데이터 변화, 권한, 오류 처리, 관측성, 수용 기준을 분리한다.
3. API, UI, 권한 정책처럼 독립적으로 테스트할 수 있는 기능이 함께 묶였으면 capability map을 먼저 작성한다.
4. 설계 책임자와 보안·개인정보 책임자가 필요한 항목을 승인한다.

예시 capability map:

| 기능 ID | 책임 | 의존성 | 독립 검증 기준 |
|---|---|---|---|
| `notification-preference-data` | 설정 저장·조회 데이터 모델 | 없음 | 생성·조회·갱신 테스트 통과 |
| `notification-preference-api` | 권한 검사와 설정 API | `notification-preference-data` | 역할별 API 계약·오류 테스트 통과 |
| `notification-preference-ui` | 사용자의 설정 조회·변경 화면 | `notification-preference-api` | 실제 사용자 흐름 E2E 통과 |
| `notification-preference-observability` | 실패 로그·지표 | API, UI | 실패 이벤트가 대시보드에 기록됨 |

수용 기준은 “설정 화면을 만든다”처럼 구현 지시로 쓰지 않는다. 예를 들어 “프로젝트 관리자만 해당 프로젝트의 이메일 알림 설정을 변경할 수 있고, 권한 없는 요청은 정의된 오류 응답을 반환한다”처럼 테스트 가능한 결과로 작성한다.

### 3. Plan — 세로 Slice와 검증 명령을 승인한다

`plan.md`에는 파일 목록만 나열하지 않고, 각 Slice가 독립적으로 작동·검증될 수 있게 순서를 정한다.

| Slice | 범위 | 완료 기준 | 다음 Slice 전 확인 |
|---|---|---|---|
| 1 | 데이터 모델·마이그레이션·저장 로직 | 설정 생성·조회·갱신 단위/통합 테스트 통과 | 기존 데이터와 마이그레이션 호환성 확인 |
| 2 | API·권한 검사 | 역할별 요청·오류 계약 테스트 통과 | 권한 우회와 입력 검증 확인 |
| 3 | 설정 UI | 설정 변경의 브라우저/E2E 검증 통과 | API 실패·로딩·접근성 상태 확인 |
| 4 | 관측성·기능 플래그 | 실패 로그와 핵심 지표가 관측되고 플래그 OFF에서 기존 동작 유지 | 배포·중단·롤백 경로 확인 |

각 Slice에는 다음 항목을 명시한다.

- 읽을 `intent.md`, `spec.md`, 관련 코드 경로
- 변경할 파일·데이터 계약과 변경하지 않을 범위
- 해당 Slice의 테스트·build·lint·브라우저 검증 명령
- 위험, 기능 플래그 여부, 되돌릴 방법
- 이전 Slice에서 확정된 결정과 실행 결과

### 4. Build와 Verify — 구현·테스트·검증을 Slice별로 반복한다

각 Slice에서는 다음 루프를 따른다.[3]

```text
수용 기준과 현재 Slice 재확인
  → 실패하는 테스트 또는 재현 절차 작성
  → 해당 Slice에 필요한 최소 구현
  → focused test · build · lint · 필요 시 브라우저 검증
  → 결과와 계획 차이를 기록
  → 작동 가능한 상태에서 작은 커밋
  → 다음 Slice
```

- 구현 도중 발견한 인접 코드의 개선점은 바로 함께 고치지 않는다. `구현-변경-기록.md`의 “남아 있는 중복·임시 우회·숨은 결합”에 기록해 별도 작업으로 분리한다.[3]
- 버그 수정이라면 먼저 실패하는 회귀 테스트 또는 재현 절차로 현상을 고정한다.
- 각 Slice의 검증 결과는 `테스트-검증-기록.md`의 수용 기준별 표에 남긴다.
- 테스트가 통과해도 “검증 완료”라고 단정하지 않는다. 권한·오류 경로·데이터 마이그레이션·UI 상태처럼 해당 Slice의 경계를 별도로 확인한다.

### 5. Review — 병합 전 5축으로 확인한다

리뷰는 별도 템플릿으로 추가하지 않고, PR과 기존 검증 기록에 근거를 남긴다. `code-review-and-quality`의 검토 축을 다음처럼 적용한다.[4]

| 축 | 알림 설정 예시의 질문 | 근거 위치 |
|---|---|---|
| 정확성 | 권한 있는 사용자만 변경 가능하고, 설정 변경이 실제 발송 조건에 반영되는가? | API·통합·E2E 테스트 |
| 가독성·단순성 | 알림 설정 규칙이 기존 알림 발송 흐름에 임시 조건으로 얽히지 않았는가? | 변경 diff, 모듈 구조 |
| 아키텍처 | 설정·권한·발송 책임의 경계와 데이터 계약이 명확한가? | `spec.md`, API 계약, 코드 리뷰 |
| 보안 | 프로젝트 간 설정 조회·변경, 입력 검증, 로그의 개인정보 노출을 막는가? | 권한·보안 테스트, 로그 점검 |
| 성능 | 알림 발송마다 불필요한 설정 조회나 N+1 접근이 생기지 않는가? | 성능 측정, 쿼리·추적 결과 |

Critical 또는 Required 이슈가 남았다면 배포로 진행하지 않는다. 단순한 취향 차이와 실제 병합 차단 사유를 분리해 기록한다.[4]

### 6. Ship과 Operate — 관측 가능한 롤아웃과 되돌림을 준비한다

`shipping-and-launch`의 원칙에 따라 배포는 되돌릴 수 있고, 관측 가능하며, 점진적으로 진행한다.[5]

1. `배포-롤백-기록.md`에 기능 플래그 소유자·만료일, 스테이징 결과, 롤아웃 단계, 관측 지표, 중단·롤백 조건을 기록한다.
2. 운영 배포는 기능 플래그 OFF 상태로 시작하고, 내부 사용자 → 제한된 사용자 → 전체 사용자 순으로 확대한다.
3. 각 단계에서 설정 변경 API 오류율, 알림 발송 실패율, 지연 시간, 사용자 문의를 기존 기준선과 비교한다.
4. 사전에 정한 임계값을 넘거나 데이터 무결성·보안 문제가 발견되면 플래그를 끄거나 승인된 롤백 절차로 되돌린다.
5. 출시 뒤 발견한 인시던트는 `운영-인시던트-기록.md`에 남기고, 재발 방지 테스트 또는 eval을 추가한다.

## 새 프로젝트와 기존 프로젝트의 시작점

| 프로젝트 상태 | 시작 방식 | 우선 스킬·활동 |
|---|---|---|
| 새 프로젝트 | 첫 기능부터 전체 흐름 적용 | 명세, 계획, TDD, 작은 커밋, 리뷰, 관측성·출시 준비 |
| 기존 프로젝트 | 검증 우선의 점진 도입 | 실제 규칙·명령을 정리하고, 읽기·리뷰·버그 재현·변경 예정 영역의 특성화 테스트부터 시작 |

기존 코드베이스에서는 미검증 영역을 바로 리팩터링하지 않는다. 먼저 실제 동작을 고정하는 특성화 테스트와 작은 변경 단위를 만들고, 새 기능은 전체 흐름으로, 레거시 영역은 검증 우선 흐름으로 다루는 두 속도 방식을 사용한다.[2]

## 완료 기준

다음 조건을 모두 만족할 때 이 예시의 변경을 완료로 판단한다.

- [ ] `intent.md`, `spec.md`, `plan.md`이 실제 변경과 연결되고 필요한 승인 기록이 있다.
- [ ] 각 Slice가 작동 가능한 상태에서 테스트·build·lint·필요한 UI 검증 근거를 남겼다.
- [ ] 계획과 실제 구현의 차이, 남은 위험, 다음 변경 전 필요한 보강을 기록했다.
- [ ] PR에서 정확성·가독성·아키텍처·보안·성능을 검토했고, Critical·Required 이슈를 해소했다.
- [ ] 배포가 필요한 경우 기능 플래그, 관측 지표, 중단·롤백 조건, 책임자를 기록했다.
- [ ] 배포 뒤의 인시던트 또는 회귀는 테스트·eval·후속 작업으로 환류할 수 있다.
