# 테스트와 지속적 evals

## 목적

AI 에이전트의 결과를 작성자 신뢰가 아니라 재현 가능한 실행 결과로 검증하고, 에이전트 설정 자체도 회귀 검증 대상으로 관리한다.

## 출처에서 확인한 내용

- 에이전트에는 테스트·빌드·스크린샷 비교처럼 스스로 작업을 검증할 수 있는 피드백 루프가 필요하다.[1]
- 버그 수정은 실패하는 테스트로 먼저 재현하고, 그 테스트가 수정되거나 삭제되지 않게 보호하면 수정 결과의 신뢰도를 높일 수 있다.[1]
- 에이전트의 규칙 파일·skills·hooks·모델 또는 프롬프트 변경은 작업 품질에 영향을 주므로, 실제 과업과 허용 조건으로 구성한 eval을 CI에서 실행할 수 있다.[2]
- 운영 인시던트는 재발 방지를 위해 지속 eval 사례로 추가할 수 있다.[2]

## 실무 가이드

### 1. 완료 조건을 실행 가능한 문장으로 쓴다

`plan.md`와 작업 지시에는 다음처럼 검증 가능한 완료 조건을 적는다.

- `make test` 또는 동등한 명령이 성공한다.
- lint 경고가 0개다.
- 변경한 API가 필요한 상태 코드와 필드를 반환한다.
- UI가 기준 화면과 비교해 의도한 동작을 보인다.

### 2. 에이전트의 피드백 루프를 만든다

각 프로젝트는 가능한 한 다음 명령을 한 번에 실행할 수 있게 한다.

```text
build → test → lint → 필요 시 UI/E2E 검증
```

에이전트는 검증 실패 시 결과를 숨기지 않고, 테스트를 약화시키기보다 구현을 수정해 다시 실행한다.

### 3. 테스트 변경은 목적별로 분리한다

- 신규 기능: 수용 기준을 검증하는 테스트를 추가한다.
- 버그 수정: 실패 테스트를 먼저 커밋하거나 PR에 포함한다.
- 테스트 자체의 수정: 기존 검증이 왜 잘못됐는지 별도 설명과 리뷰를 요구한다.

### 4. 지속 eval을 별도 회귀군으로 운영한다

대표적인 실제 작업 20~50개 수준부터 시작해, 각 작업에 프롬프트와 통과 조건(테스트, lint, 동작, 정책 준수)을 둔다.[2] 에이전트 설정이 바뀌면 CI 또는 정기 실행으로 통과율을 비교하고, 품질 하락은 검토 전 병합하지 않는다.

## 권장 지표

- 1차 CI 성공률
- 에이전트 설정 변경 전후 eval 통과율
- 운영에서 발견된 회귀 대비 CI에서 발견된 회귀 비율
- 인시던트가 regression eval로 추가되기까지 걸린 시간

## 점검 목록

- [ ] build/test/lint가 재현 가능한 명령으로 제공되는가?
- [ ] 작업마다 측정 가능한 완료 조건이 있는가?
- [ ] 버그 수정에 실패 테스트가 포함되는가?
- [ ] UI 변경에 시각 또는 E2E 검증이 있는가?
- [ ] 규칙·skill·hook 변경도 eval 대상인가?
- [ ] 운영 인시던트가 eval 사례로 환류되는가?
