# CI/CD와 안전한 배포

## 목적

AI 에이전트를 CI/CD 작업에 연결할 때, 자동화의 이점은 활용하면서도 운영 배포 권한·승인·롤백을 안전하게 통제하는 방법을 정리한다.

## 출처에서 확인한 내용

- 에이전트는 CI/CD에서 실패한 빌드 요약, flaky 테스트 분류, 변경 로그 초안처럼 읽기 중심의 판단 작업부터 수행할 수 있다.[4]
- 에이전트가 생성한 변경은 보호 브랜치에 직접 반영하지 않고 PR과 브랜치 보호를 거치게 할 수 있다.[4]
- 에이전트 작업은 네트워크 정책·샌드박스·범위 제한 단기 토큰으로 제한하고, 운영 자격 증명을 기본 제공하지 않는 방식이 제시된다.[4]
- 개발·스테이징·운영 환경별 자율성을 다르게 두고, 운영 배포는 지정된 책임자의 승인 게이트 뒤에 둘 수 있다.[4]
- 롤백은 사전 승인된 단일 경로로 만들고 스테이징에서 반복 검증하는 것이 권장된다.[4]

## 실무 가이드

### 1. 읽기 전용 자동화부터 시작한다

처음에는 실패 로그 요약, 테스트 분류, 릴리스 노트 초안처럼 쓰기 권한이 필요 없는 작업에 에이전트를 사용한다. 이후 PR 기반의 문서 갱신·lint 수정처럼 되돌리기 쉬운 변경으로 확대한다.

### 2. 환경별 권한을 계층화한다

| 환경 | 에이전트 권한 예시 | 사람의 역할 |
|---|---|---|
| 개발 | 테스트·배포·로그 확인 | 규칙과 비용 한도 관리 |
| 스테이징 | 배포 제안 또는 제한된 배포 | 품질·릴리스 준비 검토 |
| 운영 | 상태 확인·배포 준비·롤백 제안 | 명시적 배포 승인과 최종 책임 |

### 3. 배포를 승인 가능한 도구로 만든다

배포·상태 조회·롤백은 쉘에 광범위한 자격 증명을 주는 대신, 환경별로 허용된 도구와 인자로 제한한다. 모든 실행은 에이전트 식별자, 실행 시각, 대상 환경, 승인 정보와 함께 기록한다.

### 4. 롤백을 먼저 검증한다

새 배포 자동화보다 롤백 경로를 먼저 설계한다. 어떤 조건에서 롤백할지, 누가 승인하는지, 데이터 변경이 있을 때 어떤 복구 절차를 쓸지 `plan.md`에 기록한다.

## 권장 지표

- 사람 호출 없이 분류·요약된 파이프라인 실패 비율
- 배포 실패율과 변경 실패율
- 평균 복구 시간(MTTR)
- 롤백 경로의 스테이징 검증 성공률

## 점검 목록

- [ ] 에이전트가 `main` 또는 운영 환경에 직접 쓰기 권한을 갖지 않는가?
- [ ] 자격 증명이 단기·범위 제한 방식인가?
- [ ] 환경별 자율성 및 승인자가 정의되어 있는가?
- [ ] 배포·상태 조회·롤백 경로가 분리되어 있는가?
- [ ] 롤백이 스테이징에서 정기적으로 검증되는가?
