# PR 리뷰와 승인 게이트

## 목적

AI가 생성하거나 검토한 변경을 일관되게 검사하되, 제품 의도·위험 수용·최종 병합 책임은 사람에게 남기는 방식을 정리한다.

## 출처에서 확인한 내용

- AI 기반 PR 리뷰는 모든 PR에 동일한 검토 패스를 적용하고, 사람은 변경이 의도와 위험 수준에 부합하는지 판단하는 데 집중할 수 있다.[3]
- 리뷰 정책은 버그·논리 오류, 보안·취약점, `spec.md`·`plan.md` 준수, 설계 원칙 등으로 나누어 관리할 수 있다.[3]
- AI가 작성한 변경도 브랜치 보호를 거쳐 코드 오너가 승인하도록 하면, 작성과 승인 역할을 분리할 수 있다.[3]

## 실무 가이드

### 1. 리뷰 기준을 문서화한다

저장소 루트 또는 팀 규칙에 아래 기준을 둔다.

| 검토 패스 | 핵심 질문 |
|---|---|
| 동작·회귀 | 기존 동작과 경계 조건을 깨지 않는가? |
| 보안·개인정보 | 인증·권한·입력 검증·민감정보 처리가 안전한가? |
| 명세·계획 준수 | `spec.md`, `plan.md`, 수용 기준과 일치하는가? |
| 설계·운영성 | 영향 범위, 관측성, 장애·롤백 가능성을 고려했는가? |

### 2. AI 리뷰와 인간 승인을 구분한다

AI 리뷰 결과는 발견·분류·수정 제안에 활용한다. 그러나 다음은 사람의 명시적 판단을 요구한다.

- 고위험 보안·권한·결제·개인정보 변경
- 운영 배포 또는 대규모 데이터 변경
- 제품 목표·비용·성능 트레이드오프
- 예외적 정책 위반의 수용 여부

### 3. PR을 감사 기록으로 남긴다

PR에는 변경 목적, 관련 intent/spec/plan, 실행한 검증, 리뷰 결과, 승인자, 배포·롤백 관련 결정을 남긴다. 이 기록은 이후 장애 분석과 규칙 개선의 근거가 된다.

### 4. 반복 지적을 규칙으로 환류한다

같은 유형의 문제가 반복되면 리뷰어의 개인 기억에만 두지 않고 `AGENTS.md`, review 정책, 정적 검사 또는 훅 중 적절한 위치에 반영한다.

## 권장 지표

- 첫 리뷰까지 걸린 시간
- 병합 전 발견된 결함·취약점 비율
- 운영으로 유출된 결함 비율
- AI 리뷰 지적의 유효 비율과 반복 지적 빈도

## 점검 목록

- [ ] PR이 intent/spec/plan 또는 작업 이슈와 연결되는가?
- [ ] AI 리뷰 결과의 심각도 기준이 정의되어 있는가?
- [ ] 코드 오너의 최종 승인과 브랜치 보호가 적용되는가?
- [ ] 고위험 변경의 인간 승인 기준이 명확한가?
- [ ] 반복 지적을 규칙 또는 자동 검사로 환류하는가?
