# 한 줄 요약

Spec-Driven Development는 자연어 스펙을 코드 생성과 검증의 기준으로 삼고, 이를 자기 완결적인 작업 단계·독립 에이전트 세션·실행 가능한 수용 기준·상태 기록으로 연결하는 하네스를 통해 장시간 작업으로 확장하는 접근이다.

# 출처와 분석 범위

이 문서는 영상에서 설명한 Spec-Driven Development의 주장과 데모를 정리하고, 영상에서 사용한 `harness_framework` 저장소의 실제 파일과 실행 코드를 함께 분석한다.[1][2]

영상의 자동 자막과 메타데이터는 저장소의 [유튜브 분석 도구](../../99-도구/01-유튜브-분석/README.md)로 수집했다. 원본 자막과 중간 산출물은 로컬 `결과/`에만 보관하고 이 문서에는 분석 결과만 남긴다.

# 영상에서 확인한 내용

## TDD 이전에 무엇을 만들지 합의한다

영상은 동작이 명확한 버그 수정이나 작은 함수에는 테스트 우선 접근이 잘 맞지만, 새 도메인이나 제품을 처음 설계할 때는 테스트보다 먼저 무엇을 만들지 합의해야 한다고 설명한다. 여기서 Spec-Driven Development를 자연어 스펙으로 코드 생성과 검증을 주도하는 방식으로 정의한다.[1]

핵심은 스펙 문서만 작성하는 것이 아니다. 사람이 설계와 판단을 담당하고 AI가 계획 분해와 구현을 맡으며, 실패를 규칙·스킬·하네스 개선으로 환류하는 실행 시스템까지 포함한다.

## 다섯 가지 사고 전환

영상이 제시한 전환은 다음과 같다.[1]

1. **Spec first, Code second**: 코드를 수정하기 전에 명확한 스펙을 작성한다.
2. **작성자에서 판단자로 이동**: 사람은 아키텍처, 도메인 맥락, 예외와 우선순위 판단에 집중한다.
3. **암묵지를 외부화**: 컨벤션, 워크플로, 패턴과 기술 결정을 규칙 파일과 문서로 기록한다.
4. **주의력을 앞단에 배치**: 구현 속도가 빨라질수록 설계와 스펙 검토가 중요한 병목이 된다.
5. **학습 루프를 만든다**: 실패를 회고로 끝내지 않고 규칙, 스킬과 실행 환경 개선으로 연결한다.

## SDD 실행 루프

```text
설계 → 계획 → 구현 → 교정 → 회고·시스템 개선
```

- 설계에서는 사람이 PRD, Architecture, ADR과 조직 제약을 주도한다.
- 계획에서는 AI가 스펙을 작은 실행 단계로 나누고 사람이 검토한다.
- 구현에서는 AI가 승인된 단계와 수용 기준을 따라 코드를 작성하고 검증한다.
- 교정에서는 사람이 결과와 설계 일치 여부를 검토한다.
- 회고에서는 발견한 실패를 규칙과 하네스에 반영한다.[1]

## 좋은 스펙의 요소

영상에서 제시한 요소를 실무 질문으로 바꾸면 다음과 같다.[1]

| 요소 | 확인 질문 |
|---|---|
| 입력·출력과 동작 | 무엇을 입력받고 어떤 관측 가능한 결과를 내는가? |
| 목적과 성공 기준 | 왜 만들며 성공을 어떻게 측정하는가? |
| 제약 | 성능, 보안, 기술 스택과 조직 정책 중 지켜야 할 것은 무엇인가? |
| 범위와 비범위 | 이번 작업에서 포함하거나 의도적으로 제외하는 것은 무엇인가? |
| 예외 처리 | 실패, 경계 조건과 복구를 어떻게 처리하는가? |

수용 기준, 인터페이스, 사용자 여정, 오류 처리와 검증 명령이 비어 있으면 AI와 반복적으로 보완한다. 프로젝트가 커지면 하나의 거대한 스펙에 모두 넣지 않고 마스터 스펙과 컴포넌트 스펙으로 나눠 단일 세션이 처리할 수 있는 크기로 관리한다.[1]

# Harness Framework 구현 분석

## 문서와 규칙을 실행 문맥으로 만든다

저장소는 다음 자료를 기본 골격으로 제공한다.[2]

| 파일 | 역할 |
|---|---|
| `CLAUDE.md` | 기술 스택, 아키텍처 규칙, 개발 프로세스와 명령 |
| `docs/PRD.md` | 목표, 사용자, 핵심 기능과 MVP 비범위 |
| `docs/ARCHITECTURE.md` | 디렉터리 구조, 패턴, 데이터 흐름과 상태 관리 |
| `docs/ADR.md` | 기술 결정, 선택 이유와 트레이드오프 |
| `docs/UI_GUIDE.md` | UI 설계 기준 |

이 문서들은 단순 참고 자료가 아니라 각 구현 세션에 다시 주입되는 가드레일 역할을 한다. 실행기는 `CLAUDE.md`와 `docs/*.md`를 읽어 Step 프롬프트 앞에 붙인다.[4]

## 자기 완결적인 Step으로 분해한다

`harness.md`는 작업 단계를 다음 원칙으로 설계하도록 요구한다.[3]

- 하나의 Step은 하나의 레이어 또는 모듈만 다룬다.
- 이전 대화를 참조하지 않고 필요한 정보를 Step 파일 안에 넣는다.
- 관련 문서와 이전 Step에서 생성한 파일을 먼저 읽게 한다.
- 함수와 클래스의 인터페이스 수준을 지시하되 핵심 제약은 명시한다.
- 수용 기준은 실제 실행 가능한 명령으로 작성한다.
- 금지 사항은 금지 대상과 이유를 구체적으로 적는다.

Step은 `phases/<task-name>/step<N>.md`로 저장되고, 전체 진행 상태는 상위 및 작업별 `index.json`에서 `pending`, `completed`, `error`, `blocked`로 추적한다.[3]

## 독립 세션 사이에 최소 컨텍스트를 전달한다

완료된 Step의 `summary`는 다음 Step 프롬프트에 누적된다. 따라서 다음 세션은 이전 대화 전체가 아니라 생성 파일과 핵심 결정의 요약을 전달받는다.[3][4]

```text
프로젝트 규칙과 설계 문서
+ 현재 Step 파일
+ 완료된 이전 Step의 요약
+ 이전 시도의 오류 메시지
```

이는 긴 메인 세션에 구현 기록을 계속 쌓는 대신 파일과 짧은 상태 정보로 작업을 연결하는 방법이다.

## 실행·재시도·Git 기록을 자동화한다

`execute.py`는 다음 순서로 작업한다.[4]

1. `feat-{phase}` 브랜치를 생성하거나 체크아웃한다.
2. 프로젝트 규칙, 설계 문서와 이전 Step 요약을 프롬프트에 넣는다.
3. Claude Code의 헤드리스 모드로 현재 Step을 실행한다.
4. 실패 정보를 다음 시도에 주입하며 최대 세 번 재시도한다.
5. 코드 변경과 실행 메타데이터를 나눠 커밋한다.
6. Step과 Phase의 상태·타임스탬프를 기록한다.
7. 선택적으로 원격 브랜치에 push한다.

## 훅은 빠른 검증과 일부 명령 차단을 담당한다

`.claude/settings.json`은 세션 종료 시 lint, build, test를 실행하고, Bash 실행 전 일부 위험 문자열을 탐지한다.[5] 이는 문서 규칙을 실행 가능한 장치로 옮긴 사례지만 완전한 권한 통제나 샌드박스는 아니다.

# 데모에서 제시한 증거

영상은 PRD, Architecture, ADR을 작성한 뒤 썸네일 생성기 구현을 여러 Step으로 나눠 독립 세션에서 실행한다. 각 Step의 상태와 커밋을 추적하고 마지막에 빌드와 테스트를 거쳐 애플리케이션을 실행하는 과정을 보여준다.[1]

다만 한 번의 성공 데모는 일반적인 신뢰성이나 생산성 향상을 입증하는 벤치마크가 아니다. 스펙이 좋아질수록 오류 가능성을 줄일 수 있다는 실무 예시로 해석하되, 다른 프로젝트·모델·권한 환경에서도 같은 결과가 재현되는지는 별도 평가가 필요하다.

# 장점

- 설계 문서와 구현 작업 사이를 자동 실행 가능한 Step으로 연결한다.
- 독립 세션으로 컨텍스트 누적을 제한한다.
- 범위, 선행 자료, 수용 기준과 금지 사항을 작업 단위로 명시한다.
- 완료·오류·차단 상태를 파일로 남겨 중단 후 재개하기 쉽다.
- 실패 메시지를 다음 시도에 전달해 제한된 자기 교정 루프를 만든다.
- 구현 코드와 실행 상태 기록을 Git 이력으로 남긴다.

# 제한과 위험

## 권한 확인 생략

원본 실행기는 Claude Code에 `--dangerously-skip-permissions`를 사용한다.[4] 장시간 무인 실행에는 편리하지만 최소 권한, 샌드박스, 네트워크 제한과 자격 증명 격리 없이 일반 프로젝트에 적용하기에는 위험하다.

## 광범위한 Git 변경

실행기는 `git add -A`, 자동 커밋과 선택적 push를 수행한다.[4] 작업 전 깨끗한 작업 트리를 확인하고 별도 clone 또는 worktree를 사용해야 한다. 보호 브랜치 반영과 원격 push는 사람 승인 뒤에 둔다.

## 완료 상태의 자기 보고

구현 에이전트가 작업별 `index.json`에 `completed`를 기록하고 실행기는 이 상태를 읽어 진행한다.[3][4] 에이전트의 완료 보고와 독립 검증을 구분하고, 빌드·테스트·정적 분석을 별도 프로세스나 CI에서 다시 실행해야 한다.

## 훅의 보안 한계

문자열 패턴으로 일부 위험 명령을 차단하는 훅은 실수 방지에는 도움이 되지만, 명령 우회·파일 권한·네트워크·자격 증명을 통제하는 보안 경계는 아니다.[5]

## Claude Code 종속성

워크플로의 원칙은 다른 에이전트에 적용할 수 있지만 현재 구현은 `CLAUDE.md`, Claude 명령과 훅, `claude -p`에 직접 결합돼 있다.[3][4] Codex 등에 적용하려면 실행 어댑터와 권한·결과 형식을 별도로 설계해야 한다.

# AI 네이티브 SDLC와의 연결

| SDLC 단계 | 이 사례가 보완하는 내용 |
|---|---|
| Intent·Spec | 목적, 성공 기준, 제약, 비범위와 예외를 구현 전에 외부화한다. |
| Plan | 계획을 독립 실행 가능한 자기 완결적 Step으로 분해한다. |
| Build | 오케스트레이터와 구현 세션을 분리하고 최소 컨텍스트만 전달한다. |
| Test | 수용 기준을 실행 명령으로 작성하고 완료 보고와 독립 검증을 분리한다. |
| Review·Deploy | 자동 커밋과 push 뒤에 사람 검토와 보호 브랜치 정책을 둔다. |
| Operate·Improve | 실패와 회고를 규칙, 스킬, 문서와 하네스 개선으로 환류한다. |

# 실무 적용 기준

## 그대로 참고할 원칙

- 문서와 규칙을 버전 관리한다.
- 작업을 작고 자기 완결적인 단계로 나눈다.
- 각 단계에 선행 자료, 범위, 인터페이스, 검증 명령과 금지 사항을 넣는다.
- 세션 간에는 전체 대화보다 결정과 산출물 요약을 전달한다.
- 오류·차단 상태와 재시도 결과를 구조화해 기록한다.

## 안전하게 수정할 부분

- 권한 확인 생략을 기본값으로 두지 않는다.
- 자동 커밋은 격리된 작업 트리와 허용 경로 안에서 수행한다.
- push는 기본 비활성화하고 사람 승인 뒤에 실행한다.
- 작업 에이전트와 검증 주체를 분리한다.
- 훅 외에 샌드박스, 자격 증명과 네트워크 통제를 적용한다.
