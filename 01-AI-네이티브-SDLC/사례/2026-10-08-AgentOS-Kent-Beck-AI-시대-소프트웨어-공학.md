# 영상 상세 정리 및 분석

**대상:** AgentOS, 「100명이 10년 걸리던 엉망을 AI로 혼자 1주일 만에 — JUnit 만든 켄트 벡이 말하는 ‘기능 사이에 멈추는 법’」

**핵심 결론:** AI는 소프트웨어를 만드는 속도를 급격히 높이지만, 그 자체로 “더 나은 프로그래밍”을 보장하지 않는다. AI 시대의 핵심 역량은 다음 기능을 계속 생성하는 일이 아니라, **기능 사이에 의도적으로 멈춰 시스템의 변경 가능성(여지, futures)을 회복하고 학습·검증하는 능력**이다.[1]

> 아래에서 **‘영상의 주장’**과 **‘분석·실무 제안’**을 구분한다.
>
> 제공된 영상은 Kent Beck의 Prodacity 2026 발표를 AgentOS가 한국어 맥락으로 편집·해설한 영상이며, 원 발표 링크가 함께 제공되어 있다.[1][2]

## 1. 영상의 논지 구조

영상은 다음 흐름으로 전개된다.

```text
AI가 코드를 빨리 만든다
  ≠ AI가 인간 프로그래머보다 낫다

기능을 빠르게 누적한다
  → 변경 여지(futures)가 줄어든다
  → 결국 아무것도 안전하게 바꾸기 어려워진다

따라서 기능 하나를 끝낼 때마다
  → 멈춘다
  → 이해·검증·정리·재설계를 한다
  → 다음 기능을 넣을 수 있는 여지를 회복한다

성과 측정도
노력/산출물(코드량·PR 수)이 아니라
사용자 행동 변화와 공동의 미션으로 옮겨야 한다
```

# 2. 영상 요약

## 2.1 AI가 만드는 것은 종종 “그럴듯한 코드”이지 “작동하는 소프트웨어”가 아니다

**타임스탬프: 1:15–4:09**

Kent Beck은 “AI가 이제 인간보다 코딩을 잘한다”는 식의 주장에 반대한다. 그의 기준은 문법적으로 맞는 코드나 데모가 아니라, **실제로 요구된 일을 안정적으로 수행하는 프로그램인지**이다.[1]

영상에서 구분하는 것은 다음과 같다.

| 구분 | 의미 |
|---|---|
| 그럴듯함(plausible) | 문법이 맞고, 코드 형태가 자연스럽고, 얼핏 동작할 듯 보이는 상태 |
| 실제 작동함(working) | 요구한 입력·환경·경계 조건에서 실행되고, 수정 후에도 회귀하지 않는 상태 |
| “C compiler-ish” | C 컴파일러처럼 보이지만 실제 C 프로그램을 효율적으로 컴파일·실행하지 못하는 상태 |

Beck의 문제 제기는 AI가 실패한다는 단순한 비판이 아니다. 오히려 **AI가 빠르게 산출물을 만들기 때문에, ‘보여지는 진척’과 ‘검증된 가치’를 혼동하기 쉬워진다**는 비판이다.[1]

### 분석

이 주장은 AI 에이전트 도입에서 특히 중요하다. AI 생성물은 보통 다음 순서로 신뢰하면 위험하다.

```text
코드가 생성됨
→ 테스트가 일부 통과함
→ 데모가 됨
→ 요구사항을 충족했다고 판단함
```

여기에는 빠진 단계가 있다.

```text
명시된 수용 기준 충족
→ 경계 조건 검증
→ 기존 기능 회귀 검증
→ 실제 실행 환경 검증
→ 사용자·운영 관점의 결과 검증
```

즉, **AI가 만든 코드의 위험은 ‘못 만든다’보다 ‘거의 맞아 보인다’에 더 가깝다.** 따라서 AI-native 개발에서 핵심 병목은 코드 생성이 아니라 **독립적인 검증과 피드백 루프**가 된다.

## 2.2 전통적 코드 크래프트의 일부 레버리지는 줄어들었다

**타임스탬프: 4:54–7:11**

Beck은 과거 자신이 강조했던 코드 크래프트의 요소들—신중한 명명, 작은 함수 분해, 들여쓰기, 공백, 사람이 읽기 좋은 구조—중 일부가 AI 시대에는 과거와 같은 직접적 레버리지를 갖지 않는다고 말한다.[1]

그 이유는 AI가 코드 설명, 탐색, 변환, 초안 생성을 지원하기 때문이다. 사람이 코드의 모든 세부 구조를 장기간 기억하고 직접 해석해야 했던 비용이 줄어든 것이다.

다만 그는 **사람이 읽을 수 있는 시스템을 포기해야 한다**고 말하지 않는다. 사람에게 읽히는 코드가 여전히 더 낫다고 보되, 코드의 국소적 미학을 다듬는 데 쓰던 에너지를 더 높은 수준의 판단에 배분해야 한다고 본다.[1]

### 분석: “가독성의 종말”이 아니라 “가독성의 목적 변화”

이 부분은 오해하기 쉽다.

| 잘못된 해석 | 더 적절한 해석 |
|---|---|
| AI가 설명해 주니 사람이 읽을 수 없는 코드도 괜찮다 | AI가 설명을 도와도 사람이 시스템의 책임·경계·위험을 판단할 수 있어야 한다 |
| 리팩터링은 중요하지 않다 | AI가 빠르게 구현하므로, 리팩터링의 목표를 ‘예쁜 코드’에서 ‘변경 가능성·검증 가능성’으로 더 명확히 잡아야 한다 |
| 코드 상세는 전부 AI에게 맡긴다 | 세부 구현보다 제품 경계, 데이터 계약, 보안, 테스트 전략, 운영 가능성의 판단 비중이 커진다 |

AI가 코드 설명을 해도, 그 설명이 정확하다는 보장은 없다. 영상에서도 Beck은 AI가 “거짓말하지 않는다면” 더 빠르게 이해할 수 있다고 단서를 둔다.[1] 따라서 가독성은 여전히 중요하지만, **AI에게 설명을 받기 위한 가독성**이 아니라 **사람이 AI의 설명과 결과를 반증·판단할 수 있게 하는 가독성**이어야 한다.

## 2.3 핵심 모델: Features와 Futures의 교환 관계

**타임스탬프: 8:40–17:07**

영상의 중심 개념은 **Features(현재 제공하는 기능)**와 **Futures(앞으로 선택할 수 있는 변경 가능성·옵션·여지)**의 관계다.[1]

### 영상의 모델

프로젝트 시작점에는 만들 수 있는 선택지가 많지만 실제 기능은 없다.

```text
초기 상태
- Features: 거의 없음
- Futures: 매우 많음
```

기능을 하나 구현하면 사용자는 가치를 얻지만, 동시에 그 구현은 이후 선택지를 제약한다.

- 공개 API를 만들면 하위 호환성을 유지해야 한다.
- 데이터 모델을 선택하면 이후 변경 비용이 생긴다.
- 임시 구현을 누적하면 의존성과 예외가 쌓인다.
- 잘못된 방향을 택했다면 제거·이행 비용이 발생한다.

즉, 기능 하나를 만드는 것은 어느 정도의 futures를 소비하는 일이다.[1]

```text
기능 추가
  → 현재 가치 증가
  → 미래의 선택지 일부 감소
```

문제는 기능을 쉬지 않고 누적할 때다.

```text
Feature 1 → Feature 2 → Feature 3 → Feature 4 → ...
                                  ↓
                    변경하기 어려운 복잡한 시스템
                                  ↓
                   작은 수정도 다른 부분을 깨뜨림
                                  ↓
                      재작성 프로젝트 시작
```

Beck은 과거에는 “100명, 10년”이 걸려 도달하던 변경 불가능한 엉망 상태에, AI를 사용하면 “한 사람, 일주일”만에도 도달할 수 있다고 풍자한다.[1]

### 분석: AI는 부채를 줄이지 않고, 부채 축적 속도를 높일 수 있다

이 모델의 가장 중요한 함의는 다음이다.

> AI가 구현 비용을 낮추면, 좋은 설계가 자동으로 만들어지는 것이 아니라 **나쁜 결정도 훨씬 더 빨리 누적된다.**

기존에는 개발 속도와 인력 제약이 일종의 자연스러운 완충 장치였다. AI는 그 장벽을 낮춘다. 따라서 다음 현상이 나타날 수 있다.

| 이전의 문제 | AI 도입 후 악화될 수 있는 형태 |
|---|---|
| 요구사항이 불명확함 | 불명확한 요구사항이 더 많은 코드로 즉시 확장됨 |
| 설계 결정을 미룸 | 임시 구조가 더 넓은 범위로 복제됨 |
| 테스트가 부족함 | 검증되지 않은 변경이 더 자주 병합됨 |
| 중복 구현 | 에이전트·세션별로 유사하지만 다른 구현이 누적됨 |
| 추적하기 어려운 의존성 | 빠른 도구 호출과 자동화로 외부 결합이 확대됨 |

따라서 “AI로 개발 속도가 빨라졌다”는 사실만으로 생산성이 높아졌다고 말할 수 없다. **미래 변경 하나를 얼마나 안전하고 싸게 할 수 있는가**까지 봐야 한다.

## 2.4 대안: 기능과 기능 사이에서 쉬어라

**타임스탬프: 11:50–16:32**

Beck은 첼리스트 Pablo Casals에 관한 “음표 사이에서 쉰다”는 일화를 빌려, 기능과 기능 사이의 정지 구간을 강조한다. 그는 해당 일화가 사실이 아닐 수 있다는 점도 직접 밝히지만, 비유 자체는 유효하다고 사용한다.[1]

기능 하나가 완료된 뒤, AI가 다음 기능을 구현하겠다고 할 때 사람이 즉시 “다음 기능”을 지시하지 않는 순간이 중요하다.

그 사이에 가능한 작업은 다음과 같다.[1]

- 중복 제거
- 리팩터링
- 가독성 개선
- 오류 원인 제거
- 테스트 보강
- 방금 만든 구현을 폐기하고 다른 방식으로 재구현
- 요구사항과 실제 구현의 차이 재검토
- 관측·운영·보안 관점의 결함 점검

그의 경제적 모델은 다음과 같다.

```text
프로젝트의 가치
= 현재 제공되는 기능(Features)
+ 앞으로 만들고 바꿀 수 있는 가능성(Futures)
```

즉, 리팩터링이나 재설계는 단순한 비용이 아니라 **미래 선택지를 되살리는 가치 생산 활동**이다.[1]

### 분석: “기능 사이의 휴식”을 작업 단위의 품질 게이트로 바꿔야 한다

이 원칙은 감각적인 조언으로 두면 실행되지 않는다. AI 개발 환경에서는 명시적인 작업 흐름으로 만들어야 한다.

권장 루프는 다음과 같다.

```text
1. 작은 기능 구현
2. 수용 기준과 자동 테스트로 동작 확인
3. 기능 간 점검 구간
   - 요구사항과 구현의 불일치 확인
   - 회귀 테스트·통합 테스트
   - 중복·복잡도·결합도 점검
   - 데이터·API 호환성 확인
   - 관측성·오류 처리 확인
   - 다음 변경의 난이도 검토
4. 필요하면 리팩터링 또는 재설계
5. 다음 기능 착수
```

핵심은 3번을 “시간이 남으면 하는 리팩터링”이 아니라 **다음 기능을 허용하기 전의 기본 게이트**로 만드는 것이다.

### 실무 의사결정 질문

다음 질문에 “아니오”가 많다면 새 기능보다 futures 회복 작업이 우선이다.

- [ ] 현재 기능의 수용 기준과 테스트 근거가 있는가?
- [ ] AI가 생성한 코드의 핵심 경로를 사람이 설명하거나 반증할 수 있는가?
- [ ] 다음 기능을 추가할 때 어느 모듈을 바꿔야 하는지 예측 가능한가?
- [ ] 기존 계약(API·데이터·이벤트)을 깨지 않고 변경할 수 있는가?
- [ ] 오류·성능 저하·실패가 발생했을 때 관측할 수 있는가?
- [ ] 비슷한 기능을 같은 방식으로 다시 구현할 수 있을 만큼 패턴이 명확한가?

## 2.5 완전 무인 “다크 팩토리”의 위험

**타임스탬프: 18:17–22:44**

Beck은 사람이 전혀 개입하지 않는 “dark software factory”를 시도해 봤지만, 항상 탈선했다고 말한다. 여기서 “다크”는 악의적이라는 뜻이 아니라 **사람과 피드백이 없는 자동화 공장**이라는 의미다.[1]

그가 지적하는 위험은 다음과 같다.

1. AI는 인간이 피드백을 수집하고 해석할 수 있는 속도보다 더 빠르게 결과물을 만든다.
2. 자동 실행은 진행 중일 때 매우 인상적으로 보인다.
3. 그러나 시스템이 잘못된 방향으로 달리고 있을 수 있다.
4. 마지막에야 오류를 발견하면 많은 산출물이 남아도 학습과 수정 여지는 줄어든다.

그는 Ward Cunningham과의 일화를 통해, 어느 날 오후에 작성한 “약간 찜찜하지만 동작하던” 코드를 꺼 버리고 다음 날 약 15분 만에 더 명확하게 다시 구현했던 경험을 이야기한다.[1]

그가 끌어내는 결론은 다음이다.

> 목표를 “소프트웨어 생산”으로 두면 학습은 우연히 일어난다.
> 목표를 “학습 극대화”로 두면 소프트웨어는 그 부산물로 나온다.[1]

### 분석: 자율성 수준은 “행동량”이 아니라 “되돌림·검증 능력”에 맞춰야 한다

완전 자율 에이전트가 위험한 이유는 에이전트가 많은 행동을 하기 때문만이 아니다. **행동 속도에 비해 독립 검증, 사람의 이해, 되돌리기 비용이 따라가지 못하기 때문**이다.

따라서 에이전트 자율성은 다음 조건을 기준으로 높여야 한다.

| 조건 | 낮을 때의 정책 | 높을 때 가능한 정책 |
|---|---|---|
| 되돌릴 수 있는가 | 사람 승인 후 실행 | 제한적 자동 실행 가능 |
| 결과를 자동 검증할 수 있는가 | 구현 보조만 허용 | 테스트 통과 범위에서 자동 반복 가능 |
| 외부 부작용이 있는가 | 승인 필수 | 샌드박스 범위 내 자동화 가능 |
| 실패를 빨리 감지할 수 있는가 | 짧은 작업 단위 유지 | 더 긴 작업 위임 가능 |
| 변경 범위를 이해할 수 있는가 | 사람 검토 강화 | 단계적 자율성 확대 가능 |

예를 들어, 로컬 테스트 코드 생성과 실행은 자동화하기 쉽지만, 데이터 삭제·배포·권한 변경·결제 흐름 수정처럼 되돌림이 어렵거나 외부 부작용이 큰 작업은 같은 방식으로 무인화하면 안 된다.

## 2.6 Spec-Driven Development 비판: 스펙을 한 번 쓰고 AI에게 넘기는 방식은 워터폴의 재현이다

**타임스탬프: 23:28–24:42**

Beck은 “좋은 스펙을 작성하면 AI가 좋은 소프트웨어를 한 번에 만들어 줄 것”이라는 관념을 비판한다. 그는 이를 과거 워터폴 개발의 환상과 유사한 것으로 본다.[1]

그의 논리는 다음과 같다.

```text
좋은 스펙 작성
→ AI가 구현
→ 완성된 제품
```

이라는 일방향 흐름은 현실의 개발 과정을 충분히 반영하지 못한다. 개발 중에 드러난 사실이 이전 설계와 요구사항을 다시 바꿔야 하기 때문이다.

영상에서 언급한 Royce의 1970년 논문도 단방향 단계 진행의 위험을 지적하며, 인접 단계 사이의 반복 관계와 피드백을 설명한다.[1][3]

### 분석: 문제는 스펙이 아니라 “스펙의 지위”다

이 영상은 스펙 자체를 폐기하자는 주장이 아니다. 오히려 기존 저장소의 **Intent → Spec → Plan → 구현 → 테스트 → 운영** 흐름과도 양립할 수 있다.

구분해야 할 것은 다음이다.

| 나쁜 사용 | 좋은 사용 |
|---|---|
| 스펙을 완결된 계약으로 취급 | 스펙을 현재 최선의 가설로 취급 |
| 한 번 작성하고 구현 단계에 넘김 | 구현·검증 결과에 따라 스펙도 갱신 |
| 구현 완료를 스펙 충족으로 간주 | 사용자·운영 결과까지 관찰 |
| AI에 스펙을 던지고 결과를 기다림 | 작은 작업 단위마다 인간·테스트 피드백 삽입 |
| 문서 충실도를 성과로 측정 | 의사결정 품질과 검증 가능성을 성과로 측정 |

즉, **Spec-Driven Development가 워터폴이 되는 순간은 스펙을 “피드백을 받지 않는 일회성 명세”로 다룰 때**이다.

반대로 좋은 스펙은 다음을 위해 존재한다.

- AI와 사람 사이의 의도 정렬
- 수용 기준의 명시
- 범위·비범위·제약의 외부화
- 구현 중 발견한 사실을 반영할 수 있는 기준점
- 테스트·리뷰·운영 관측의 추적 기준

## 2.7 노력 → 산출물 → 성과 → 미션

**타임스탬프: 26:24–32:10**

영상 후반부에서 Beck은 개발의 가치 사슬을 다음과 같이 확장한다.[1]

```text
노력(Effort)
  → 산출물(Output)
    → 사용자 성과(Outcome)
      → 미션(Mission)
```

| 단계 | 예시 | 한계 |
|---|---|---|
| 노력 | 개발 시간, 토큰 사용량, 에이전트 수 | 많이 썼다고 가치가 생기지 않음 |
| 산출물 | 코드 라인 수, PR 수, 생성된 기능 수 | 많이 만들었다고 사용자가 성공한 것은 아님 |
| 성과 | 사용 행동 변화, 전환율, 오류 감소, 작업시간 감소 | 제품마다 적절한 정의가 필요 |
| 미션 | 조직과 사용자가 함께 달성하려는 목적 | 측정이 어렵지만 가장 중요함 |

그는 AI가 20만 줄의 코드를 만들었다는 사실은 노력이나 산출물의 지표일 뿐, 미션 달성과 직접적 관계가 없다고 지적한다.[1]

또한 “지표가 목표가 되면 좋은 지표가 아니게 된다”는 Goodhart의 법칙을 인용하면서, 더 강한 표현을 사용한다. 단지 측정이 왜곡되는 정도가 아니라, **사람들이 지표를 개선하려고 시스템 전체를 더 나쁘게 만들 수 있다**는 것이다.[1]

### 분석: AI 시대의 생산성 지표는 더 쉽게 왜곡된다

AI는 코드량·PR 수·커밋 수·완료 티켓 수 같은 선행 지표를 폭발적으로 늘릴 수 있다. 그러므로 이전부터 불완전했던 지표가 더 위험해진다.

| 측정하지 말아야 할 단독 KPI | 왜 위험한가 | 함께 봐야 할 결과 |
|---|---|---|
| 생성 코드 라인 수 | AI가 쉽게 부풀릴 수 있음 | 결함률, 유지보수성, 실제 사용자 가치 |
| PR 수 | 작은 변경 쪼개기로 증가 가능 | 리드타임, 재작업률, 배포 성공률 |
| 에이전트 실행 횟수 | 실행은 가치가 아님 | 해결된 문제, 회귀 감소, 비용 대비 효과 |
| 완료된 기능 수 | 사용되지 않는 기능이 쌓일 수 있음 | 채택률, 사용자 행동 변화 |
| 테스트 수 | 약한 테스트를 대량 생성할 수 있음 | 결함 발견력, 변이 테스트·실패 사례 |
| 토큰 대비 코드량 | 모델의 산출량일 뿐 | 미션·고객·운영 결과 |

실무에서는 “AI 도입으로 얼마나 많은 코드를 만들었나?”보다 다음 질문이 더 중요하다.

1. 사용자의 행동이나 업무 결과가 실제로 좋아졌는가?
2. 변경 하나를 안전하게 완료하는 시간은 줄었는가?
3. 회귀 결함, 장애, 재작업은 줄었는가?
4. 다음 기능을 넣을 때의 복잡도와 불확실성은 줄었는가?
5. 팀이 제품과 시스템을 더 잘 이해하게 되었는가?

# 3. 이 영상이 제안하는 AI-native SDLC 원칙

## 원칙 1. AI의 속도에 맞춰 기능 속도를 올리지 말고, 검증 주기를 짧게 만든다

AI가 빠르게 구현할 수 있다는 것은 짧은 피드백 주기를 만들 수 있다는 뜻이어야 한다.

```text
잘못된 적용
AI가 빠르다 → 기능 묶음을 더 크게 만든다 → 마지막에 통합한다

권장 적용
AI가 빠르다 → 작업 단위를 더 작게 만든다 → 더 자주 검증한다
```

## 원칙 2. “완료”를 구현 완료가 아니라 검증된 학습 단위로 정의한다

기능 완료의 기준을 다음처럼 넓히는 것이 좋다.

```text
구현 완료
+ 자동 테스트 통과
+ 수용 기준 확인
+ 회귀 영향 확인
+ 운영·관측 요구 충족
+ 다음 변경을 가로막는 부채 확인
= 작업 단위 완료
```

## 원칙 3. futures를 측정 가능한 대리 지표로 관리한다

“변경 가능성” 자체를 완벽하게 수치화하기는 어렵다. 그러나 다음 같은 관측 지표로 악화를 감지할 수 있다.

| 관찰 대상 | futures가 줄고 있다는 신호 |
|---|---|
| 변경 범위 | 작은 기능도 여러 모듈·서비스를 동시에 수정해야 함 |
| 회귀 | 사소한 변경 뒤 기존 테스트가 자주 깨짐 |
| 배포 | 기능 출시 후 핫픽스·롤백이 반복됨 |
| 이해 비용 | 새 작업마다 AI와 사람이 코드 구조를 처음부터 재발견해야 함 |
| 테스트 | 테스트가 구현 세부에 강하게 묶여 리팩터링을 막음 |
| 의존성 | 순환 의존성, 숨은 전역 상태, 공유 DB 결합이 증가함 |
| 작업 재개 | 이전 결정·미완료 상태를 복원하는 데 긴 시간이 듦 |

이 지표들은 단독 KPI로 경쟁시키기보다, **다음 기능을 시작해도 되는지 판단하는 건강도 신호**로 써야 한다.

## 원칙 4. 스펙은 AI 자동생성의 입력값이 아니라 반복 학습의 기준점이다

기존 `intent.md`, `spec.md`, `plan.md` 구조는 Beck의 비판과 충돌하지 않는다. 다만 다음처럼 운용해야 한다.

```text
Intent
  → 왜 이 문제를 푸는가?

Spec
  → 지금 시점에서 무엇을 관측 가능하게 달성할 것인가?

Plan
  → 어떻게 작고 검증 가능한 단계로 만들 것인가?

Implementation
  → 가설을 구현한다

Verification / Observation
  → 가설이 맞는지 확인한다

Feedback
  → Intent, Spec, Plan 중 무엇을 수정해야 하는가?
```

여기서 문서는 승인 후 고정되는 산출물이 아니라, **새로운 증거에 따라 갱신되는 의사결정 기록**이다.

# 4. 영상의 강점과 한계

## 강점

1. **AI 생산성 담론의 핵심 착시를 정확히 짚는다.** 코드 생성량과 실제 가치·신뢰성을 구분한다.
2. **기술 부채를 미래 선택지의 손실로 설명한다.** 단순히 “코드가 지저분해진다”보다 훨씬 전략적인 언어다.
3. **리팩터링을 비용이 아닌 가치 회복으로 재정의한다.** “다음 기능을 만들 수 있는 능력”을 되살리는 투자로 볼 수 있다.
4. **완전 자동화의 위험을 속도와 피드백 불균형으로 설명한다.** 사람 검토를 감정적 통제 장치가 아니라 학습·검증 장치로 본다.
5. **지표의 위험을 AI 시대에 맞게 확장한다.** 산출물 중심 생산성 지표의 왜곡 가능성이 더 커졌음을 보여 준다.

## 한계 및 보완점

1. **‘얼마나 자주 멈출지’에 대한 운영 규칙은 제시하지 않는다.** 실제 팀에는 기능 크기, 위험도, 되돌림 가능성에 따른 구체적 게이트가 필요하다.
2. **futures의 비용·가치를 정량화하기 어렵다.** 조직은 가시적인 기능과 매출 압박을 받으므로, 리팩터링을 위한 시간·예산 보호 장치가 필요하다.
3. **AI의 장기 자율 실행을 전면 부정하는 것으로 읽히면 안 된다.** 테스트 가능하고 되돌릴 수 있으며 외부 부작용이 제한된 작업은 높은 자율성을 허용할 수 있다. 핵심은 무인 실행 자체가 아니라, **독립 검증과 안전한 복구의 부재**다.
4. **스펙 주도 개발 비판은 ‘고정 스펙 기반 일괄 위임’에 한정해 해석해야 한다.** 실행 가능한 수용 기준, 작은 계획 단위, 피드백에 따른 스펙 갱신은 오히려 영상의 반복 개발 철학과 잘 맞는다.

# 5. 이 저장소의 AI 네이티브 SDLC 구조에 적용할 변화

현재의 `Intent → Spec → Plan → Code/Test/Deploy/Operate` 구조는 유지하되, 각 기능 사이에 다음 단계가 명시적으로 들어가면 좋다.

```text
Intent
  → Spec
    → Plan
      → 작은 기능 구현
        → 검증
          → Futures 회복 점검
            → 다음 기능 또는 리팩터링
```

## 기능 완료 후 추가할 “Futures 회복 점검”

`테스트-검증-기록.md` 또는 `구현-변경-기록.md`에 다음 항목을 넣는 방식을 권장한다.

```markdown
## 다음 변경 가능성 점검

- 이번 변경으로 새로 고정된 API·데이터·운영 계약은 무엇인가?
- 다음 기능 구현 시 예상되는 변경 지점은 무엇인가?
- 중복, 임시 우회, 숨은 결합, 미검증 가정은 남아 있는가?
- 지금 해결해야 할 리팩터링·테스트·관측성 작업은 무엇인가?
- 다음 기능으로 진행해도 되는 근거는 무엇인가?
```

이 기록의 목적은 문서량을 늘리는 것이 아니라, AI가 빠르게 누적시키기 쉬운 **암묵적 제약과 미래 비용을 보이게 만드는 것**이다.

# 6. 최종 판단

이 영상은 “AI가 코딩을 잘하는가?”라는 질문을 더 유용한 질문으로 바꾼다.

```text
AI가 코드를 얼마나 빨리 만들 수 있는가?
```

보다 중요한 질문은 다음이다.

```text
AI가 만든 변경을 우리는 얼마나 빨리 이해·검증·되돌릴 수 있는가?
그리고 그 과정이 다음 변경의 가능성을 늘리는가, 줄이는가?
```

AI 시대의 좋은 개발 조직은 AI에게 기능을 연속으로 생성시키는 조직이 아니라,

- 작은 단위로 구현하고,
- 실제 동작을 독립적으로 검증하며,
- 기능 사이에서 의도적으로 멈추고,
- 설계·테스트·관측성·문서를 통해 futures를 회복하고,
- 코드량이 아니라 사용자와 조직의 미션으로 성과를 판단하는 조직

이라고 정리할 수 있다.
