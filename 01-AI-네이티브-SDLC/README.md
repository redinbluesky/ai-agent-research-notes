# AI 네이티브 SDLC 개요

## 1. 정의

AI 네이티브 SDLC는 AI 에이전트를 단순 코드 생성 도구로 한정하지 않고, **계획 → 설계 → 구현 → 테스트 → 배포 → 운영** 전 과정의 초안 작성과 피드백 루프에 연결하는 개발 방식이다.

AI가 코드 작성 속도를 크게 높인 상황에서 요구사항 정리, 리뷰, 테스트, 배포, 운영이 새 병목이 되는 문제를 해결하는 데 목적이 있다.

> 원칙: **AI는 초안과 반복 검증을 맡고, 사람은 제품·우선순위·고위험 변경의 판단과 승인을 책임진다.**

---

## 2. 핵심 원칙

1. **의도를 코드보다 먼저 기록한다.**  
   구현 결과만으로는 왜 해당 변경이 필요한지 알기 어렵다. 큰 기능은 `intent.md`로 문제와 목표를 먼저 남긴다.

2. **단계별 산출물을 Markdown으로 축적한다.**  
   다음 단계의 사람과 AI가 읽을 수 있도록 문서, 코드, 테스트 결과, 회고를 저장소에 남긴다.

3. **AI가 모든 단계의 초안을 만든다.**  
   AI는 문서·설계·코드·테스트·분석의 초안과 반복 작업을 담당한다.

4. **사람은 책임 있는 승인에 집중한다.**  
   제품 방향, 우선순위, 보안·인증·결제·개인정보와 같은 고위험 변경은 사람이 판단한다.

5. **코드뿐 아니라 AI 작업 환경도 검증한다.**  
   규칙 파일, 스킬, 훅, 프롬프트 변경도 에이전트 성능에 영향을 주므로 eval과 CI 검증 대상에 포함한다.

---

## 3. 전체 흐름

```text
Intent (왜 만드는가)
  → Spec (무엇을 만들 것인가)
    → Plan (어떻게 구현·검증할 것인가)
      → Code / Test / Deploy / Operate
```

| 단계 | 핵심 질문 | AI 역할 | 사람 역할 | 대표 산출물 |
|---|---|---|---|---|
| 계획 | 왜 만드는가? | 질문·정리·의도서 초안 | 문제와 우선순위 승인 | `intent.md` |
| 설계 | 무엇을 만드는가? | 요구사항·설계·목업 초안 | 요구사항·설계 결정 승인 | `spec.md` |
| 구현 준비 | 어떻게 만들고 검증하는가? | 코드베이스 분석·계획 초안 | 구현 범위·아키텍처 판단 | `plan.md` |
| 구현·테스트 | 제대로 동작하는가? | 코드·테스트 생성 및 반복 실행 | 고위험 결과 검토 | 코드, 테스트, CI 결과 |
| 배포 | 안전하게 출시 가능한가? | 다층 리뷰·정책 검사 | 위험 기반 배포 승인 | 리뷰·배포 기록 |
| 운영 | 품질 저하·장애를 어떻게 대응할까? | 지표 분석·원인·수정안 초안 | 실제 조치와 우선순위 결정 | 회고, 후속 PR |

## 4. 핵심 문서

### 4.1 `CLAUDE.md` 또는 `AGENTS.md`

AI 에이전트가 따라야 할 팀 공통 규칙을 제공한다.

- 빌드·테스트·린트 명령
- 코드 스타일과 디렉터리 구조
- 아키텍처·의존성 규칙
- 보안·배포 정책
- `intent.md`, `spec.md`, `plan.md`을 참조하도록 하는 지침

### 4.2 `intent.md` — 왜 만드는가

복잡하거나 영향 범위가 큰 기능의 출발점이다. PM, PO, CS, 운영, 개발자 등 **문제를 발견한 누구나** AI와 대화하며 초안을 만들 수 있고, PO 또는 책임자가 검토·승인한다.

```md
# Intent: [기능 또는 문제 이름]

Author: [이름]
Status: draft

## Problem
- 현재 누가 어떤 문제를 겪는가?
- 문제의 근거는 무엇인가?

## Proposed outcome
- 해결되면 무엇이 달라지는가?
- 성공을 어떻게 판단하는가?

## Affected users and systems
- 사용자:
- 영향을 받는 시스템:

## Constraints
- 반드시 지켜야 할 것:
- 범위 밖인 것:

## Open questions
- 아직 결정하지 못한 사항:
```

### 4.3 `spec.md` — 무엇을 만드는가

승인된 intent를 요구사항과 설계로 구체화한다. 일반적으로 AI가 초안을 만들고 PO가 승인한다.

```md
# Spec: [기능 이름]

Related intent: `[intent.md 경로]`
Status: draft

## Goals
## Non-goals
## Functional requirements
## User flows / UX
## Technical design
## Data and API changes
## Security, privacy, and performance
## Acceptance criteria
- [ ]

## Open questions
```

### 4.4 `plan.md` — 어떻게 구현·검증하는가

개발 직전에 코드베이스 문맥을 바탕으로 작성한다. 어떤 파일을 어떤 순서로 변경하고, 어떤 방식으로 검증할지를 명확히 한다.

```md
# Plan: [기능 이름]

Related intent: `[intent.md 경로]`
Related spec: `[spec.md 경로]`

## Scope
## Files and components to change
## Implementation steps
1.

## Validation plan
- [ ] Lint
- [ ] Build
- [ ] Unit / integration tests
- [ ] E2E or UI verification
- [ ] Security / migration checks, if applicable

## Rollback / rollout plan
## Risks and open questions
```

## 5. 구현·테스트·배포·운영 원칙

### 구현

- 에이전트가 코드와 테스트를 생성하되, 팀 규칙·아키텍처·보안 기준을 규칙 파일과 스킬에 명확히 제공한다.
- 기능 범위가 커져 `spec.md`가 여러 개 필요해진다면, 하나의 큰 기능으로 관리하기보다 intent를 더 작은 독립 단위로 나눈다.

### 테스트

- lint, build, unit/integration/e2e 테스트를 CI의 기본 관문으로 둔다.
- UI 변경은 브라우저 기반 검증이나 스크린샷 검증을 포함한다.
- 가능하면 TDD 흐름(실패 테스트 → 최소 구현 → 리팩터링)을 적용한다.
- 에이전트가 테스트 통과만을 위해 테스트를 무단 수정하지 않도록 보호 훅을 고려한다.
- 규칙 파일·스킬·훅 변경 시에도 대표 과업 기반 eval을 실행한다.

### 배포

- AI 리뷰와 자동 정책 검사를 먼저 수행한다.
- 인증, 결제, 개인정보, 권한, 대규모 데이터 변경 등은 사람의 명시적 승인을 필수로 한다.
- 정책 위반은 가능하면 리뷰 이후가 아니라 에이전트 편집 시점의 훅에서 차단한다.

### 운영

- CI 실패율, 오류율, 성능 저하, PR 리드타임 등은 규칙 기반 임계치로 감지한다.
- AI는 감지 이후 로그와 코드를 분석하고 원인·수정안·회고 초안을 만든다.
- 사람 승인 후 실제 조치하고, 장애 회고와 후속 작업을 저장소에 남겨 다음 intent의 입력으로 활용한다.

## 6. 단계적 도입 체크리스트

### 1단계 — 의도 기록

- [ ] 큰 신규 기능에 `intent.md`를 작성한다.
- [ ] PO 또는 책임 승인자를 지정한다.
- [ ] 에이전트 규칙 파일에 intent 문서를 읽도록 명시한다.

### 2단계 — 설계와 구현 계획 분리

- [ ] `spec.md`에 요구사항, 예외, 수용 기준을 기록한다.
- [ ] `plan.md`에 변경 파일, 구현 순서, 검증 방법을 기록한다.
- [ ] Intent → Spec → Plan별 승인 기준을 정한다.

### 3단계 — 품질 피드백 자동화

- [ ] lint, build, unit/integration/e2e 테스트를 CI 필수 항목으로 둔다.
- [ ] UI 변경에는 브라우저 기반 검증을 추가한다.
- [ ] 에이전트 규칙·스킬·훅 변경에도 eval을 실행한다.
- [ ] 보안·정책 위반을 편집 단계에서 차단하는 훅을 적용한다.

### 4단계 — 운영 루프 연결

- [ ] 오류율, CI 실패율, 성능 저하, PR 리드타임을 모니터링한다.
- [ ] 결정론적 임계치로 이벤트를 감지한다.
- [ ] AI가 분석·문서·수정안 초안을 만들고, 사람 승인 후 조치한다.
- [ ] 장애 회고와 후속 작업을 저장소에 남긴다.

---

## 7. 적용 범위와 주의사항

- 모든 작업에 문서 절차를 강제하지 않는다. 오탈자나 명확한 단순 버그는 바로 수정하는 편이 낫다.
- `intent.md`는 특정 도구가 자동 인식하는 예약 파일이나 업계 표준이 아니라, 의도를 관리하기 위한 권장 방식이다.
- AI의 결과물은 빠른 초안이지 최종 의사결정이 아니다.
- 티켓·Notion 등 외부 도구를 사용하더라도, 원본 위치와 저장소 문서 간 연결을 명확히 한다.

## 8. AI 시대의 품질 원칙

### 구현 품질과 결정 품질을 구분한다

AI가 구현을 빠르게 만들수록, 올바른 문제·아키텍처·트레이드오프·성공 기준을 선택하는 결정 품질이 더 중요해진다. 큰 기능의 intent와 spec에는 성능, 비용, 신뢰성, 보안, 사용자 경험의 우선순위를 명시한다.

### 변경을 시스템 단위로 검토한다

파일 단위 코드 정확성뿐 아니라 API, 데이터 계약, 이벤트, 인프라, 보안 정책, 모니터링, 다운스트림 서비스에 미치는 영향을 함께 검토한다.

### 신뢰는 저자가 아니라 행동 증거에서 얻는다

AI 또는 사람이 작성한 코드인지와 무관하게, 단위·통합·계약·보안·성능 테스트와 런타임 관측 결과를 신뢰의 근거로 둔다.

### 표준을 실행 가능한 가드레일로 만든다

보안, 아키텍처, 테스트, 배포 기준은 문서에만 두지 않는다. CI, 정적 분석, 템플릿, 훅, 정책 코드화를 통해 개발 흐름에 내재화한다.

### 품질을 라이프사이클 전반의 활동으로 다룬다

품질은 릴리스 직전의 체크포인트가 아니라 계획부터 운영까지 지속적으로 검증·관측·개선하는 활동이다.
