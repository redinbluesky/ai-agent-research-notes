# 차세대 에이전트 친화적 웹 어플리케이션의 장점과 구축 원칙

## 1. 제안 요약

**목표는 기존 화면의 복제가 아니라, 기존 업무 지식을 복원하고 사람·에이전트 공용의 차세대 실행 구조로 재설계하는 것이다.**

Aside·REA로 허가된 기존 시스템의 동작과 근거를 조사하고, 현업과 함께 업무 객체·상태·규칙·예외를 정리한다. Codex 또는 Claude Code는 승인된 범위에서 명세·구현·테스트·문서화를 수행한다. 구축 이후에도 같은 업무 지식·테스트·관측 환경을 유지보수에 재사용한다.

### 제안서에 사용할 핵심 가치

- **구축 속도:** 야간·비업무 시간에도 구현과 검증을 진행하여 다음 검토까지의 대기 시간을 줄인다.
- **브라우저까지 확인하는 품질:** Aside를 활용해 실제 화면·입력·이동·결과를 확인하고 API·데이터 검증과 연결한다.
- **업무 실행의 안정성:** 사람 UI와 에이전트 도구가 공통 업무 규칙과 권한 체계를 사용한다.
- **담당자 교체 위험 완화:** 업무 지식과 설계 결정을 개인 기억이 아닌 버전 관리된 자산으로 남긴다.
- **SDLC 전반의 유지보수 지원:** 요구 변경부터 영향 분석·수정·회귀 테스트·배포 준비·운영 관측까지 연결한다.
- **미래 변경 비용 관리:** 빨리 만든 코드가 아니라 다음 변경을 안전하게 수행할 수 있는 구조를 성과로 삼는다.

> 이 문서는 출처 기반 조사와 프로젝트 적용 제안이다. 실제 대상 시스템의 성능 시험, Aside–REA 직접 연결, 무인 야간 실행 또는 비용 절감 실증은 수행하지 않았다. 확정 일정·견적·절감률은 파일럿 측정 후 산정한다.

## 2. 근거를 읽는 기준

- **출처 사실:** 공식 문서가 제공하는 기능 또는 게시자가 보고한 사례다.
- **적용 제안:** 본 프로젝트에 맞춰 구성한 아키텍처·운영·승인 정책이다.
- **기대 효과:** 전제 조건이 충족될 때 검증할 가설이며 보장된 수치가 아니다.

OpenAI는 신규 내부 제품을 Codex 중심으로 구축한 사례에서 수작업 대비 약 10분의 1의 시간을 자체 추정한다. 그러나 이는 특정 신규 제품의 보고이며, 기존 시스템의 데이터·연계·업무 이행을 포함한 본 프로젝트의 일정 약속으로 전용하지 않는다. 같은 글도 장기간의 아키텍처 일관성은 아직 학습 중이라고 밝힌다.[1]

METR의 후속 연구는 AI의 생산성 효과를 측정할 때 참여자·작업 선택 편향과 동시 에이전트 사용으로 정확한 효과 크기를 판단하기 어렵다고 설명한다. 따라서 AI 사용 여부나 생성 코드량만으로 생산성 향상을 주장하지 않는다.[7]

## 3. 개발 방식과 제품 구조를 함께 바꾼다

| 구분 | 설계 대상 | 성공 조건 |
|---|---|---|
| 에이전트 중심 개발 | 저장소 지침, 명세, 코드, 테스트, 실행 환경 | 에이전트가 근거를 찾아 작은 변경을 구현·검증할 수 있음 |
| 에이전트 친화적 웹 | 기능 발견, 입력·출력 계약, 권한, 상태·결과 | 에이전트가 화면 추측에만 의존하지 않고 업무 기능을 안전하게 실행 |
| 에이전트 친화적 유지보수 | 설계 이력, 운영 정보, 재현 절차, 복구 경로 | 다른 담당자·세션·모델도 변경 근거와 검증 방법을 이어받음 |

**AI가 개발했다는 사실만으로 에이전트 친화적인 시스템이 되는 것은 아니다.** 업무 실행 인터페이스와 개발·운영 환경을 모두 설계해야 한다.

### 목표 구조 — 적용 제안

```text
사람용 웹 UI                  에이전트용 API·MCP·선택적 WebMCP
       └────────────────┬────────────────┘
                    공통 업무 서비스
       객체·상태·규칙·권한·승인·예외·멱등성
                          │
                데이터·감사·결과 검증

개발·유지보수 에이전트
  └─ 명세·코드·테스트·브라우저·로그·메트릭·변경 이력
       └─ 영향 분석 → 작은 변경 → 독립 검증 → 사람 승인
```

WebMCP는 페이지가 기능 목적과 입력을 명시하여 에이전트의 해석 부담을 줄이는 접근이다. 다만 제안 단계의 표준이며 사람과 함께 사용하는 로컬 브라우저 흐름을 주 대상으로 한다. API/MCP와 역할을 구분하고, 야간 실행 전체를 WebMCP에 의존하지 않는다.[3]

## 4. 도구 역할과 통합 경계

| 도구·주체 | 주요 역할 | 보장하지 않는 것 |
|---|---|---|
| Aside | 기존 업무 탐색, 신규 UI 조작·스모크 테스트, 화면·페이지 검사 | 모든 결함 탐지, 모든 브라우저 호환성, 백엔드 정합성 |
| REA | 관찰 근거와 한계 수집, 정적·런타임 분석 보조 | 비공개 서버 업무 규칙 전체 복원, 원본과의 완전 동등성 |
| Codex / Claude Code | 명세화, 구현, 테스트, 분석·문서 갱신 | 업무 타당성·법적 책임·최종 승인 대체 |
| 테스트·CI·관측 도구 | 반복 가능한 판정, 회귀·보안·계약 검사 | 잘못된 수용 기준 자체의 자동 교정 |
| 현업·개발·운영 책임자 | 정책·예외 확정, 위험 판단, 수용·배포 승인 | 에이전트 실행을 검토 없이 신뢰하는 역할이 아님 |

REA의 기능과 관찰 한계는 [기존 구현 분석](01-기존-웹-어플리케이션-REA-기반-독립-구현.md)을 따른다. Aside의 세션에 REA가 직접 CDP로 붙을 수 있는지는 아직 검증하지 않았다. 확인 전에는 탐색과 관찰을 별도 테스트 프로필로 분리하고, 동일 시나리오·입력·관찰 시점을 기록한다.

Aside 내부 모델 연결과 외부 코딩 에이전트의 MCP 연결도 구분한다. 공식 개발자 문서는 CLI에서 브라우저 작업을 시작하고 `aside mcp`로 외부 에이전트에 연결하는 방식을 안내한다.[8]

| 기존 문제 | 설계 변화 | 기대 장점 | 성립 조건·측정 |
|---|---|---|---|
| 사람의 업무시간에 구현이 집중 | 승인된 작업의 야간 실행 | 개발 대기 시간 단축 | 다음 날 승인 가능한 변경안, 검토·재작업 시간까지 측정 |
| 코드 테스트와 실제 화면 동작이 분리 | 브라우저 조작과 결과 상태 검증 결합 | UI·연동 결함 조기 발견 | 성공·오류·권한별 시나리오, API·DB 판정기 |
| 업무 규칙이 개인 경험에 의존 | 명세·계약·결정 기록·테스트를 저장소에 유지 | 교체·휴직·퇴사 시 인수인계 위험 감소 | 새 담당자의 재현·변경 과제로 검증 |

| 기능 증가와 함께 숨은 결합 누적 | 작은 변경·회귀 검증·기능 간 정리 | 미래 변경 비용과 위험 완화 | 변경 범위·회귀·재작업·복구 비용 |

## 6. 야간 개발: 사람이 판단하고 에이전트가 작업을 이어간다

OpenAI는 Codex가 한 작업을 6시간 이상 수행하는 경우를 정기적으로 관찰하며, 사람이 자는 동안에도 실행한다고 보고한다. 변경별 격리 환경과 UI·로그·메트릭 관측을 제공한 사례다.[1]

Anthropic은 장기 작업에 초기 환경 구성, 기능 목록, 진행 기록, Git 이력, 한 번에 한 기능 구현과 브라우저 검증을 결합한다. 큰 프롬프트 하나만 주면 미완성 상태를 남기거나 완료를 잘못 선언하는 문제가 있었다고 설명한다.[2]

### 권장 운영

1. 주간: 현업 요구·수용 기준을 확정하고 작은 작업을 승인한다.
2. 야간: 격리 환경에서 구현·테스트·제한된 재시도·문서 갱신을 수행한다.
3. 종료: 변경안, 실행 근거, 실패·미해결 사항, 다음 작업 상태를 남긴다.
4. 다음 업무시간: 사람이 검토하고 승인·보완·중단을 결정한다.

**야간의 기본 산출물은 검토 가능한 변경안이며, 무승인 운영 배포가 아니다.**

- 시간·비용·토큰·재시도 상한을 설정한다.
- 같은 실패의 반복, 정책 충돌, 범위 확대 시 중단한다.
- 작업별 브랜치·worktree·테스트 데이터를 분리한다.
- 운영 자격 증명과 실고객 데이터는 기본 접근 대상에서 제외한다.
- 다중 에이전트는 병렬성이 있는 작업에만 적용하고 충돌·통합 비용을 측정한다.

## 7. Aside로 실제 브라우저 동작까지 검증한다

Aside 공식 문서는 로컬 웹앱을 열어 스모크 테스트를 요청하는 CLI 예시와, REPL을 통한 페이지 검사·스크린샷·다운로드·결정적 브라우저 단계를 제공한다.[8]

따라서 제안서에는 **“실제 사용자 흐름까지 확인하는 통합 검증 환경”**으로 표현한다. “Aside만으로 완벽한 테스트 환경을 보장한다”는 표현은 사용하지 않는다. Anthropic도 브라우저 검증이 코드만으로 드러나지 않는 오류 발견에 도움이 되지만 도구·시각 인식의 한계가 남는다고 설명한다.[2]

### 검증 계층 — 적용 제안

| 계층 | 검증 내용 | 실행·판정 수단 |
|---|---|---|
| 코드·업무 규칙 | 계산, 경계값, 상태 전이 | 단위 테스트, 타입·정적 검사 |
| 서비스·데이터 | API 계약, 권한, 트랜잭션·정합성 | 통합 테스트, 계약 테스트, 테스트 DB 조회 |
| 사용자 여정 | 입력, 클릭, 이동, 검색, 저장, 오류·빈 결과 | Aside 브라우저 실행 + 명시적 수용 기준 |
| 호환성·비기능 | 대상 브라우저, 접근성, 성능·부하, 보안 | 별도 대상 환경과 전문 검사 도구 |
| 운영·복구 | 배포 후 상태, 경보, 복구·보상 | 스모크 테스트, 관측 도구, 복구 훈련 |

에이전트의 “저장 성공” 응답이나 성공 화면만으로 완료 처리하지 않는다. 허가된 검증 API 또는 테스트 DB에서 실제 결과 상태를 확인한다. Anthropic의 평가 가이드도 실행 기록과 최종 환경 상태를 구분한다.[6]

대표 시나리오에는 정상 경로뿐 아니라 잘못된 입력, 권한 부족, 중복 요청, 타임아웃, 재시도, 새로고침 후 상태, 취소를 포함한다. 반복 테스트용 데이터 초기화와 안정적인 판정 기준을 마련하고 실행 시나리오·버전·결과·실패 근거를 보존한다.

## 8. 담당자가 바뀌어도 업무 지식이 남는 유지보수

### 출처 사실

OpenAI는 저장소 안에 설계 문서·실행 계획·기술 부채를 버전 관리하고, 문서 노후화 탐지와 반복적인 정리 PR을 수행하는 에이전트를 운영한다고 설명한다. UI·로그·메트릭을 에이전트에 제공하여 버그 재현과 수정 검증을 지원한다.[1]

### 프로젝트 적용 제안과 기대 효과

개인의 기억·대화방에 흩어진 정보를 다음 자산으로 남긴다.

- 업무 용어와 객체·상태·허용 행동·예외·승인권자
- 의도·명세·설계 결정과 변경 이유
- API·데이터 계약과 주요 불변 조건
- 테스트·재현 절차·개발 환경 시작 방법
- 알려진 제약·기술 부채·운영 대응·복구 절차

신규 담당자와 유지보수 에이전트가 같은 자산을 탐색하면, 이전 담당자의 설명을 반복해서 기다리는 부담과 누락 위험을 줄일 수 있다. **인수인계를 없애는 것이 아니라, 인수인계의 검증 가능성을 높이는 효과**다. 문서가 낡거나 현업의 암묵지가 빠지면 효과는 제한된다.

교체 위험은 새로운 담당자가 자료만으로 개발 환경을 실행하고, 업무 규칙을 추적하며, 대표 오류를 재현·수정·검증하는 과제로 평가한다. 특정 담당자·모델·채팅 세션에만 의존하지 않도록 결정과 근거를 공유 저장소에 남긴다.

## 9. SDLC 전반의 관리 지원으로 유지보수를 연결한다

**에이전트의 전 과정 참여와 무제한 운영 권한은 다르다.** 아래는 사람의 책임과 승인 아래 수행할 운영 모델이다.

| 단계 | 에이전트 역할 | 사람의 판단·승인 | 연결 산출물 |
|---|---|---|---|
| 요구·분석 | 기존 동작 조사, 변경 요청·예외 정리 | 업무 목표·정책 확정 | 의도·업무 명세 |
| 설계 | 영향 분석, 대안·계약·이행안 초안 | 구조·보안·비용 판단 | 설계 결정·계약 |
| 구현 | 작은 변경, 테스트·문서 갱신 | 범위·핵심 경로 리뷰 | 코드·변경 근거 |
| 검증 | 단위·통합·브라우저·회귀 테스트 | 수용 기준·검증 독립성 확인 | 테스트 결과·결함 |
| 배포 | 변경 요약, 이행·복구 준비 | 운영 반영·고위험 변경 승인 | 배포·복구 기록 |
| 운영 | 허가된 로그 분석, 오류 재현, 수정안 제안 | 사고 대응·정책·외부 영향 판단 | 장애 기록·개선 명세 |

이 구조는 유지보수 요청을 별개의 새 개발로 시작하지 않고, 기존 명세와 운영 근거에서 변경으로 연결한다. 테스트·지침·문서 갱신을 같은 변경 단위에 포함해 다음 작업의 문맥 복원 부담을 낮추는 것을 목표로 한다.

## 10. Kent Beck의 관점을 반영한 필수 구현 원칙

다음 세 원칙은 [Kent Beck 발표에 관한 기존 분석](../../../01-AI-네이티브-SDLC/사례/2026-10-08-AgentOS-Kent-Beck-AI-시대-소프트웨어-공학.md)의 해석을 이번 프로젝트 정책으로 채택한 것이다. Kent Beck의 직접 인용문으로 취급하지 않는다.

### 원칙 1. 사람이 AI의 설명과 결과를 반증·판단할 수 있게 한다

**AI에게 설명을 받기 위한 가독성이 아니라 사람이 AI의 설명과 결과를 반증·판단할 수 있게 하는 가독성**을 목표로 한다.

- 업무 규칙·모듈 책임·데이터 경계·실패 경로를 드러낸다.
- 핵심 주장에 명세·코드 위치·테스트·실행 결과를 연결한다.
- 숨은 전역 상태와 암묵적 부작용을 줄이고 계약·불변 조건을 명시한다.
- 구현 에이전트의 자기 보고만으로 승인하지 않고 독립 검증을 수행한다.

### 원칙 2. 초기 속도와 미래 변경 비용을 함께 평가한다

**“AI로 개발 속도가 빨라졌다”는 사실만으로 생산성이 높아졌다고 말할 수 없다. 미래 변경 하나를 얼마나 안전하고 싸게 할 수 있는가까지 봐야 한다.**

- 기능 사이마다 중복·결합·회귀·계약·관측성·기술 부채를 점검한다.
- 리팩터링은 미관 개선이 아니라 다음 변경의 선택지를 회복하는 작업으로 취급한다.
- 작은 기능이라도 여러 모듈을 동시에 바꿔야 하면 경계를 재검토한다.
- 명세는 한 번 확정한 문서가 아니라 검증 결과로 갱신하는 가설이다.

### 원칙 3. 자율성은 되돌림·검증 능력에 비례한다

**자율성 수준은 행동량이 아니라 되돌림·검증 능력에 맞춘다.**

| 작업 | 기본 정책 |
|---|---|
| 격리된 코드·테스트·문서 변경 | 자동 검증과 예산 상한 아래 반복 허용 |
| 승인 범위의 수정안·배포안 작성 | 자동 준비, 사람 검토 후 반영 |
| 운영 DB 이행·권한 변경·외부 발송 | 사전 승인·최소 권한·결과 확인 필수 |
| 되돌릴 수 없는 업무 행동 | 자동 복구 가능하다고 가정하지 않고 보상·책임 경로 별도 설계 |

지침 파일·스킬·Effort 설정은 권한 통제의 대체물이 아니다. CI, 서버 측 권한, 배포 보호와 승인 장치로 강제한다.

### 기능 완료 게이트

수용 기준 충족, 독립 테스트, 브라우저·실제 상태 검증, 보안·회귀 점검, 문서·관측 갱신, 복구 계획, 다음 변경 가능성 점검이 완료되어야 다음 기능으로 진행한다. 업무 위험에 비례해 검사 범위를 조절한다.

## 11. 레거시 전환 절차

Fowler는 기존 동작을 새 기술로 그대로 옮기는 접근의 어려움과 불필요한 동작까지 재현할 위험을 지적하고, 작은 부분의 점진적 교체를 설명한다.[4]

| 단계 | 수행 내용 | 통과 기준 |
|---|---|---|
| 현황 진단 | 화면·소스·DB·배치·연계·권한·수작업 조사 | 미확인 범위와 책임자 식별 |
| 업무 복원 | Aside·REA 근거와 현업 확인 연결 | 유지·개선·폐기·추가 조사 분류 |
| 파일럿 | 제한된 업무를 공통 서비스·도구로 구현 | 동일 기준의 기능·비용·안전 검증 |
| 점진 교체 | 기존·신규 공존, 기능별 전환 | 연계 호환성·데이터 대사·복구 훈련 |
| 확대·운영 | 검증된 범위의 자율성 확대 | 품질·비용·사람 검토 부담의 지속 평가 |

브라우저 관찰만으로 서버 계산·배치·정산·DB 제약·역할별 예외를 모두 복원할 수 없다. 허가된 내부 자료와 현업 인터뷰로 보강한다. 소스가 있는 자사 시스템은 이를 우선 활용하고 REA를 보완 수단으로 사용한다.

데이터 이행에서는 매핑·정합성·중복·이력 보존·쓰기 주체·동기화·전환 시점을 명시한다. **코드 롤백은 이미 반영된 데이터와 외부 업무 행동을 자동으로 되돌리지 않는다.**

## 12. 성과와 경제성 평가

기존 개발·유지보수 방식의 대표 과제와 동일 수용 기준을 기준선으로 삼는다. 과제 난이도와 기존 코드 친숙도를 기록하고, 비교 가능한 파일럿에서 경과시간과 사람의 실제 투입시간을 따로 측정한다.

| 영역 | 평가 지표 |
|---|---|
| 속도 | 승인부터 검토 가능한 변경안까지의 시간, 야간 결과의 수용 비율 |
| 사람 투입 | 요구 정의·감독·리뷰·재작업·통합 시간 |
| 품질 | 회귀·운영 유출 결함, 승인 후 재작업, 실제 결과 일치 |
| 변경 가능성 | 영향 모듈, 수정 검증 시간, 계약 파손·복구 비용 |
| 인수인계 | 새 담당자의 환경 실행·오류 재현·첫 안전한 변경까지의 시간 |
| 안전 | 승인 준수, 금지 행동 차단, 복구 성공, 감사 기록 완결성 |
| 비용 | 모델·구독·실행 인프라·보안·인력·실패 복구를 포함한 완료 건당 비용 |

초기 명세·테스트·환경 구축 비용도 포함한다. 생성 코드량·PR 수·에이전트 실행시간만을 KPI로 삼지 않는다. 파일럿 전 현업·개발·보안 책임자가 합격 기준을 정하고 결과에 따라 확대·보완·중단을 결정한다.

## 13. 위험과 통제

| 위험 | 통제 |
|---|---|
| 기존 버그를 정상 요구사항으로 고정 | 현업 확인, 유지·개선·폐기 분류 |
| 브라우저 성공 화면을 실제 완료로 오인 | 독립 판정기로 API·데이터 결과 확인 |
| 문서 노후화와 담당자 의존 | 코드와 같은 변경으로 갱신, 새 담당자 재현 검증 |
| 무인 실행의 비용·변경 폭주 | 시간·예산·범위·재시도 상한, 실패 시 중단 |
| 개인정보·토큰 유출, 페이지 지시 오인 | 테스트 데이터, 비밀값 분리, 외부 콘텐츠를 데이터로 취급 |
| 모델·도구 의존 | 계약·지식·검증기를 제품 중립적으로 유지, 교체 평가 |
| 운영 전환 실패 | 단계적 전환, 데이터 대사, 롤백·보상 훈련 |

## 14. 제안서 작성에 필요한 추가 조사

확정 일정·예산 산정 전 다음을 확인한다: 대상 업무와 사용자, 기존 기술·소스 접근성, 데이터 규모·품질, 배치·외부 연계, 보안·개인정보 제약, 가용성 요구, 기존 장애·변경 기준선, 현업 검수 담당자, 전환 허용 시간, 모델 사용·비용 정책.
