# Plan: REA 역설계 기반 VAATZ 두 화면 파일럿

상태: 신규 파일럿 실행 계획. 아래 작업·명령은 착수 후 순서대로 수행하고 검증한다.
관련: [README](README.md) · [03.spec.md](03.spec.md)

## 1. 범위와 실행 원칙

REA 역설계 → 근거 기반 명세 검토 → 로컬 LLM 독립 구현 → 테스트·Aside·필요한 REA 비교 순으로 진행한다. Aside는 탐색·재현·검증 보조다. 두 화면, React + TypeScript + Vite만 구현하며 OTP·DB·업무 백엔드·API stub은 만들지 않는다.

현재 계획은 선행 역설계 결과에 따라 갱신하는 기준안이다. 실제 Evidence와 갱신 명세를 승인받기 전 화면 구현을 시작하지 않는다. 구현 단위는 하나씩 실행하고 단위 종료마다 검증·다음 변경 가능성 점검을 수행한다.

## 2. 산출물과 예상 파일 구조

다음은 **실행 시 생성할 예정 경로**이며 현재 존재하거나 결과가 확보됐다는 뜻이 아니다. 현재 문서 체계는 README·01.intent.md·02.plan.md·03.spec.md·99.기술_스택-추천.md다.

```text
02-파일럿/
├── README.md / 01.intent.md / 02.plan.md / 03.spec.md
├── 99.기술_스택-추천.md
├── 역설계-기록.md          # 질문·관찰·근거 대응·한계·설계 결정
├── 검증-기록.md            # 실행 조건·명령·결과·차이·사람 보완·변경 가능성
├── 근거/                  # 필요한 마스킹된 REA Evidence·캡처
└── frontend/              # 신규 Vite 앱
    ├── package.json / package-lock.json
    ├── src/
    │   ├── App.tsx
    │   ├── pages/         # 메인·로그인 초기 화면
    │   ├── components/    # 실제 재사용이 필요한 의미 있는 UI만
    │   ├── domain/        # 순수 TypeScript 데모 입력 검증
    │   └── data/          # 정적 가상 데이터
    └── e2e/               # 이동·새로고침·키보드·데모 시나리오
```

단위·컴포넌트 테스트는 해당 소스 옆에 둔다. 업무 상태는 React 지역 상태로 관리하고 전역 상태 라이브러리는 도입하지 않는다. 명명·컴포넌트·오류 결과 타입 규칙은 초기 작업에서 확정하고 실제 코드 예시와 함께 기록한다. 두 화면 경로는 `/`와 `/login`을 제안하며 라우팅 의존성 선택은 구현 전 검토한다.

## 3. 단계별 작업과 승인

### P0. 기존 환경과 허용 범위 확인

- [ ] 설치 이력을 읽고 현재 필요한 연결만 재확인한다. 기존 등록을 재설치·덮어쓰지 않는다.
- [ ] Codex–REA의 실제 도구와 대상 웹 관찰 가용성을 확인한다. 도구명·인수는 현재 노출 스키마에서 확인하며 추측하지 않는다.
- [ ] Aside 로컬 모델과 개발용 로컬 에이전트를 구분하고 각 도구 권한을 확인한다.
- [ ] 분석 권한·대상·프로필·수집 범위·금지 행동·증빙 보관을 확인한다.

통과: 사용 경로와 제한 기록. REA 대상 연결이 없으면 다음 단계 완료로 표시하지 않는다. 새 연결·설정 변경은 계획과 범위를 제시해 승인받는다.

### P1. REA 관찰 준비와 최소 실제 Evidence

- [ ] 격리된 테스트 프로필과 CDP 연결을 준비한다. Aside 직접 연결은 검증된 경우에만 사용한다.
- [ ] 별도 브라우저라면 조작 도구·주체·재현 방법을 확인한다. 사람 조작이 필요하면 기록한다.
- [ ] 메인 화면의 최소 관찰 결과를 실제로 확보하고 Evidence 위치·범위·누락을 확인한다.
- [ ] 전환을 분석할 경우 관찰 시작을 이동 전에 준비한다. 관찰 창 밖 이벤트는 확보했다고 하지 않는다.

통과: 실제 대상 근거를 읽고 질문에 활용할 수 있음. 실패하면 도구 연결과 사이트 관찰 실패를 분리하고 대안·재시도 범위를 승인받는다.

### P2. REA 중심 역설계 반복

- [ ] 메인 주요 영역·요소·접근성 구조를 분석한다.
- [ ] 로그인 진입 요소·이벤트·경로를 분석하고 가능한 실행 관찰과 대조한다.
- [ ] 로그인 초기 화면의 입력·안내·버튼·속성·초기 상태를 분석한다. 실제 입력·인증 제출은 하지 않는다.
- [ ] Aside는 필요한 화면 탐색·전환 재현·실패 조건 수집을 지원한다.
- [ ] 이번 관찰의 정적 분석과 실행 결과가 다르면 시점·프로필·재현 조건을 대조하고 미확인 사항을 구분한다.
- [ ] 원본의 접근성·관찰성 문제와 개선 후보를 분리한다.

기록: `역설계-기록.md`에 질문·Evidence·사실·해석·한계·결정·요구 ID를 연결한다. 원본 코드 전체를 개발 입력으로 복사하지 않고 구조·행동 명세로 인계한다.

통과: spec AC-R1·AC-R2의 역설계 부분을 검토할 수 있음. 핵심 화면·이동 근거가 없으면 화면 구현은 보류한다.

### P3. 역설계 결과와 명세·작업 검토

- [ ] 메인·로그인 초기 화면의 실제 구현 요소 목록을 확정한다.
- [ ] 유지·개선·제외·추가 확인을 분류하고 원본 재현 요구와 개선 요구의 근거를 분리한다.
- [ ] 입력 규칙·미구현 메뉴·로컬 데모 안내 등 세부 수용 기준을 확정한다.
- [ ] spec을 갱신해 사용자 검토를 받고, 이어서 plan·작업·의존성·검증 명령을 승인받는다.
- [ ] 반복 검증 시나리오·횟수·조건과 사람 투입시간 측정 구간을 실행 전에 정한다.

통과: 역설계·spec·plan의 충돌 없음. 명세 승인 전에 구현을 시작하지 않는다. 01.intent.md의 최초 의도와 99.기술_스택-추천.md의 현재 선택을 대조한다. 파일 번호와 무관하게 명세 승인 후 계획·작업을 확정한다.

### P4. 로컬 LLM의 작은 독립 구현

구현 에이전트는 필요한 근거와 현재 작업의 수용 기준을 읽고 아래 순서대로 진행한다. 각 작업 시작 전 변경 예정 파일·검증 항목을 기록한다.

| 작업 | 범위 | 검증·수용 기준 |
|---|---|---|
| T0 기반 준비 | Vite React TS, 테스트 도구·스크립트, 경로 정책 | 타입·테스트·빌드 실제 실행, 의존성·버전·명령 기록 |
| T1 최소 이동 | 메인 기본 구조, 로그인 링크, 로그인 기본 구조 | AC-F1: 이동·직접 진입·새로고침·뒤로 가기 |
| T2 메인 상세 | 승인 영역·가상 공지·범위 밖 안내 | AC-F2, T1 회귀, 요소 역할·이름 |
| T3 로그인 초기·데모 | 라벨·가상 입력·순수 검증·오류·데모 안내 | AC-F3·AC-S1: 누락/정상/반복, 외부 요청·저장 없음 |
| T4 에이전트 사용성 | 키보드·포커스·상태 안내와 식별성 보완 | AC-A1·AC-A2, T1~T3 회귀 |

모든 작업의 반복 절차:

1. 결과 중심 테스트를 작성하고 의도한 이유로 실패하는지 확인한다.
2. 최소 구현 후 해당 테스트를 통과시킨다. 컴포넌트 내부 구현에 불필요하게 결합하지 않는다.
3. 타입·회귀 테스트·빌드와 해당 브라우저 검증을 실행한다.
4. 중복·숨은 상태·임시 우회·결합·다음 수정 위치를 점검한다.
5. 필요하면 동작을 보존하는 정리를 하고 재검증한다.
6. `검증-기록.md`에 결과·미실행·남은 위험·다음 작업 가능 근거를 남긴다.

막힌 요구·반복 실패·범위 변경은 구현을 계속 누적하지 말고 보고한다. 구현과 테스트는 이번 역설계 근거와 승인된 명세를 기준으로 작성한다.

### P5. 비교·독립 검증

- [ ] 단위 테스트: 로컬 검증의 누락·정상·확정된 경계값.
- [ ] 컴포넌트 테스트: 역할·이름·라벨·오류 연결·데모 결과.
- [ ] E2E: 메인→로그인, 직접 진입·새로고침·뒤로 가기, 키보드·반복 실행.
- [ ] Aside 채팅: 좌표나 코드 내부 설명 없이 기능 발견·로그인 이동·입력 식별·데모 제약 설명.
- [ ] REA 재관찰: 필요한 로컬 화면 구조·접근성·전환의 차이를 기록하고 유지·개선·의도된 제외와 대조.
- [ ] 안전: 원본 요청·실제 인증·영구 저장·민감 로그·OTP·업무 백엔드 부재를 코드와 실제 실행으로 확인.
- [ ] 가능하면 별도 검토 세션에서 명세–근거–테스트를 대조하되 모델 자기 보고만으로 판정하지 않는다.

통과: spec의 모든 수용 기준에 실행 근거 연결. 미실행·차단은 완료가 아니라 제한으로 남긴다. 화면 유사성만으로 동등성 판정을 내리지 않는다.

### P6. 평가·인계

- [ ] 원본 재현 요구 목록 기준 REA 근거 연결률과 신규 개선 요구를 별도 집계한다.
- [ ] 사람 보완·모델 대체·재작업·검증 실패·작업시간을 기록한다.
- [ ] 작은 변경의 영향 범위·회귀·검증 부담을 점검한다.
- [ ] 재현 명령·실행 환경·미해결 사항·다음 작업을 남긴다.

최종 완료: 승인된 수용 기준 충족과 제한 검토. 운영 배포·실제 인증 체계 검증은 포함하지 않는다.

## 4. 테스트 도구와 명령 계약

권장 도구는 Vitest·React Testing Library(단위/컴포넌트), Playwright(E2E), 접근성 자동 검사와 키보드 검토다. 추가 의존성은 T0에서 승인받고 설치 버전을 lockfile에 고정한다.

아래는 **T0에서 package.json에 마련하고 실제 실행해야 할 명령 계약**이다. 아직 앱이나 해당 scripts가 존재한다고 가정하지 않는다. 작업 디렉터리는 `02-파일럿/frontend`다.

| 목적 | 예정 명령 | script 계약 |
|---|---|---|
| 개발 | `npm run dev -- --host 127.0.0.1` | Vite 로컬 기동. 실제 URL·포트 기록 |
| 타입 | `npm run typecheck` | `tsc -b --pretty false` |
| 단위·컴포넌트 | `npm run test:unit -- --run` | Vitest |
| E2E | `npm run test:e2e` | Playwright test, webServer 설정과 실행 대상 확인 |
| 빌드 | `npm run build` | 타입 검사와 Vite build |

라우트 직접 진입은 사용하는 Vite 환경에서 시험한다. 배포하지 않은 호스팅 환경의 fallback까지 검증했다고 주장하지 않는다. REA·Aside 호출 명령은 현재 도구 스키마를 확인한 뒤 기록하며 존재하지 않는 API 이름을 만들어 쓰지 않는다.

## 5. 실패·안전·복구

- REA 대상 연결 실패: setup 재실행으로 덮어쓰기 전에 연결·프로필·권한·관찰 범위를 분리 진단한다. 대안 승인 전 임의 브라우저 설정을 바꾸지 않는다.
- Aside 재현 실패: URL·요소·시점·실제 결과를 보존한다. 도구 응답 성공과 기능 성공을 구분한다.
- 로컬 모델 도구 실패: 텍스트 응답 성공을 근거로 계속 진행하지 않는다. 보완 모델·사람 개입은 승인·기록한다.
- 증빙에 민감정보 포함: 저장·공유를 중단하고 허용된 마스킹·최소 수집 범위를 재검토한다.
- 구현 회귀: 마지막 변경 단위를 기준으로 원인을 확인하고 관련 테스트를 보강한다. 무관한 기존 변경을 되돌리지 않는다.
- 복구: 시작 시 Git 상태와 변경 범위를 기록한다. 승인된 변경 단위만 복원하고 본인이 생성한 프로세스만 종료한다. 폴더 전체 삭제·`reset --hard`·자동 commit·push는 하지 않는다.
