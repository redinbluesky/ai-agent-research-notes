# 파일럿 기술 스택 — 확정 사항과 보조 도구 추천

관련: [01.intent.md](01.intent.md) · [02.plan.md](02.plan.md) · [03.spec.md](03.spec.md) · [README](README.md)

## 1. 결론과 문서의 지위

**구현 스택은 React + TypeScript + Vite로 확정한다. REA를 역설계의 핵심 도구로, AI Agent가 연결된 Aside를 탐색·재현·브라우저 테스트의 필수 보조 도구로 사용한다.**

이번 파일럿은 단계 전체에 걸쳐 프론트엔드 전용이다. 이 문서는 확정된 선택과 아직 승인·설치·시험이 필요한 보조 도구 추천을 구분하며 설치 완료나 성능 우위를 주장하지 않는다.

## 2. 분석·구현·검증 구성

| 영역 | 선택 | 상태·역할 |
|---|---|---|
| 역설계 | REA + 분석 에이전트 | 핵심. 현재는 Hermes–REA 연결 우선(Codex 크레딧 소진, 2026-10-20 등록 완료·실연결 검증 중). VAATZ 대상 Evidence 확보는 별도 검증 |
| 탐색·재현·브라우저 시험 | Aside + 연결된 AI Agent | 필수 보조. 채팅으로 실제 작업 요청, 관찰·테스트 결과 확인 |
| 구현 주체 | 로컬 LLM 기반 개발 에이전트 | 사용자 선택. 파일 편집·터미널·테스트·필요한 MCP 가용성 확인 |
| UI | React | 확정. 두 화면을 명시적 컴포넌트와 상태로 표현 |
| 언어 | TypeScript | 확정. 입력·오류·데모 상태 계약 명시 |
| 개발·빌드 | Vite | 확정. 로컬 개발 서버와 정적 프론트엔드 빌드 |
| 상태 | React 지역 상태 | 권장. 두 화면에 전역 상태 관리 라이브러리 추가하지 않음 |
| 입력 검증 | 순수 TypeScript 함수 | 권장. UI와 분리해 같은 규칙을 테스트 |
| 스타일 | 기본 CSS와 의미 있는 HTML | 권장. 대형 UI 프레임워크 없이 필요한 구성부터 |
| 단위·컴포넌트 시험 | Vitest + React Testing Library | 권장·도입 전 승인. 실제 scripts·버전은 초기 구현에서 확정 |
| 반복 브라우저 시험 | Playwright | 권장·도입 전 승인. Aside의 에이전트 조작 검증과 상호 보완 |
| 접근성 | 자동 검사 + 키보드·포커스·라벨 검토 | 권장. 자동 검사만으로 완료 처리하지 않음 |
| 데이터 | 정적 가상 데이터·메모리 내 상태 | 확정. 계정 정보·인증 상태의 영구 저장 없음 |

## 3. React + TypeScript + Vite를 사용하는 이유

사용자가 지정한 스택을 유지하면서 이번 범위에 필요한 책임을 나눈다.

- React: 화면 구성·이벤트·로컬 상태를 코드에서 추적할 수 있도록 한다.
- TypeScript: 데모 입력과 검증 결과의 형태를 명시한다. 원본 OTP·서버 응답 필드를 그대로 이식하지 않는다.
- Vite: 로컬에서 화면을 제공하고 프론트엔드 산출물을 빌드한다. 업무 백엔드나 인증 서버 역할은 맡기지 않는다.
- 순수 검증 함수: 화면과 테스트가 같은 규칙을 사용하되 React 내부 구현에 테스트를 과도하게 결합하지 않는다.

이 스택을 택한다고 접근성·안전성·에이전트 친화성이 자동으로 확보되지는 않는다. 명시적 라벨·실제 링크·버튼·포커스·상태 안내를 설계하고 검증해야 한다. “특정 모델이 가장 잘 다룬다”거나 다른 프레임워크보다 우월하다는 확인되지 않은 주장은 선택 근거로 사용하지 않는다.

## 4. REA·Aside·로컬 모델의 연결 경계

- [REA 설치 이력](../../../05-에이전트-네이티브-도구/핵심-문서/REA-설치-이력.md)은 Codex–REA 설치·진단·실호출과 2026-10-20 Hermes–REA 등록을 기록한다. 등록·doctor 상태와 대상 웹의 CDP 연결·Evidence 수집 성공과는 구분한다.
- [Aside 설치 이력](../../../05-에이전트-네이티브-도구/핵심-문서/Aside-설치-이력.md)은 Codex·Hermes MCP와 로컬 Custom Provider 채팅 검증을 기록한다. 현재 세션의 가용성과 다단계 브라우저 성공은 다시 확인해야 한다.
- Aside 내부 모델, 외부 개발 에이전트, REA를 호출하는 에이전트는 반드시 동일할 필요가 없다. 결과 파일과 근거 대응표로 인계할 수 있다.
- REA가 Aside 세션에 직접 붙는다고 가정하지 않는다. 별도 Chrome/Chromium 테스트 프로필이 필요하면 조작 주체·도구·관찰 시점을 명시한다.
- 로컬 모델의 text 입력 구성에서는 DOM·접근성·텍스트를 우선 활용한다. 시각 판정에 별도 모델·사람이 필요하면 승인·기록한다.
- REA는 역설계 근거, Aside는 실제 흐름, 자동 테스트는 반복 판정을 담당한다. 하나가 나머지 검증을 대체하지 않는다.

## 5. 에이전트 친화적 프론트엔드의 최소 설계

- 의미 있는 영역과 제목, 명시적 `/`·`/login` 경로를 사용한다. 경로는 계획상의 제안이며 직접 진입·새로고침까지 시험한다.
- 좌표·이미지에만 의존하지 않는 링크·버튼·입력 이름을 제공한다.
- 입력과 라벨, 오류와 입력을 연결하고 상태 변경을 읽을 수 있게 한다.
- 사람과 Aside가 같은 UI·검증 규칙을 사용한다. 에이전트만을 위한 인증 우회·특수 성공 경로를 만들지 않는다.
- 로컬 데모는 실제 인증 미구현을 알리고 끝난다. 원본 서버 요청·인증 성공 모사·OTP 화면은 없다.
- 별도 MCP 서버·WebMCP는 이번에 필수로 도입하지 않는다. 브라우저 UI 수준의 조작 가능성을 먼저 실증한다.

라우팅 라이브러리·접근성 검사 패키지 등 구체 의존성과 버전은 초기 구현에서 필요한 범위를 검토해 승인받고 lockfile에 기록한다. 선택되지 않은 패키지를 이미 설치된 것처럼 문서화하지 않는다.

## 6. 도입하지 않는 구성

| 제외 | 이유 |
|---|---|
| Spring Boot·기타 업무 백엔드·API stub | 사용자 지정 프론트엔드 범위 밖. 인증 서버 없이 데모 안내로 검증 가능 |
| DB·ORM·Spring Security·세션 발급 | 실제 인증·데이터 영속성이 목적이 아님 |
| OTP·인증 결과 상태 머신 | 로그인 초기 화면 이후 동작은 범위 밖 |
| 전역 상태 라이브러리·대형 프레임워크 | 검증된 필요가 없는 복잡성을 선제 도입하지 않음 |
| 원본 인증 API와 리소스 의존 | 독립 구현·안전 경계 유지 |

구현과 테스트는 이번 REA 역설계와 승인된 명세를 기준으로 새로 작성한다. 입력 규칙·길이 제한 등 세부값은 근거를 확인하고 테스트와 함께 반영한다.

## 7. 실행·검증·도입 판단

앱 위치·작업 순서·예정 npm 명령 계약은 [02.plan.md](02.plan.md)에 둔다. frontend 생성, 의존성 설치, 테스트 scripts 작성은 아직 수행 결과가 아니라 후속 작업이다.

구현 착수 전 REA 핵심 근거와 명세를 검토한다. 구현 시 의도 정렬 → 작은 동작 테스트 → 최소 구현 → 타입·빌드·브라우저 검증 → 다음 변경 가능성 점검을 반복한다. Aside를 통한 범위 내 기능 시험은 생략하지 않으며, 차단·미실행은 결과에 남긴다.

선택 근거는 [MINDUNG 스킬 비교](../../../03-에이전트-설정/사례/2026-10-18-MINDUNG-AI-코딩-스킬-비교.md)의 단계별 검증과 [Kent Beck 분석](../../../01-AI-네이티브-SDLC/사례/2026-10-08-AgentOS-Kent-Beck-AI-시대-소프트웨어-공학.md)의 변경 가능성 원칙을 이 파일럿에 적용한 것이다. 향후 인증·업무 서버가 필요해지면 별도 범위·설계 승인으로 다루며 이번 파일럿의 자동 후속 단계로 넣지 않는다.
