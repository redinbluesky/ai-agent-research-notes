# 파일럿 — REA 역설계 기반 VAATZ 두 화면 독립 구현

## 1. 목적과 핵심 원칙

**REA로 기존 웹의 구조·동작을 역설계하고, 근거에서 도출한 명세를 바탕으로 로컬 LLM이 에이전트 친화적인 웹을 독립 구현한다. Aside는 AI Agent가 연결되어 탐색·흐름 재현·브라우저 검증을 수행하는 필수 보조 도구다.**

사용자가 요구한 완전한 분석·테스트는 승인된 두 화면의 기능·시나리오를 빠짐없이 다루고 실제 결과를 확인하는 목표다. 모든 결함의 부재를 보장한다는 뜻이 아니며, 미실행·차단은 해결 또는 명시적 범위 조정·승인 전까지 완료로 처리하지 않는다. 최초 의도는 [01.intent.md](01.intent.md)에 정리한다.

사용자가 화면을 일일이 설명하는 대신 분석 에이전트가 REA를 호출해 구현 가능한 요구사항 초안을 만든다. 사람은 범위·권한·미확인 사항·개선 결정과 결과를 검토한다. 원본 코드·인증 체계의 복제가 아니라 관찰 가능한 사용자 결과의 독립 구현이 목적이다.

검증할 목표는 다음과 같다.

- **역설계:** 두 화면의 구조와 로그인 진입 동작을 Evidence로 설명할 수 있는가?
- **분석 자동화:** 사람의 수동 조사·설명을 줄이고 근거 있는 명세 초안을 만들 수 있는가?
- **개발·사용:** 로컬 LLM이 명세를 구현하고 사람과 Aside 에이전트가 같은 웹을 안정적으로 사용할 수 있는가?
- **변경 가능성:** 작은 변경을 이해·검증·되돌릴 수 있으며 다음 작업의 부담이 통제되는가?

## 2. 확정 범위

| 구분 | 포함 | 제외 |
|---|---|---|
| 원본 분석 | `https://www.vaatz.com/vmp/main.do` → 우측 상단 로그인 선택 → 로그인 초기 화면 | 실제 로그인, 자격 증명 입력, OTP 등록·검증, 로그인 이후 업무 |
| 메인 구현 | 주요 화면 영역·공지·내비게이션의 정적 표현, 로그인 진입 | 회원가입·장바구니·공지 상세 등 실제 기능 |
| 로그인 구현 | 초기 입력·안내·버튼, 명시적 라벨, 로컬 오류·데모 안내 | 인증 성공 모사, OTP 단계 전환, 서버 응답 처리 |
| 기술 | **React + TypeScript + Vite**, 정적 테스트 데이터와 메모리 내 상태 | DB, 업무 백엔드, Spring Boot, API stub, 원본 서버 호출 |
| 표현 | 원본 영역 구성과 사용자 흐름을 참고한 독립 스타일 | 원본 코드·GIF·브랜드 자산의 무단 복제, 픽셀 단위 복제 |

Vite 개발 서버는 로컬 화면 제공용이며 업무 백엔드가 아니다. 실제 계정 정보는 사용하지 않는다. 로컬 검증에는 가상 테스트 값만 사용하고 저장·로그·외부 전송하지 않는다. 원본에 대한 분석·재구현 권한 범위를 확인하며, 브라우저 권한 변경·다운로드·추가 대상 탐색은 별도 승인 대상이다.

## 3. 신규 파일럿의 시작점

이번 파일럿은 환경 확인 → REA 역설계 → 명세·계획 검토 → 구현 → 검증 순으로 시작한다. 대상 화면의 이동 방식·입력 속성·구조는 새로 수집한 근거로 확정하며, 모든 수용 기준은 이번 실행 결과로 판정한다.

| 단계 | 시작 시 확인할 내용 | 완료 근거 |
|---|---|---|
| 환경 준비 | REA·Aside·로컬 개발 에이전트의 도구·권한·연결 | 현재 사용할 경로와 제한 |
| 대상 관찰 | 격리 프로필·CDP·분석 대상·시나리오 | 실제 REA Evidence와 Aside 보조 관찰 |
| 역설계 | 두 화면의 구조·로그인 진입·초기 상태 | 요구사항에 연결된 근거와 분석 한계 |
| 구현 | 승인된 명세에 따른 React 두 화면 | 소스·테스트·타입 검사·빌드 결과 |
| 수용 검증 | 기능·접근성·Aside 에이전트 조작 | 시나리오별 실제 결과와 판정 |

설치 정보는 환경 준비를 위한 참고로만 사용한다: [REA 설치 이력](../../../05-에이전트-네이티브-도구/핵심-문서/REA-설치-이력.md), [Aside 설치 이력](../../../05-에이전트-네이티브-도구/핵심-문서/Aside-설치-이력.md). 설치·연결 상태를 이번 대상의 분석·테스트 완료로 간주하지 않는다.

## 4. 역할과 연결 경계

| 주체 | 역할 | 산출물 |
|---|---|---|
| **REA** | DOM·접근성·스크립트·전환·허용된 네트워크 메타데이터 등 역설계 근거 수집·분석 | Evidence와 수집 한계 |
| 분석 에이전트 | REA 질문·호출·결과 종합, 관찰과 추론 구분, 요구사항 도출 | 역설계 기록·근거 대응표·명세 |
| Aside와 연결된 AI Agent | 화면 탐색, 흐름 재현, 관찰 지점 발견, 구현 후 UI 검증 | 보조 관찰·재현·검증 기록 |
| 로컬 개발 에이전트 | 승인된 명세에 따른 작은 구현·테스트·수정 | 코드·검증 결과·변경 기록 |
| 사용자 | 범위·위험·개선·미확인 사항과 완료 판단 | 승인·결정 |

- 기존 Codex–REA 연결을 우선 활용한다. 로컬 개발 에이전트에 REA가 연결되어 있지 않다면 결과 파일로 인계한다. Aside 채팅 성공이 파일 편집·터미널·REA 권한까지 증명하지 않는다.
- REA의 웹 관찰은 일반 클릭 자동화와 구분한다. Aside와 REA가 같은 세션을 공유한다고 가정하지 않는다.
- 직접 CDP 연결이 확인되지 않으면 별도 Chrome/Chromium 테스트 프로필에서 같은 시나리오를 관찰한다. 해당 프로필의 조작 주체·도구·관찰 시작 시점까지 확인한다. 수동 재현이 필요하면 자동화 한계로 기록한다.
- Aside 로컬 모델은 설치 기록상 text 입력 구성이다. DOM·접근성·텍스트 중심으로 분석하고 캡처의 시각 판정은 가능한 모델 또는 사람이 보완한다. 모델 전환과 사람 보완을 별도 기록한다.
- Aside 외부 MCP 보조 경로로 다단계 작업을 요청할 때는 단일 `exec`로 묶되 내부 REPL 구현까지 금지하지 않는다. 임시 REPL 탭과 Desktop 탭을 동일시하지 않는다.

## 5. 전체 실행 절차

| 단계 | 수행 | 통과 기준 |
|---|---|---|
| 1. 범위·환경 확인 | 기존 연결 재사용, 권한·금지 행동·도구 가용성 확인 | 사용 가능한 경로와 막힌 경로 구분 |
| 2. REA 관찰 준비 | 대상·프로필·CDP 연결, Evidence 저장·마스킹 방식 확인 | 실제 대상 관찰 결과 확보 |
| 3. REA 중심 역설계 | 관찰 → 분석 질문 → 추가 관찰 반복, Aside로 탐색·재현 보조 | 두 화면 구조·로그인 이동·초기 상태의 근거와 한계 |
| 4. 결과·명세 검토 | 유지·개선·제외·추가 확인 분류, 요구사항·테스트 연결 | 역설계 결과와 갱신 spec 승인 |
| 5. 독립 구현 | 승인 plan에 따라 작은 단위의 테스트·구현·정리 | 각 단위의 실행 근거와 회귀 점검 |
| 6. 비교·사용 검증 | 자동 테스트, Aside UI 조작, 필요한 REA 재관찰 | 기능·접근성·에이전트 조작성 및 의도된 차이 확인 |
| 7. 평가·인계 | 자동화·수동 보완·재작업·다음 변경 기록 | 다음 세션에서 작업 재개 가능 |

**실제 역설계 근거 확보 전에는 본격적인 화면 구현으로 넘어가지 않는다.** 이번 문서 작성 승인은 REA 관찰 완료나 구현 완료 승인이 아니다. REA 연결이 막히면 원인을 기록하고 대안 승인을 받는다. Aside 결과만으로 REA 단계를 완료 처리하지 않는다.

## 6. 역설계 산출물과 추적 방식

실행 시 `역설계-기록.md`에 질문·관찰·해석·한계·결정을 모으고, `근거/`에 민감정보를 제거한 필요한 Evidence만 둔다. 두 경로는 **향후 생성 대상**이며 현재 확보된 결과가 아니다. 가짜 예시 Evidence를 실제 결과처럼 채우지 않는다.

| 기록 항목 | 필수 내용 |
|---|---|
| 관찰 단위 | 질문 ID, 대상 URL, 시각, 도구·모델, 프로필 역할, 재현 절차 |
| 근거 | REA Evidence ID 또는 정확한 파일 위치, 정적 분석/실행 관찰 구분 |
| 분석 | 확인 사실 / 해석 / 미확인 / 누락·절단·실패 |
| 결정 | 유지 / 개선 / 제외 / 추가 확인, 승인 상태 |
| 추적 | 요구사항 ID → 근거 또는 개선 결정 → 수용 기준 → 테스트·검증 결과 |

역설계 질문은 메인 영역·로그인 이벤트와 이동·로그인 초기 요소와 속성·에이전트 관찰성에 집중한다. OTP·인증 분기가 스크립트에 보여도 이번 구현 대상으로 확장하지 않는다. 원본의 이동 방식은 분석 결과로 확인하며, 새 구현에서는 승인된 사용자 결과를 기준으로 적절한 방식을 선택한다.

| pstack — 실행 근거·독립 검증 | 재현 조건·실제 실행 결과로 판단. Cursor 플러그인 명령을 다른 도구에 그대로 가정하지 않음 |

기본 흐름은 Osmani 방식으로 통일하고 나머지는 필요한 지점에 보완한다. 로컬 개발 환경의 스킬 지원을 확인하며 슬래시 명령에 의존하지 않고 아래 절차를 전달한다.

`요구·근거 확인 → 실패하는 동작 테스트 확인 → 최소 구현 → 테스트·타입·빌드 → 브라우저 검증 → 다음 변경 가능성 점검 → 필요시 명세·코드 수정`

작업은 최소 이동 흐름 → 메인 상세 → 로그인 초기 화면·로컬 데모 검증 → 에이전트 사용성 보완 순으로 나눈다. 테스트는 구현 내부 형태보다 사용자 결과를 판정한다. 미관만을 위한 재구조화나 미래 백엔드 대비 과잉 설계를 하지 않는다.

각 단위 종료 시 확인한다:

- 수용 기준과 실제 실행 근거, 미실행 검증이 구분되는가?
- 기존 이동·입력·오류 안내에 회귀가 없는가?
- 중복 규칙·임시 우회·숨은 전역 상태·불필요한 결합이 생겼는가?
- 다음 변경 위치를 예측할 수 있는가? 먼저 정리할 항목은 무엇인가?
- 발견한 사실을 spec·plan에 반영해야 하는가?

## 8. 에이전트 친화적 웹과 검증

- 의미 있는 HTML 영역·제목, 실제 링크·버튼, 입력과 연결된 텍스트 라벨을 사용한다.
- 사람과 에이전트가 같은 UI·검증 규칙을 사용하며 우회용 별도 로직을 만들지 않는다.
- URL·화면 제목·오류·데모 결과를 명시적으로 관찰할 수 있게 한다.
- 키보드 조작, 포커스, 입력별 오류 연결·상태 안내를 검증한다.
- 별도 MCP 서버·WebMCP는 이번 필수가 아니다. 표준 웹 요소로 Aside 조작을 먼저 검증한다.
- UI 친화성의 실증을 서버 권한·감사·업무 API 검증으로 확대 해석하지 않는다.

Aside 검증 요청 예: “주요 기능을 설명하고 로그인 화면으로 이동한 뒤 입력 항목과 데모 제약을 알려줘. URL·화면 요소로 결과를 확인하고, 실제 계정 정보는 사용하지 마.”

구현 에이전트의 자기 보고 대신 자동 테스트와 실제 URL·DOM·화면 상태로 판정한다. REA 재관찰은 구조와 의도된 차이를 보강하며 테스트를 대체하지 않는다. 별도 검토 세션을 사용해도 모델만 바꾸거나 세션을 나누는 것으로 완전한 독립 검증을 보장하지 않는다.

## 9. 성과 측정

| 지표 | 측정 기준 |
|---|---|
| REA 근거 연결률 | REA 근거가 연결된 원본 재현 요구 수 / 원본 재현 요구 총수. 분자·분모와 대상 목록 함께 기록. 신규 개선 요구는 별도 |
| 사람 보완 | 직접 조사·조작·설명·수정한 항목 수, 이유, 투입시간 |
| 재작업 | 근거 누락·추정·요구 오해로 되돌아간 작업과 시간 |
| 에이전트 조작 | 사전 확정한 동일 시나리오의 성공/실패/차단 횟수, 모델·보완 여부 |
| 변경 가능성 | 작은 변경의 영향 파일·검증 시간·회귀·문맥 복원 부담 |

최초 실행 전 시나리오·반복 횟수·측정 구간을 기록한다. 임의의 절감률을 약속하지 않으며, 코드량·테스트 수만을 성과로 삼지 않는다. 상세 수용 기준은 [03.spec.md](03.spec.md), 실행과 기록은 [02.plan.md](02.plan.md)를 따른다.

## 10. 로컬 LLM 인계 규칙

1. README → 01.intent.md → 03.spec.md → 02.plan.md → 해당 작업의 역설계 근거 순으로 읽는다.
2. 관찰 사실·개선 결정·미확인 항목을 구분하고 모순은 보고한다.
3. 한 번에 승인된 작업 하나만 구현한다. 실패 테스트를 삭제하거나 수용 기준을 낮춰 통과시키지 않는다.
4. REA가 확인하지 못한 원본 동작은 만들어 넣지 않는다. 개선 요구는 별도 승인으로 추가한다.
5. 파일 편집·터미널·브라우저·REA 도구 가용성을 확인한다. 없는 기능은 결과 파일 인계 등 명시적 대안으로 처리한다.
6. 범위 확대·의존성 추가·권한 변경·원격 작업은 승인받는다. 실제 인증·자격 증명 저장·외부 전송은 금지한다.
7. 단위마다 변경 파일·실행 명령·결과·실패·미실행 항목·다음 판단을 남긴다. 자동 commit·push·배포하지 않는다.
