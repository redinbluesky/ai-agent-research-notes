# Intent: REA 역설계와 AI Agent 기반 웹 재구축 파일럿

## 1. 최초 의도

**기존 웹 어플리케이션을 사람이 화면마다 수작업으로 분석해 개발자에게 설명하는 대신, REA 중심의 역설계와 AI Agent가 연결된 Aside 브라우저를 활용해 기능을 분석·검증하고, 그 결과로 로컬 LLM이 에이전트 친화적인 웹을 구축할 수 있는지 확인한다.**

이 문서는 이번 대화에서 사용자가 처음 제시하고 이후 명확히 한 요청을 목적 중심으로 정리한 것이다. 도구 설치 보고서나 구현 완료 보고서가 아니며, 상세 절차는 [02.plan.md](02.plan.md), 수용 기준은 [03.spec.md](03.spec.md), 전체 운영 흐름은 [README.md](README.md)에 둔다.

## 2. 해결하려는 문제

- 기존 웹의 구조·기능을 사람이 일일이 살펴보고 문서화하면 분석과 인계에 많은 수작업이 필요하다.
- 화면의 겉모습만 참고해 개발하면 실제 이동·상태·입력 규칙을 잘못 이해하거나 근거 없는 기능을 만들 수 있다.
- AI가 코드를 만들었다는 이유만으로 그 웹이 AI Agent가 이해·조작하기 쉬운 제품이 되는 것은 아니다.
- 도구가 설치되거나 채팅 응답이 나온 사실만으로 기능 분석·역설계·브라우저 테스트가 끝났다고 볼 수 없다.
- 로컬 LLM에 큰 요청을 한 번에 넘기면 원래 의도가 흐려지거나 검증 없이 기능과 복잡성이 늘어날 수 있다.

따라서 이번 파일럿은 화면 제작 자체뿐 아니라 **근거 있는 자동 분석에서 개발·실제 브라우저 검증까지 이어지는 방식**을 확인하려는 작업이다.

## 3. 이 세션에서 정리된 사용자 요청

| 요청 | 의도와 기대 결과 |

| Aside 브라우저에 AI Agent 연결 | 사용자가 Aside 채팅으로 분석·탐색·테스트를 요청하고 에이전트가 실제 브라우저에서 수행할 수 있어야 한다 |

| 에이전트 친화적인 웹 구축 | `01-문서/`의 원칙을 적용해 사람과 에이전트가 요소·기능·상태를 이해하고 같은 흐름을 사용할 수 있게 한다 |
| 두 화면의 프론트엔드 파일럿 | React + TypeScript + Vite만 사용하고 DB·업무 서버를 만들지 않는다 |

## 4. REA 중심과 Aside 보조의 의미

**REA는 역설계의 중심이고, Aside는 그 역설계를 위한 탐색·사용자 흐름 재현과 완성된 웹의 실제 브라우저 검증을 맡는 필수 보조 도구다.** 보조라는 말은 Aside 검증을 생략해도 된다는 뜻이 아니다.

- REA와 분석 에이전트: 관찰 근거를 수집하고 화면 구조·클라이언트 동작을 해석해 개발 가능한 명세로 정리한다.
- Aside와 연결된 AI Agent: 채팅 요청을 실제 탐색·이동·관찰·테스트로 이어 주고 REA에 필요한 재현 조건을 제공한다.
- 로컬 개발 에이전트: 승인된 근거와 명세를 읽고 독립 구현·테스트·수정을 수행한다.
- 사용자: 목적·범위·미확인 사항·위험·개선 방향·완료 결과를 판단한다.

Aside 내부 모델 연결, 외부 에이전트의 Aside MCP 연결, REA MCP 연결은 서로 구분한다. 같은 모델이나 같은 브라우저 세션을 자동 공유한다고 가정하지 않는다. 연결 방식보다 중요한 결과는 **분석·재현·구현·검증 사이에 근거와 작업 문맥이 끊기지 않는 것**이다.

## 5. “완전한 기능 분석·테스트”의 의미

사용자의 목표는 도구 응답이나 캡처 몇 장에 그치지 않고 **승인된 두 화면의 기능 목록과 시나리오를 끝까지 분석·시험하는 것**이다.

- 원본: 두 화면의 주요 구조·요소·로그인 진입·초기 상태를 분석하고 실제 이동을 확인한다. 실제 계정 입력·인증 제출은 하지 않는다.
- 신규 웹: 대응 화면·이동·입력 안내·로컬 데모·키보드·에이전트 조작을 실제 브라우저에서 검증한다.
- 범위에 포함된 항목은 근거와 판정 결과를 남기고, 미실행·차단·실패가 있으면 해결 또는 명시적 범위 조정·승인 전에는 완료로 취급하지 않는다.
- Aside의 “성공” 답변만으로 판정하지 않고 URL·DOM·화면 상태·자동 테스트 등 독립적인 결과를 확인한다.

이는 모든 웹 기능·서버 규칙을 복원하거나 모든 결함이 없음을 보장한다는 뜻은 아니다. 로그인 이후·실제 인증·DB는 애초에 제외된 범위다. 도구가 확인하지 못한 사항을 “완전 분석”이라는 표현으로 숨기지 않는다.

## 6. 파일럿 범위와 경계

- 대상 화면: VAATZ 메인과 로그인 선택 후 도달하는 로그인 초기 화면.
- 구현: React + TypeScript + Vite, 정적 테스트 데이터, 메모리 내 상태와 로컬 데모 안내.
- 제외: 실제 인증·OTP·로그인 이후 업무·DB·업무 백엔드·API stub·원본 서버 호출.
- 독립 구현: 원본 구조·행동을 이해하되 원본 코드·브랜드 자산·인증 방식을 그대로 복제하지 않는다.
- 안전: 분석 권한 범위 안에서 수행하고 실제 자격 증명·고객 데이터·운영 상태 변경을 다루지 않는다.

기능 범위를 작게 정한 이유는 단순한 화면 모형을 빨리 만들기 위해서가 아니라, **역설계에서 검증까지의 연결을 작은 대상에서 제대로 실증하기 위해서**다.

- 사람과 에이전트가 같은 목적·용어·범위를 이해하게 한다.
- 원본에서 확인한 사실과 새 웹의 개선 결정을 구분한다.
- 명세·계획을 검토한 뒤 작은 단위로 구현하고 테스트한다.
- 명세를 고정된 일회성 지시가 아니라 관찰과 검증으로 갱신하는 기준으로 사용한다.
- 기능 사이에 멈춰 회귀·중복·숨은 결합·다음 변경 가능성을 점검한다.
- 코드량·모델 응답량보다 실제 기능 수행·분석 부담·재작업·유지보수 가능성으로 평가한다.

## 8. 원하는 최종 결과

1. REA 근거에서 어떤 요구사항이 나왔는지 설명할 수 있다.
2. Aside 채팅과 연결된 AI Agent로 범위 내 분석·테스트를 수행하고 실제 결과를 확인할 수 있다.
3. 사람의 반복 화면 설명 대신 근거 있는 분석·명세가 개발 에이전트에 전달된다.
4. 로컬 LLM이 만든 두 화면을 사람과 에이전트가 사용할 수 있다.
5. 무엇을 검증했고 무엇이 제한되는지 명확하며, 다른 세션이 다음 작업을 이어갈 수 있다.
