## 영상 요약

영상은 대화에서 받은 답이 기록으로 남지 않는 문제를 출발점으로 삼는다. 자료를 넣을 때 AI가 요약·개념·비교 페이지를 만들고 기존 페이지를 갱신하는 LLM 위키를 제시하며, Obsidian과 Hermes가 같은 폴더를 다루는 방식으로 설명한다.[2]

### 구조

- **원본 자료층:** 기사 등 수집 자료를 보존하고 AI는 읽기만 한다.
- **위키층:** AI가 생성·갱신하는 요약, 개념, 비교 문서와 링크를 둔다.
- **스키마층:** 작성 규칙과 자료 처리 절차를 운영 설명서로 남긴다.
- **목차와 일지:** 무엇이 있는지와 언제 무엇을 처리했는지를 구분해 기록한다.[2]

### 시연에서 설명하는 흐름

1. Obsidian Vault를 만들고 Hermes의 작업 폴더를 그 위치로 지정한다.
2. 목적과 관심 주제를 알려 위키 구조·운영 규칙을 만든다.
3. Web Clipper로 AI 코딩 도구 관련 기사를 Markdown으로 수집한다.
4. 자료 처리 뒤 에이전트가 짧은 질문을 하게 해 **사용자의 관점**도 저장한다.
5. 기사를 요약·개념·비교 문서로 정리하고 서로 연결한다.
6. 자신의 생각과 모은 자료를 바탕으로 영상 소재를 요청하고 답도 노트로 남긴다.
7. 오래된 주장·모순·연결되지 않은 페이지를 점검한다.[2]

개별 기사 정리와 영상 소재 생성은 발표자의 활용 예시이지 정확도·생산성의 통제된 비교 실험은 아니다.

## 분석 — 단순 자료 보관과 무엇이 다른가?

**1. 가치가 생기는 지점은 ‘중간 결과를 남기는 것’이다.**

질문할 때만 검색하는 방식과 달리 기존에 만든 비교·개념 설명을 재사용할 수 있다. 다만 초기에 정리하는 비용과 이후 갱신·검토 비용이 추가된다. 자주 다시 보는 주제에는 유용하지만 한 번 보고 버릴 자료까지 정교한 위키로 만들면 관리 비용이 더 클 수 있다.

**2. 내 관점이 있어야 개인 지식 시스템에 가까워진다.**

영상의 강점은 자료 요약에 “왜 저장했는가”라는 개인 맥락을 추가한다는 점이다.[2] 이 프로젝트에서는 출처 사실, 사용자의 생각, AI의 분석을 구분해야 한다. AI가 만들어 낸 의견을 사용자 생각처럼 기록해서는 안 된다.

**3. ‘모두 기억한다’보다 ‘찾아 읽을 수 있도록 남긴다’가 정확하다.**

이 방식은 외부 Markdown을 축적하는 것이지 모델을 재학습하거나 모든 문서를 매번 문맥에 넣는 방식이 아니다.[8] 목차가 누락되거나 검색 범위가 좁으면 관련 기록을 놓칠 수 있다. “내 노트에 근거가 없으면 없다고 말하고, 사용한 문서를 표시하라”는 운영 규칙이 필요하다.

**4. 답변의 재저장은 검토를 거쳐야 한다.**

좋은 답을 문서로 남기는 것은 유용하지만, 잘못된 AI 답을 다시 읽으면 오류가 반복될 수 있다. 저장된 분석에는 원출처·검토 상태를 남기고 이전 AI 요약을 새로운 독립 증거처럼 세지 않는 것이 중요하다.

**5. 문서 규칙은 권한 통제와 다르다.**

“원본은 수정하지 말라”는 규칙은 필요하지만 파일 시스템의 읽기 전용 권한을 자동으로 설정하지는 않는다. 원본 보호, 변경 검토, 백업·버전 이력은 별도로 운영해야 한다. 이번 분석에서는 실제 설정을 바꾸지 않았다.

## 1차 문서 교차 확인

| 확인 항목 | 결과 |
|---|---|
| Karpathy의 LLM Wiki 개념 | 원문은 지속적으로 갱신하는 Markdown 위키와 원본·위키·스키마 구분을 명시한다.[8] |
| Ingest / Query / Lint | 원문에도 자료 반영, 근거 있는 질의 응답, 모순·누락 점검이라는 운영 흐름이 있다.[8] |
| 목차와 로그 | 원문에서 `index.md`는 내용 탐색, `log.md`는 시간순 작업 기록으로 구분한다.[8] |
| 사람이 읽기만 하면 되는가? | 원문은 AI 중심 유지보수를 제안하지만, 작성자가 요약과 변경을 확인하며 자료를 하나씩 처리하는 방식도 설명한다. 사람의 검토가 불필요하다는 뜻은 아니다.[8] |
| Web Clipper | 공식 페이지에서 브라우저용 웹 수집 도구임을 확인했고, Markdown 변환 활용은 Karpathy 원문에도 설명되어 있다.[5][8] |

원문의 일반적인 RAG 비판은 제안 배경이다. 모든 검색 기반 시스템에 기록·갱신 기능이 없다는 기술적 법칙으로 일반화하지 않는다. 위키와 검색은 함께 사용할 수 있으며 원문도 규모가 커지면 별도 검색 도구를 제안한다.[8]

영상의 모델 제공자·OAuth·요금·설치 화면 설명은 당시 시연 맥락으로만 취급한다. 현재 이용 조건이나 설치 가이드로 재사용하지 않는다. 설명란이 안내한 외부 공유방의 프롬프트 원문은 확보하지 않았으므로 복원해 제시하지 않는다.

## 이 프로젝트의 활용 제안

이미 있는 주제별 폴더와 README, `AGENTS.md`를 활용하고 영상의 폴더 구조를 통째로 다시 만들지 않는다. 출처별 분석은 `사례/`, 짧은 공통 원칙은 주제 README에 유지한다. 설치나 활성 에이전트 규칙 변경은 별도 작업으로 다룬다.

좋은 질문 예시는 다음과 같다.

> 내가 저장한 자료에서 추천 조건이 서로 다른 부분을 비교해 줘. 각 판단의 근거 문서와 내가 기록한 의견을 구분해서 보여 줘.

시작 범위는 관심 주제 하나가 적당하다. 활용 후에는 **근거를 다시 찾을 수 있는지, 기존 문서를 재사용하는지, 요약 수정 부담이 줄었는지**를 확인한다. 문서 수 증가 자체를 성공 지표로 삼지 않는다.
