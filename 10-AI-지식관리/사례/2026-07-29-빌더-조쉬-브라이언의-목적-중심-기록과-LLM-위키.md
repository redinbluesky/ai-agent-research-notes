## 영상 요약

브라이언은 기록이 AI에게 자신이 어떤 사람이고 무엇을 위해 질문하는지 알려 주는 맥락이라고 설명한다. 기록을 많이 하는 것보다 필요할 때 꺼내 활용할 수 있는지가 중요하며, 자신의 고도화된 기록 방식을 모두가 따라 할 필요는 없다고 말한다.[13]

### 1. 수집을 넘어 목적을 함께 기록한다

자료를 위키에 넣는 인제스트는 파일을 Markdown으로 바꾸는 것뿐 아니라 개념·엔티티를 나누고 기존 지식과 연결하는 과정으로 설명된다. 자료를 처리할 때 다음 질문을 추가한다.[13]

- 왜 이 자료를 저장했는가?
- 어떤 부분에 가치를 느꼈고, 내 생각은 무엇인가?
- 나중에 어디에 활용하고 싶은가?

영상에서는 AX 관련 영상을 정리하면서 컨설팅 관점과 관심 개념을 함께 입력한다. 개인 맥락을 넣은 자료가 개념·엔티티 노트로 연결되는 흐름을 소개한다.[13]

### 2. 하루를 서로 다른 관점으로 남긴다

영상의 표현을 단순화하면 다음과 같다. 실행과 현실은 출연자도 일부 겹친다고 설명한다.[13]

| 기록 층 | 담는 내용 |
|---|---|
| 의도 | 오늘 무엇에 시간을 쓰려 했는가 — 계획·우선순위 |
| 실행 | 실제 행동, 대화, 회의, 직접 남긴 타임스탬프 기록 |
| 현실 | 화면·활동 흔적 등 기억이나 수기 기록에서 빠질 수 있는 자료 |
| 해석 | 하루를 어떻게 느끼고 이해했는가 — 일기·개인 회고 |
| AI 로그 | AI와 무엇을 논의하고 만들었으며 어디까지 진행했는가 |

음성 기록 장치, Screenpipe, Hermes와 Claude의 개인 스킬을 결합한 운영을 소개한다. AI 작업 로그는 다음 세션에서 이어가기 위한 중간 저장점으로 사용하고, 기록을 바탕으로 일·월·분기·연간 회고와 개인 서사를 생성한 경험을 이야기한다.[13]

이는 출연자의 개인 운영 사례와 경험담이다. 모든 도구의 기본 기능이나 설치 즉시 가능한 자동화로 확인한 것은 아니다. 영상에서 부르는 로그·인제스트 스킬 역시 출연자의 설정이지 모든 에이전트에 내장된 공통 명령이 아니다.

### 3. 지식 그래프보다 먼저 정리 기준을 갖는다

출연자는 지식 그래프를 실제 연결된 지식으로, 온톨로지를 일관된 정리 기준이나 질서로 설명한다. 자신의 목적·세계관·판단 방식을 문서화해 자료 정리의 기준으로 활용한다.[13] 여기서 개인 철학 문서를 형식 논리 기반 온톨로지와 동일한 구현으로 간주할 필요는 없다.

## 분석 — 무엇을 가져오면 좋은가?

**자료 수집보다 활용 질문을 먼저 정하는 점이 핵심이다.**

“나중에 유용할 것”이라는 이유만으로 저장하면 분류 작업만 늘어난다. 반면 어떤 비교·판단에 쓸지 남겨 두면 나중에 AI도 관련 자료를 고르기 쉬워진다. 이 프로젝트에서는 출처별 사례에 수집 이유와 적용 질문을 짧게 추가하는 정도로 시작할 수 있다.

**의도·관찰·해석을 나누면 회고를 점검하기 쉬워진다.**

계획과 실제 활동을 구분하면 실행 차이를 살펴볼 수 있다. 그러나 화면 기록이 사람의 의도나 성과를 완전히 설명하지는 않는다. AI가 그럴듯한 서사를 만들어도 누락된 활동, 다른 사람의 기여, 해석 오류를 사람이 확인해야 한다.

**지식관리를 위한 기록과 상시 감시는 다르다.**

24시간 녹음·화면 기록은 입문 필수 조건이 아니다. 타인의 음성, 고객 정보, 로그인 화면, 개인 대화가 함께 수집될 수 있다. 도입하려면 참여자 동의와 조직 정책, 제외 대상, 보존 기간, 삭제 방법, 외부 AI 전송 범위를 먼저 정해야 한다. 여기서는 상시 수집을 권장하거나 설치하지 않는다.

**‘나에 대한 문서’도 수정 가능한 가설로 다루는 편이 낫다.**

영상은 기존 기록을 AI로 읽어 자신의 목적·가치를 정리하라고 제안한다.[13] 유용한 출발점일 수 있지만 과거 기록의 편향을 현재 정체성으로 고정하거나, AI가 추정한 성향을 사용자 발언처럼 저장하지 않아야 한다. 사용자가 확인한 가치와 AI의 추론을 분리하고 필요할 때 갱신하는 것을 추천한다.

## LLM 위키와 RAG — 영상 주장과 확인 사실 구분

영상에는 새 자료가 들어오면 RAG는 전체 인덱싱이 필요하지만 LLM 위키는 해당 자료만 처리하면 된다는 취지의 설명과, 기업에서도 위키가 더 좋다는 의견이 나온다.[13]

**전체 재색인은 RAG의 필수 특성이 아니다.** Microsoft의 Azure AI Search 공식 문서는 문서별 추가·삭제·병합과 증분 인덱싱을 지원한다고 설명한다. 따라서 해당 비교는 일반적 기술 차이로 사용할 수 없다.[15]

| 비교 관점 | 간단한 이해 |
|---|---|
| RAG | 질문에 필요한 외부 근거를 검색해 답변에 활용하는 방식 |
| LLM 위키 | 읽은 자료를 개념·비교·연결 문서로 축적하고 갱신하는 운영 방식.[8] |
| 함께 사용 | 정리된 위키와 원본을 검색해 답할 수 있으므로 양자택일이 아님.[8] |
| 도입 판단 | 자료 변경 빈도, 검색 품질, 근거 추적, 정리·검토 비용을 실제 질문으로 비교 |

사람이 읽는 정리 문서를 남긴다는 장점은 중요하지만, 위키도 새 자료가 기존 결론을 바꾸면 관련 페이지를 함께 갱신해야 한다. 반대로 검색 기반 시스템도 원문 텍스트와 메타데이터를 함께 보관할 수 있다. “RAG는 사람이 읽을 수 없고 위키만 읽을 수 있다”는 식의 대조도 피한다.

영상 제목의 “Obsidian+Claude Code 필수”는 제목의 강조 표현이다. Karpathy 원문은 특정 도구에 묶이지 않는 선택적·모듈형 패턴으로 설명한다.[8]

## 이 프로젝트에 대한 최소 적용 제안

1. 자료마다 **수집 이유·내 관점·활용할 질문**을 짧게 남긴다.
2. 중요한 작업을 마치면 **결정·근거·미완료 항목·다음 시작점**을 기록한다.
3. 주기적으로 기존 기록을 바탕으로 “무엇을 실제 결과물에 재사용했나?”를 점검한다.
4. 대규모 라이프 로깅이나 새로운 볼트 분리보다 현재 주제별 문서 구조에서 먼저 시험한다.

도입 기준은 “AI가 나를 잘 아는 느낌”보다 **필요한 기록을 찾는가, 근거를 설명하는가, 다음 작업에 실제로 도움이 되는가**다. 자동화 유지·수정에 드는 시간이 이득보다 크면 범위를 줄인다.
