## 영상 요약

구요한은 Obsidian을 파일 보관 장소뿐 아니라 자신의 연구·강의·프로젝트를 연결하는 운영 중심으로 설명한다. Markdown의 이식성과 로컬 보관을 선택 이유로 들고, 자신을 위해 만든 지식 분류·메타데이터 설명서가 이후 AI를 위한 설명서가 되었다고 이야기한다.[14]

### 1. 사람의 지식과 AI가 정리한 자료를 구분한다

| 영역 | 영상에서 설명한 주체와 목적 |
|---|---|
| 메인 볼트 | 사람이 주저자이고 AI가 보조. 자신이 이해하고 승인한 기록과 프로젝트 맥락 |
| LLM 위키 볼트 | AI가 주로 정리하고 사람이 관리·감독. 관심은 있지만 아직 충분히 소화하지 않은 외부 지식 |
| 실제 작업 폴더 | 개발 프로젝트, 계약서, PPT·PDF 등 실제 산출물. 모든 파일을 Obsidian 안에 넣지는 않음 |

기획·운영 문서는 Obsidian에 남기고 외부 프로젝트 폴더를 가리키게 한다. 핵심은 모든 데이터를 한곳에 복제하는 것이 아니라 필요한 곳으로 갈 수 있게 연결하는 것이다.[14]

### 2. 목차와 메타데이터를 지식에 들어가는 길로 사용한다

주제별 목차, 문서 종류, 날짜, 태그, 관련 세션 등을 통해 같은 지식에 여러 경로로 접근한다. 문서 작성 모델도 기록해 나중에 평가와 피드백을 연결하는 사례를 설명한다.[14]

본문 전체를 항상 읽기보다 짧은 설명과 메타데이터로 관련 문서를 고르는 방식도 강조한다. 자신의 숫자 분류 체계는 출연자의 설계 사례이며, 모든 사용자가 같은 번호·필드를 도입해야 한다는 뜻은 아니다.

### 3. 에이전트에게 맡겨도 사람이 방향을 안다

영상은 아홉 역할의 에이전트 설계를 소개하지만 모두 완전히 동작하는 상태는 아니라고 명시한다. 출연자는 전면 자동 운영보다 자신이 이해하고 검토할 수 있는 업무의 보조·감사·의견 제시에 무게를 둔다.[14]

모든 지식을 머릿속이나 저장소에 넣는 것보다 “어디에 물어보면 되는가”를 아는 것이 중요하다는 설명이다. 실제 도구 기능, 개인 구성, 아직 설계 단계인 구상은 구분해 읽어야 한다.

### 4. 기록을 실제 운영과 결과물로 연결한다

음성 전사본을 지식으로 정리하고, 인터뷰 질문을 기존 기록과 대조해 수정·응답 초안을 만드는 사례를 소개한다. 지식관리 성숙도를 점검하는 AKM Index도 보여 주며, 시작은 좋아하는 주제나 취미의 단순한 기록이어도 충분하다고 권한다.[14]

## 분석 — 이 사례의 핵심 설계 원칙

**1. 볼트 분리의 핵심은 폴더 개수가 아니라 저자와 검토 책임이다.**

AI가 작성한 자료를 내 지식과 구분하면 요약 오류를 내 판단으로 오인하는 것을 줄일 수 있다. 다만 볼트가 여러 개면 중복·동기화·교차 검색 비용도 생긴다. 작은 저장소에서는 출처·작성 주체·검토 여부를 명확히 표시하는 것부터 시작해도 된다. 이번 작업에서 실제 볼트를 분리하지 않는다.

**2. 설명서는 사람과 AI 모두가 이해할 수 있어야 한다.**

규칙이 일관되면 AI가 문서를 어디에 놓고 무엇과 연결할지 판단하기 쉬워진다. 반면 복잡한 분류 체계를 먼저 도입하면 운영자가 규칙을 유지하는 데 시간을 쓰게 된다. 실제로 찾고 비교하는 데 필요한 필드부터 시작하고 사용하지 않는 분류는 늘리지 않는 편이 좋다.

**3. 메타데이터는 검색의 단서이지 답의 정확성 보장이 아니다.**

설명이 잘못되면 AI는 엉뚱한 본문을 고를 수 있다. 생성 모델·세션 링크는 추적에 도움을 주지만 사실의 근거를 대신하지 않는다. 중요한 판단은 원출처와 본문을 다시 확인해야 한다.

**4. 자동화 수준보다 검토 가능성을 먼저 본다.**

“내가 아는 일만 위임한다”는 발언은 출연자의 운영 철학이다.[14] 이 프로젝트에는 결과의 합격·불합격을 근거로 판단할 수 있는 작업부터 맡긴다는 원칙으로 적용할 수 있다. 모든 자동화를 거부하거나 모든 변경을 수동 승인하라는 보편 법칙으로 확대할 필요는 없다.

**5. 평가 점수가 지식관리의 목적을 대신하면 안 된다.**

공개 루브릭은 누락된 운영 요소를 찾는 데 유용하지만 높은 점수가 글쓰기·연구·의사결정 성과를 직접 증명하지는 않는다. 자동화를 늘리기 전에 실제 재사용과 검토 부담의 개선을 확인하는 것이 우선이다.

## 공개 문서 교차 확인

영상 이후 공개 문서가 갱신되어 있으므로 아래는 현재 조회한 자료와의 개념 대조이지, 영상 당시 버전을 재현한 결과가 아니다.

| 항목 | 확인한 내용 |
|---|---|
| 사람·AI 공용 설명서 | CMDS System Files는 시스템 철학, 운영 표준, 탐색 목차와 에이전트 지시 파일을 구분한다.[17] |
| 메인·위성 볼트 | LLM Wiki 공개 설명은 사람 주저자의 메인 볼트와 LLM 주저자의 위성 위키를 구분한다.[18] |
| 위키와 검색의 관계 | 공개 위키는 정리된 페이지를 만들면서 qmd 기반 검색도 사용한다고 명시한다. 위키와 검색을 병행하는 구현 사례다.[18] |
| RAG 비교 | RAG가 매번 전체 색인을 다시 만들어야 한다는 일반화는 맞지 않는다. Azure AI Search에는 증분 갱신이 있다.[15] |
| AKM Index | 공식 자료는 Prompt·Context·Harness·Loop·Interop & Governance를 평가하며 파일·설정·로그 증거를 요구한다. 제작자 측 공개 루브릭으로, 보편적인 공인 인증과는 구분한다.[16][19] |

CMDS의 문서 우선순위와 포함 문법은 해당 시스템의 규칙이다. 모든 에이전트가 동일한 파일을 자동 로드하고 같은 우선순위를 적용한다고 가정하지 않는다. 또한 영상의 LLM 위키 “컴파일”은 자료를 지식 문서로 정리·갱신한다는 비유이며, 결정적 코드 컴파일처럼 결과의 정확성이 보장된다는 뜻은 아니다.

## AKM 평가 스킬: 공개 구현에서 확인한 주의점

저장소 트리·README 및 커밋 `383ef42a870f284c31a8f7dae006be181be9df0b`의 `SKILL.md`를 읽었다. 이 스킬은 실행 절차를 적은 에이전트 지침이며, 참조 문서에 루브릭·리포트 구조·런타임 탐지 경로를 둔다. 저장소는 MIT 라이선스를 표시한다.[19][20]

| 구분 | 문서에서 확인한 동작 |
|---|---|
| 평가 | 저장소·런타임·최근 사용 흔적 확인 → 파일·설정·로그 수집 → 채점 → 자기검증 → 보고서 생성.[20] |
| 업로드 | 결과 요약과 안내 후, 명시적으로 거부하지 않으면 `akm-report.json`을 운영팀에 제출하도록 되어 있음.[20] |
| 보드 공개 | 운영팀 제출과 별도 동의 항목으로 구분됨.[19][20] |
| 외부 전송 해석 | “CMDSPACE에 제출하지 않음”과 “클라우드 LLM에도 아무것도 전송하지 않음”은 다름. 스킬의 로컬 실행 표현만으로 사용하는 모델 제공자의 데이터 처리를 보장할 수 없음 |

따라서 영상의 로컬 평가 설명을 **기본적으로 아무 외부 전송도 없는 도구**라고 요약하면 부정확하다. 실제 도입한다면 평가 범위, 세션 로그 접근, 보고서 전송 내용을 먼저 확인하고 **제출은 명시적으로 승인한 경우에만** 진행하는 것을 권장한다. 이번 조사에서는 스킬을 설치·실행하거나 사용자 데이터를 수집·제출하지 않았다.

이 확인은 공개 실행 지침의 정적 검토이며 백엔드의 저장·삭제 정책이나 보안성을 검증한 것은 아니다.

## 이 프로젝트에 적용할 최소 원칙

- 기존 주제별 README는 탐색 지도, `AGENTS.md`는 공통 운영 기준으로 유지한다.
- 출처 사실·사용자 의견·AI 분석을 구분하고 검토한 결론만 공통 원칙에 반영한다.
- 문서에 필요하다면 작성 주체·검토 상태·관련 작업 링크를 추가하되 일괄 재분류는 하지 않는다.
- 실제 결과물은 알맞은 작업 폴더에 두고 연구 문서에서 근거와 위치를 연결한다.
- 시작 기준은 “노트가 얼마나 많은가”가 아니라 “어디에 무엇이 있고, 다음 작업에서 다시 쓸 수 있는가”로 삼는다.
