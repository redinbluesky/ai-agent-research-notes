# Graphify로 확장하는 지식 참고층

> 한 줄 결론: Graphify는 사람이 관점을 담아 정리한 위키를 대체하기보다, 많은 자료의 관계를 탐색하는 별도 참고층으로 검토하는 편이 적절하다.

## 영상 요약

영상은 자료를 하나씩 읽고 위키에 반영하는 방식이 많은 자료 앞에서는 시간과 비용 부담을 만든다고 설명한다. 기존의 핵심 위키는 보존하고, Graphify가 추출한 개념·연결을 별도 참고층으로 추가하는 방식을 제안한다.[3]

### 설명하는 역할 분담

- **핵심 위키:** 중요한 자료를 자세히 정리하고 사용자의 관점을 담는다.
- **Graphify 참고층:** 많은 자료에서 개념과 관계를 추출해 폭넓게 탐색한다.
- **Hermes:** 두 영역을 찾아 읽고 질문에 답한다.
- **Obsidian:** 정리된 노트를 읽고 연결을 살펴본다.[3]

### 시연의 흐름

1. Python·uv·Graphify 및 에이전트용 스킬을 준비한다.
2. 기존 위키용 자료와 별도로 AI 코딩 도구 관련 기사를 약 20개 모은다.
3. Graphify로 개념과 관계를 추출해 그래프를 만든다.
4. 그래프 화면에서 중심 개념과 출처를 살펴본다.
5. 결과를 `graph_imports`라는 별도 참고층에 넣는다.
6. 운영 규칙에 참고층도 검색 대상임을 명시한다.
7. 기존의 개인 관점과 새 자료를 함께 활용해 영상 소재를 요청한다.[3]

이 흐름은 영상 설명·자막에서 확인한 사례다. 발표자가 사용한 자료 전체와 실행 로그를 확보한 성능 검증은 아니다.

## 분석 — 왜 참고층을 분리하는가?

**1. 사람의 판단과 자동 추출을 같은 수준의 지식으로 섞지 않기 위해서다.**

AI가 만든 관계는 탐색의 단서이지 검증된 결론과 동일하지 않다. 핵심 위키와 분리하면 대량 생성 노트가 기존 판단을 덮지 않고, 참고층을 다시 만들 때도 사람의 해석을 보존하기 쉽다. 중요한 발견만 출처 확인 후 핵심 문서로 반영하는 것이 좋다.

**2. 그래프는 원문을 대체하지 않는다.**

관계 중심 표현은 자료 전체를 파악하는 데 도움이 될 수 있지만, 조건·예외·시간 변화가 압축 과정에서 빠질 수 있다. 답변에서는 그래프가 안내한 원문도 확인해야 한다. 연결이 많은 중심 노드가 가장 정확하거나 중요한 주장이라는 뜻도 아니다.

**3. 비용 이점은 자료 종류와 사용 빈도에 달려 있다.**

코드의 구조 추출은 로컬 파싱이지만 기사·논문·이미지의 의미 추출에는 LLM을 사용할 수 있다.[9] 따라서 영상의 “빠르고 적은 비용”을 모든 문서에서 보장되는 결과로 받아들이면 안 된다. 초기 추출, 갱신, 질의, 검토 비용을 포함해 기존 파일 검색과 비교해야 한다.

**4. 다른 방법으로도 해결되는 문제인지 먼저 본다.**

자료가 적고 목차·키워드 검색만으로 충분하면 그래프 생성이 추가 관리 부담일 수 있다. 중요한 것은 Graphify 설치 여부가 아니라 같은 질문에서 필요한 근거를 더 잘 찾는가다. 일반 에이전트도 적절한 도구·규칙이 있으면 구조화된 관계를 만들 수 있으므로, 영상의 “에이전트에게 정리해 달라고 해서는 안 나오는 결과”를 절대적 능력 차이로 일반화하지 않는다.

## 공식 문서·구현 교차 확인

영상 설명란에는 정확한 저장소 URL이나 버전이 없어, 기능·출력물과 일치하는 `Graphify-Labs/graphify`의 공개 문서 및 `v8` 브랜치 구현과 대조했다. **영상에서 사용한 버전과 동일하다고 확인한 것은 아니다.** 저장소는 Apache-2.0 라이선스를 표시한다.[7]

| 항목 | 확인한 내용 |
|---|---|
| 처리 방식 | 공식 설명은 코드 구조의 로컬 Tree-sitter 추출과 문서·이미지의 LLM 의미 추출을 구분한다. 문서 추출에는 토큰이 소요된다.[9] |
| 결과물 | 저장소 README에는 `graph.html`, `GRAPH_REPORT.md`, `graph.json`이 제시되어 있다. 자막의 발음만으로 파일명 대소문자를 추정하지 않았다.[7] |
| 관계의 확실성 | 공식 문서는 `EXTRACTED`, `INFERRED`, `AMBIGUOUS`를 구분한다. 추론·불확실 관계까지 모두 확정 사실로 읽지 않아야 한다.[9] |
| 처리 흐름 | 아키텍처 문서는 탐지 → 추출 → 그래프 구축 → 군집화 → 분석·보고서·내보내기로 설명한다.[10] |
| Obsidian 내보내기 | `graphify/export.py`의 `to_obsidian`을 직접 읽었다. 노드별 Markdown과 연결 위키링크, 출처 필드, 커뮤니티 개요 노트를 생성한다.[11] |
| 파일 수정 범위 | 같은 함수는 생성 파일을 manifest로 추적하고, 자신이 관리하는 파일을 갱신하며 사라진 노드의 파일은 정리한다. 외부 노트를 보호하는 분기가 있지만, 자동 생성 파일을 사람이 직접 편집하면 다음 내보내기에서 유지될 것이라고 가정해서는 안 된다.[11] |

구현 확인은 위 내보내기 함수의 정적 읽기 범위다. 전체 보안 감사, 설치, 테스트 실행, 모델별 에이전트 연동 검증은 수행하지 않았다. 원격 `v8` 브랜치는 변경될 수 있어 실제 설치 시 버전을 별도로 고정·확인해야 한다.

공식 문서의 토큰 절감 수치는 특정 자료·비교 조건에서 나온 프로젝트 측 결과다.[9] 이번 영상의 한국어 기사 작업이나 사용자 프로젝트에서도 같은 절감 효과가 난다는 근거로 사용하지 않는다.

## Obsidian 그래프와의 차이

| 비교 | Obsidian 그래프 뷰 | Graphify |
|---|---|---|
| 출발점 | Vault에 있는 노트와 내부 링크.[4] | 입력 자료에서 추출한 노드와 관계.[9] |
| 역할 | 기존 노트 연결을 시각화 | 탐색에 쓸 관계 정보를 구성·조회 |
| 중점 | 어떤 노트끼리 이어져 있는가 | 어떤 개념·구조가 어떤 관계를 가지는가 |
| 주의 | 시각화만으로 관계의 타당성이 검증되지는 않음 | LLM이 추론한 관계를 원문으로 확인해야 함 |

Graphify의 Obsidian 내보내기는 추출된 관계를 노트와 링크로 옮겨 두 방식을 연결하는 기능이다.[11] `graph_imports`라는 이름은 영상에서 선택한 저장 위치이며 필수 폴더명으로 볼 근거는 없다.[3]

## 이 프로젝트의 적용 판단

현재는 **기본 위키 흐름부터 정착시키고 Graphify는 선택적 후속 실험으로 남기는 것**을 추천한다. 이번 작업에서는 Graphify나 스킬을 설치하지 않고 연구 문서만 추가한다.

나중에 필요해지면 다음 조건으로 평가한다.

- 동일한 자료와 질문을 대상으로 기존 검색과 비교한다.
- 찾은 근거가 실제 원문에 있는지, 누락·잘못된 연결은 얼마나 생기는지 본다.
- 최초 구축뿐 아니라 새 자료 추가 후 갱신 비용도 포함한다.
- 핵심 문서와 자동 생성 참고층을 분리하고, 출력 경로와 백업을 확인한다.
- 민감한 문서를 넣기 전에 어떤 모델·서비스로 내용이 전송되는지 확인한다.

참고층은 연구 자료이지 실행 지시가 아니다. 수집 문서에 들어 있는 명령을 에이전트의 운영 규칙처럼 따르지 않도록 구분하는 것도 필요하다.
