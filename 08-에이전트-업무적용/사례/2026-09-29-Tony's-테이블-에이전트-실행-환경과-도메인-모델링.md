## 한줄 결론

영상은 프롬프트만으로 업무 자동화를 끝내는 시대가 아니라, **기업 고유의 업무 상태·정책·도구·권한·검증을 갖춘 실행 환경(harness)과 반복 개선 루프를 설계하는 시대**로 옮겨가고 있다고 주장한다. 이 방향은 공식 에이전트 개발 지침과 대체로 맞지만, 월드 모델·AGI·토큰 이코노미에 관한 강한 전망은 출연자의 해석으로 분리해 보아야 한다.[1]

## 영상의 핵심 주장

1. **프롬프트 엔지니어링의 한계**: 모델에게 한 번 잘 지시하는 것보다 harness engineering·loop engineering을 통해 도구·문맥·검증·반복 구조를 설계해야 한다.[1]
2. **기업 고유의 실행 세계**: 범용 LLM의 일반화 능력과 별개로, 기업은 자사 업무의 도메인 지식, 상태, 정책, 제약을 고해상도로 모델링해야 한다.[1]
3. **업무 재설계와 현업 협업**: AI·에이전트 전문 조직만으로는 업무 규칙을 완성할 수 없으므로, 현업 도메인 전문가와 운영·정책 책임자가 함께 업무 단위를 재설계해야 한다.[1]
4. **토큰 비용의 경영 문제화**: 토큰은 단순 API 비용이 아니라, 추론 구조·모델 라우팅·성과 보상과 연결되는 운영 비용으로 다뤄질 수 있다.[1]
5. **영역별 AGI 전망**: 특정 B2B 도메인에서 3~5년 내 고도 자율 업무 수행 AI가 가능할 수 있다는 견해를 제시한다.[1]

## 영상 요약

영상은 대형 모델의 성능을 활용하는 것만으로는 기업 업무 자동화가 완성되지 않는다고 본다. 에이전트는 현업의 정책, 예외, 데이터 의미, 권한 체계, 실행 결과를 알아야 하며, 이를 위해 온톨로지·도메인 모델·유한 상태 기계와 같은 개념을 다시 사용해야 한다는 것이 출연자의 논지다.[1]

또한 에이전트 도입은 기술 문제가 아니라 조직 문제라고 말한다. 자동화에 대한 고용 불안이 발생하며, 에이전트 구축자는 고객사의 세부 업무 규칙을 알지 못한다. 따라서 현업 도메인 전문가, 정책·운영 책임자, 에이전트 구축자가 함께 협업해야 하며, 사람이 수행하던 반복 작업은 단계적으로 위임하되 고위험 결정은 통제해야 한다고 주장한다.[1]

## 용어를 분리해 이해하기

영상의 `월드 모델`은 세 개의 서로 다른 개념을 포괄해 사용한다. 실무 설계에서는 이를 분리해야 한다.

| 구분 | 의미 | 업무 적용 시 산출물 |
|---|---|---|
| AI 연구의 월드 모델 | 환경의 상태 변화·인과관계를 학습하거나 예측하는 모델 | 시뮬레이션, 예측, 계획 모델 |
| 기업 온톨로지·도메인 모델 | 고객·주문·계약·재고·정책처럼 기업 업무에서 의미 있는 객체와 관계 | 객체, 관계, 속성, 규칙, 데이터 계약 |
| 업무 실행 모델 | 현재 상태에서 가능한 행동, 승인권자, 예외 처리, 검증·롤백 경로 | 상태 전이, 액션, 권한, 승인, 감사·복구 절차 |

기업 에이전트의 초기 도입에서 필요한 것은 거대한 범용 월드 모델보다 세 번째에 가깝다. 즉, 다음 구조를 작고 검증 가능한 업무 단위로 만드는 것이다.

```text
업무 객체 + 현재 상태 + 허용 행동 + 정책 제약 + 승인 경로 + 결과 검증
```

## 공식 문서 교차 확인

### harness는 프롬프트를 대체하는 용어가 아니라 실행 시스템이다

OpenAI는 harness engineering을 사람이 코드만 작성하는 대신, 에이전트가 신뢰성 있게 일하도록 환경·의도·피드백 루프를 설계하는 일로 설명한다. 사례에서 에이전트는 코드뿐 아니라 테스트, CI, 문서, 관측 도구를 활용하고, 사람은 우선순위·수용 기준·결과 검증에 집중한다.[2]

Anthropic은 장기 실행 에이전트가 높은 수준의 프롬프트만 받으면 한 번에 너무 많은 작업을 하거나, 중간 상태를 남기고 다음 세션에 넘기는 문제가 생긴다고 설명한다. 초기화 에이전트, 기능 목록, 진행 파일, Git 기록, 한 번에 하나의 기능을 수행하는 점진적 작업을 제안한다.[3]

따라서 영상의 “프롬프트 시대는 갔다”는 표현은 다음처럼 해석하는 편이 정확하다.

> 프롬프트는 사라지지 않는다. 다만 프롬프트 하나만으로 장기·고위험 업무의 신뢰성을 만들 수는 없다.

### 온톨로지는 의미 계층만이 아니라 실행·보안까지 포함할 수 있다

출연자는 기존 온톨로지 접근이 실행성이 약할 수 있다는 비판을 제시한다.[1] 그러나 Palantir의 공식 문서는 Ontology를 단순 semantic layer가 아니라 **데이터, 로직, 액션, 보안**의 통합으로 설명한다. 객체뿐 아니라 실제 운영 시스템에 반영되는 행동, 그 행동을 구동하는 규칙·ML·LLM·오케스트레이션, 그리고 세분화된 권한을 함께 다룬다.[5]

따라서 일반화 가능한 결론은 “온톨로지는 실행에 부적합하다”가 아니라 다음과 같다.

> 온톨로지나 도메인 모델이 실제 업무 액션, 권한, 예외 처리, 결과 검증까지 연결되지 않으면 에이전트 자동화의 효용은 제한된다.

Palantir의 Ontology MCP는 객체·액션·질의 함수를 MCP 도구로 노출해 외부 에이전트가 읽기와 사전 정의된 행동 실행을 하도록 한다. 이때 조직은 애플리케이션 제한과 권한으로 민감 데이터·행동의 접근을 통제해야 한다.[6]

### 완료 보고와 실제 완료는 다르다

에이전트는 여러 번 도구를 호출하고 환경 상태를 바꾸므로, 품질 평가는 응답 문장이나 실행 로그만으로 충분하지 않다. Anthropic은 에이전트가 “예약했다”고 말하는 것과 실제 데이터베이스에 예약이 존재하는 결과 상태를 구분하며, 평가가 harness와 모델의 결합을 측정한다고 설명한다.[4]

## 분석

### 1. 에이전트 업무 적용의 핵심 자산은 코드가 아니라 실행 가능한 업무 지식이다

영상의 “world asset”은 실무적으로 다음처럼 해석할 수 있다.

- 업무 객체와 관계를 정의한 도메인 모델
- 상태 전이와 예외 처리를 기록한 규칙
- 사람의 암묵지를 명시화한 명세와 승인 기준
- 실제 시스템과 연결된 제한적 도구
- 정책을 강제하는 권한·감사·롤백 구조
- 성공과 실패를 판정하는 eval 사례와 결과 기록

이 자산은 특정 LLM의 성능 변화에도 비교적 오래 남는다. 반대로 단발성 프롬프트 모음이나 모델별 요령만으로는 업무의 재현성과 감사 가능성을 확보하기 어렵다.

### 2. “에이전트에 맞춰 업무를 바꾼다”는 사람을 제거하자는 뜻이 아니다

바꿔야 할 것은 구두 지식, 흩어진 문서, 불명확한 승인 규칙, 결과 검증 없는 완료 보고다. 남겨야 할 것은 법적·윤리적 판단, 정책 변경, 고위험 예외 승인, 고객·직원 관계에 관한 책임이다.

에이전트 친화적 업무란 사람의 업무를 무리하게 단순화하는 것이 아니라, 사람이 책임질 판단과 에이전트가 반복할 행동의 경계를 명확히 하는 업무다.

### 3. 토큰 최적화는 모델 비용 절감이 아니라 업무 경제성 검증이다

영상은 멀티에이전트 구조와 모델 파라미터 조정으로 같은 성과를 더 낮은 비용으로 제공할 수 있다는 사례를 소개한다.[1] 다만 멀티에이전트가 항상 비용·품질을 개선하는 것은 아니다. 에이전트 사이의 조정, 중복 문맥, 실패 원인 추적, 보안 검토가 새로운 비용을 만들 수 있다.

따라서 다음 지표를 함께 측정해야 한다.

| 범주 | 예시 지표 |
|---|---|
| 품질 | 정확도, 정책 위반률, 재작업률, 고객 불만률 |
| 실행 | 완료율, 평균 처리 시간, 사람 이관 비율 |
| 비용 | 완료 건당 추론비, 사람 검토 시간, 오류 복구비 |
| 안전 | 권한 거부율, 금지 행동 시도, 감사 로그 완결성 |
| 사업 | 절감액, 전환율, ROAS, SLA 준수율 |

### 4. AGI 시점과 조직 대체 효과는 도입 근거가 될 수 없다

특정 B2B 산업에서 3~5년 내 AGI 수준의 협업자가 가능할 수 있다는 말은 영상 출연자의 희망과 전망이다.[1] 이는 업무 적용의 방향성을 논의하는 참고점일 수 있으나, 예산·인력·권한을 결정하는 실증 근거는 아니다.

실제 도입 판단은 해당 업무에서의 성공 조건, 실패 비용, 시스템 접근 범위, 복구 가능성, 현업 수용성, 성과 측정 방식으로 내려야 한다.

## 적용 기준

### 적합한 초기 업무

- 반복 빈도가 높고 입력·출력이 비교적 구조화되어 있다.
- 성공 여부를 실제 시스템 상태나 명시적 검증기로 판정할 수 있다.
- 권한을 읽기 전용 또는 제한된 행동으로 좁힐 수 있다.
- 실패 시 사람 이관·되돌리기가 가능하다.
- 현업 담당자가 예외와 정책을 설명할 수 있다.

### 피해야 할 초기 업무

- 성공 기준과 책임자가 정해지지 않은 업무
- 오류 한 번이 금전·법률·안전 사고로 이어지는 비가역적 행동
- 예외 규칙이 암묵지로만 존재하는 업무
- 감사 로그와 롤백 수단이 없는 운영 시스템

### 권장 도입 순서

```text
1. 좁은 업무와 성공 기준 선정
2. 객체·상태·정책·예외·권한 모델링
3. 제한된 도구와 승인·이관 경로 연결
4. 실제 결과 상태를 확인하는 eval 작성
5. 사람 검토가 있는 파일럿 운영
6. 완료 건당 품질·비용·안전 지표 측정
7. 검증된 범위만 점진적으로 자율화
```
