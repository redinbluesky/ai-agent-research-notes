## 한 문장 결론

기본은 최종 산출물을 책임지는 단일 리드 에이전트에 독립·제한 작업만 서브에이전트로 위임하고, 반복 검증에는 Goal, 장기 역할 분리에는 Bot, 의존성·재시도·감사 이력에는 Kanban을 단계적으로 도입하라는 영상이다.[1]

## 영상 요약

영상은 다중 에이전트 팀이 항상 단일 유능한 에이전트보다 낫지는 않으며, 작업의 지속성·독립성·완료 검증·의존성에 맞춰 조정 방식을 확장해야 한다고 주장한다.[1]

1. **단일 에이전트와 서브에이전트 위임**: 리드 에이전트가 독립 조사·검토를 병렬 위임하고 결과를 종합한다. 메인 컨텍스트 부담을 낮출 수 있지만, 서브에이전트는 부모의 대화 이력을 모르므로 목표와 맥락을 구체적으로 전달해야 한다.[1]
2. **Goal loop**: 완료 기준을 명시해 같은 세션에서 조사·수정·검증을 반복한다. 출처 수, 분량, 테스트 통과처럼 확인 가능한 조건을 먼저 제시할수록 잘 작동한다고 설명한다.[1]
3. **Bot mode**: Researcher, Librarian, Orchestrator처럼 역할마다 모델·스킬·기억·도구를 나눠 지속적인 전문성을 운영한다.[1]
4. **Kanban task graph**: 작업 카드의 담당자, 선후 관계, 사람 검토, 재시도와 실행 이력을 관리한다. 단순 위임보다 장기적·다단계 작업에 적합하다고 설명한다.[1]

영상의 최종 권고는 지속적인 독립 병렬 작업이 실제로 필요하다는 것이 확인될 때만 영속 팀을 만들고, 그 전에는 단일 책임자와 제한적 위임을 기본값으로 두는 것이다.[1]

## 분석

### 핵심은 에이전트 수가 아니라 상태와 책임의 배치다

이 영상의 가장 유효한 분석 틀은 "몇 개의 에이전트를 쓸 것인가"를 제품 선택 문제가 아니라 **상태·책임·완료 판정이 어디에 남는가**의 문제로 바꾼 점이다.[1]

서브에이전트 위임에서는 리드 에이전트가 작업 정의와 최종 판단을 보유하고, 자식은 범위가 정해진 증거 수집 또는 검토를 수행한다.[2]

반면 Bot은 역할별 기억과 정책을 지속시키고, Kanban은 카드·의존성·핸드오프를 대화 밖의 내구성 있는 상태로 옮긴다.[4][5]

따라서 팀을 도입할 근거는 "작업이 어렵다"가 아니라 다음 중 무엇이 필요한지로 판단해야 한다.[1]

| 필요한 상태 또는 책임 | 가장 작은 적합 수단 | 팀·Kanban이 불필요한 이유 또는 도입 신호 |
|---|---|---|
| 한 번의 결과를 끝까지 고치고 검증 | 단일 리드 + `/goal` | 작업 간 인수인계가 없으므로 보드의 지속 상태가 필요 없다.[3] |
| 서로 독립적인 증거 수집·비교 | 리드 + 서브에이전트 | 자식이 완료 요약만 반환해도 리드가 결론을 낼 수 있다.[2] |
| 역할별 지식·도구·정책이 여러 작업에 반복됨 | Bot/Profile | 동일 역할의 문맥을 매번 `context`로 재전달하는 비용이 반복될 때다.[4] |
| 선후 관계, 재시도, 사람 승인, 실행 이력이 장기간 필요 | Kanban | 카드 간 의존성과 구조화된 핸드오프가 필요한 시점이다.[5][6] |

### 영상의 비용 비교는 아키텍처 선택의 충분한 근거가 아니다

영상의 37k 대 102k 비교는 부모 컨텍스트를 덜 쓰는 위임 구조의 장점을 보여 주지만, 서브에이전트 토큰·모델 비용·도구 호출·최종 검토 비용을 포함한 총비용 비교는 아니다.[1] 또한 같은 과업을 여러 번 반복한 통제 실험, 정확도·누락률·수정 횟수·사람 검토 시간의 비교도 영상 자막에서 확인되지 않는다.[1]

그러므로 이 영상의 수치는 일반적인 "멀티에이전트 절감률"로 사용하면 안 된다. 실제 도입 판단에는 다음 기준선을 같은 과업에서 비교해야 한다.[1]

1. **품질:** 필수 출처·테스트·요구사항의 누락률과 최종 검토 수정 횟수
2. **비용:** 리드·자식·judge·자동 분해를 모두 합친 토큰과 외부 도구 비용
3. **지연:** 첫 결과뿐 아니라 재시도와 사람 승인까지 포함한 완료 시간
4. **운영 부담:** 실패 원인 파악, 재실행, 핸드오프 확인에 드는 시간

이 네 지표에서 단일 리드 기준선보다 지속적으로 개선될 때만 Bot 또는 Kanban의 조정 비용이 정당화된다. 이는 영상의 결론을 실행 가능한 의사결정 규칙으로 바꾼 분석이다.[1]

### 자동 분해의 품질은 실행 모델보다 작업 명세에 더 크게 좌우된다

영상은 자동 분해에 강한 모델을 쓰고 실행 워커에는 비교적 저렴한 모델을 쓰는 전략을 소개한다.[1] 이는 합리적일 수 있지만, 분해 모델이 훌륭해도 원래 카드가 모호하면 잘못된 하위 작업·불필요한 병렬화·누락된 검토 단계를 만들 수 있다. Hermes의 Triage는 모호한 아이디어를 구체화하거나 그래프로 분해하는 진입점이지만, 정의되지 않은 완료 조건을 자동으로 올바르게 만들어 주는 보장은 아니다.[5][6]

따라서 자동 분해 카드에는 최소한 목표, 입력 범위, 산출물 형식, 완료 기준, 예산 또는 출처 수 상한, 사람 승인 조건을 포함해야 한다. 특히 외부 상태를 바꾸는 카드에는 "자동 실행"보다 `Blocked` 상태에서의 명시적 승인 설계가 우선이다.[5]

### 이 연구 노트 프로젝트에 대한 판단

이 저장소의 영상 분석은 하나의 최종 문서가 저장소 구조·인용·분류 규칙을 모두 만족해야 하므로, **리드 에이전트 한 명이 최종 책임을 지는 구조**가 적합하다. 공식 문서 조사, 연결 저장소 확인, 링크 검증처럼 서로 독립적인 단계만 서브에이전트로 병렬화할 수 있다.[2]

사례 문서의 인용 완결성·내부 링크·저장 위치까지 확인해야 할 때는 `/goal`로 완료 조건을 명시하는 편이 Kanban보다 단순하다.[3]

다만 여러 영상이 동시에 들어오고 `조사 → 공식 문서 검증 → 초안 → 독립 리뷰 → 저장`의 파이프라인이 반복되며, 각 단계의 담당·재시도·승인 이력을 보존해야 한다면 Kanban 도입을 재검토할 만하다.[5][6]

그 판단의 관찰 기준은 월 단위 병렬 작업 수가 아니라, **리드 대화 하나의 수동 조정만으로 더 이상 작업 순서·실패·검토를 안정적으로 관리할 수 없는지**다.[1]

### 부모 컨텍스트 절감과 총비용은 다르다

영상은 위임한 실험에서 부모가 약 36~37k 토큰, 위임하지 않은 단일 에이전트가 약 102k 토큰을 사용했다고 제시한다.[1] 다만 영상도 서브에이전트의 사용량은 이 비교에서 제외된다고 밝힌다.[1] 따라서 이 결과는 총 토큰·총비용 절감의 증거가 아니라, 리드 에이전트가 원문과 중간 산출물을 모두 유지하지 않아도 되는 **부모 컨텍스트 절감**의 사례로 해석한다.

## 공식 문서로 확인한 보충 사항

### 서브에이전트는 격리된 단기 작업자다

Hermes의 `delegate_task`는 새 대화·자체 터미널 세션·격리된 컨텍스트를 가진 자식 에이전트를 생성하고, 부모에는 최종 요약만 돌려준다.[2] 자식은 부모의 대화 이력과 이전 도구 호출을 알지 못하며 `goal`과 `context`에 전달된 정보로만 작업한다.[2] 따라서 병렬 조사, 독립 검토, 대규모 자료의 맥락 격리에는 적합하지만, 세션 종료나 프로세스 재시작 뒤에도 살아야 하는 durable 작업에는 적합하지 않다.[2]

### Goal은 단일 세션의 완료 반복 장치다

`/goal`은 매 턴 뒤 judge 모델이 목표 충족 여부를 확인하고, 미달이면 같은 세션에 후속 작업을 넣어 반복한다.[3] 그러나 Goal을 설정해도 Kanban 카드가 생성되거나 다른 프로필로 작업이 배정되지는 않는다.[3] 하나의 채팅에서 반복 검증이 필요한 경우에는 `/goal`, 다수 작업의 의존성·핸드오프·다중 프로필이 필요할 때는 Kanban을 사용해야 한다.[3]

### Bot은 장기 역할을 보유하는 Profile이다

Hermes의 Bot은 독립된 새 실행 단위가 아니라, 역할·모델·메모리·스킬·자격 증명·대화 이력을 가진 Profile을 지속적 Bot Chat으로 표현한 것이다.[4] 역할별로 필요한 맥락과 정책이 다르고 반복 업무가 충분할 때 Researcher나 Librarian 같은 Bot을 분리하는 편이 유리하다.[4]

### Kanban은 내구성 있는 작업 보드와 구조화된 핸드오프다

Hermes Kanban은 작업·핸드오프를 SQLite 보드에 저장하고, 카드별 워커를 별도 OS 프로세스로 실행한다.[5]

parent-child 의존성에 따라 후속 카드는 선행 작업 완료 뒤 `ready`가 되며, 후속 워커는 부모의 완료 요약과 메타데이터를 받을 수 있다.[5][6]

현재 기본 흐름은 `Triage → Todo → Ready → In progress → Blocked 또는 Done`이며, Triage의 작업은 설정에 따라 자동 분해하거나 수동으로 구체화할 수 있다.[6]

## 실무 적용 기준

| 상황 | 우선 선택 | 이유 |
|---|---|---|
| 하나의 짧고 명확한 작업 | 단일 에이전트 | 조정 비용이 가장 낮다. |
| 서로 독립적인 조사·비교·리뷰 | 서브에이전트 위임 | 병렬 실행과 부모 컨텍스트 격리에 적합하다.[2] |
| 동일 작업을 완료 기준까지 고쳐야 함 | `/goal` | 같은 세션에서 반복 검증한다.[3] |
| 역할별 지식·스킬·도구를 장기 보유해야 함 | Bot/Profile | 전문 역할의 맥락과 대화가 지속된다.[4] |
| 의존성·재시도·승인·감사 이력이 필요한 작업 | Kanban | durable 카드와 구조화된 핸드오프를 제공한다.[5][6] |

## 적용 시 주의점

1. **팀을 기본값으로 두지 않는다.** 다중 에이전트는 조정·비용·지연·평가 부담을 추가하므로, 단일 리드 에이전트 기준선보다 개선되는지 측정한다.[1]
2. **위임 프롬프트에 맥락을 명시한다.** 목적, 입력, 파일 또는 URL, 기대 형식, 제한 조건, 검증 기준을 `goal`과 `context`에 포함한다.[2]
3. **완료 보고를 독립 검증한다.** 서브에이전트의 요약은 증거 자체가 아니므로, 리드 에이전트 또는 검토 단계가 테스트·파일·링크·출처를 확인한다.
4. **자동 분해에는 상한을 둔다.** 카드별 범위, 출처 수, 모델, 최대 실행 시간, 재시도 횟수를 제한해 불필요한 토큰·도구 사용을 막는다.[1][5]
5. **되돌리기 어려운 행동은 사람 승인으로 막는다.** 발송, 배포, 삭제, 결제, 권한 변경은 `Blocked` 또는 명시적 review 단계를 둔다.[5]

## 기존 문서와의 관계

- [에이전트 설정 개요](../README.md): 지침·스킬·권한뿐 아니라 서브에이전트 위임, Goal, 역할 기반 Bot, Kanban 오케스트레이션을 다루는 사례다.
- 이 사례는 Hermes의 현재 기능을 다루지만, 단일 제품의 설치 절차가 아니라 에이전트의 실행 환경·역할·작업 조정 원칙을 설명하므로 `03-에이전트-설정`에 저장한다.
