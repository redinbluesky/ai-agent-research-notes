## 한 줄 결론

이 프로젝트는 AI에게 더 긴 명세를 한 번에 던지는 방식보다, **① 대화로 의도를 맞추고 → ② 실행 가능한 검증 루프를 제공하고 → ③ 코드 구조를 지속적으로 점검하는 방식**을 작은 스킬로 조합하자는 접근이다.[1][3]

## 영상 요약: 세 문제와 대응 스킬

| 문제 | 핵심 원인 | 대응 방식 / 스킬 |
|---|---|---|
| AI가 내가 원한 것을 다르게 구현함 | 말하지 않은 조건·용어·의사결정을 AI가 모름 | `grill-me`, `grill-with-docs`로 질문을 통해 의도와 용어를 정렬 |
| AI가 만든 코드가 실제로 동작하는지 불확실함 | 에이전트에게 실행 결과 피드백이 없음 | `tdd`로 실패하는 테스트 → 구현 → 통과 확인의 반복 루프 구성 |
| 기능이 늘수록 코드를 고치기 어려워짐 | 명세 충실도에만 집중하고 구조적 품질을 놓침 | `improve-codebase-architecture`로 구조 개선 후보를 찾아 사람과 결정 |

### 1. 명세를 많이 쓰는 것만으로는 부족하다

영상은 상세한 spec을 작성해 AI에 구현을 맡기는 Spec-Driven Development(SDD)를 시도했지만, 자신의 프로젝트에서는 코드와 AI 산출물이 점차 나빠졌다는 문제를 제기한다.[1] 여기서 부족한 것은 명세의 **분량**이 아니라 다음 세 가지다.

1. 사람과 AI가 같은 의미로 요구사항을 이해하는가
2. AI가 자기 결과를 실제 실행으로 검증할 수 있는가
3. 새 변경이 다음 변경을 어렵게 만들고 있지는 않은가

즉, 이 사례에서 보는 AI 코딩의 병목은 코드 생성 자체보다 **정렬·피드백·구조 관리**다.

### 2. `grill-me` / `grill-with-docs`: 프롬프트가 아니라 의도 정렬 절차

`grill-me`는 사용자가 원하는 일을 적으면 에이전트가 질문을 통해 누락 조건과 모호한 부분을 드러내는 흐름이다. 코딩 작업에서는 `grill-with-docs`가 코드베이스를 함께 살피고, 합의한 내용·용어·결정 이유를 문서화한다.[1][3]

중요한 산출물은 코드만이 아니라 다음과 같은 **공유 언어**다.

- “취소”가 상품 하나 제거인지 주문 전체 취소인지
- 어떤 모듈이 어떤 책임을 가지는지
- 설계 결정의 이유와 제외한 대안은 무엇인지

이렇게 정리하면 다음 세션이나 다른 에이전트도 같은 용어와 기준으로 작업할 수 있다. 저장소 README는 이를 `GLOSSARY.md`와 ADR 같은 지속 문서에 연결하며, 공유 언어가 변수·함수·파일의 명명 일관성과 코드베이스 탐색성에도 도움을 준다고 설명한다.[3]

### 3. `tdd`: AI에게 “완료했다”는 말을 믿지 않을 근거를 준다

영상에서 TDD는 테스트를 먼저 작성하고, 구현 전 실패(red)를 확인한 뒤, 구현 후 통과(green)를 확인하는 반복 방식으로 소개된다.[1]

AI 에이전트 관점에서 이 루프가 중요한 이유는 다음과 같다.

1. 테스트가 실패해야 해당 테스트가 문제를 실제로 포착하는지 알 수 있다.
2. 통과 결과는 에이전트의 자연어 자기평가보다 더 강한 확인 근거가 된다.
3. 정적 타입, 자동 테스트, 브라우저 조작·스크린샷 같은 실행 피드백이 함께 있을수록 AI가 추측 대신 관측에 기반해 수정할 수 있다.[1][3]

영상은 Matt Pocock이 AI가 직접 화면을 열고 링크를 누르며 결과를 확인하도록 환경을 구성한 뒤 결과물 품질이 좋아졌다고 설명한다.[1]

### 4. `improve-codebase-architecture`: “이번 기능의 성공”과 “다음 변경의 용이성”을 분리한다

기능이 현재 동작해도 구조가 나빠질 수 있다. 영상은 기능이 계속 추가될수록 변경 간 결합이 커지고, 한 곳의 수정이 엉뚱한 곳을 망가뜨리는 상태를 경고한다.[1]

`improve-codebase-architecture`는 코드를 자동으로 리팩터링하는 도구라기보다 다음을 수행하는 **구조적 부채 탐색·의사결정 보조 스킬**이다.[1][3]

1. 코드베이스를 조사한다.
2. 구조 개선 후보와 이유를 보고서로 제시한다.
3. 사람이 후보를 선택하면 질문을 통해 개선 방향을 좁힌다.

따라서 이 프로젝트의 품질 기준은 “지금 테스트가 통과하는가”에서 끝나지 않고, **다음 변경도 안전하고 이해 가능하게 만들 수 있는가**까지 확장된다.

## `mattpocock/skills` 프로젝트의 기본 구조

저장소는 “AI가 코딩을 대신하게 하는 거대한 방법론”보다, 실무 엔지니어링 절차를 작은 재사용 단위로 포장한 스킬 라이브러리다. 작성자는 이를 작고, 조정하기 쉽고, 조합 가능한 스킬로 설명한다.[2][3]

### 두 축의 분류

| 분류 축 | 내용 | 예시 |
|---|---|---|
| 업무 영역 | Engineering / Productivity | 구현·테스트·리뷰 / 인수인계·학습·질문지 |
| 호출 주체 | User-invoked / Model-invoked | 사람이 명시 실행 / 에이전트가 상황에 맞춰 자동 적용 가능 |

특히 호출 주체 분리가 핵심이다.

- **User-invoked 스킬**: 사람이 명시적으로 시작하는 오케스트레이션 진입점이다. 예: `grill-with-docs`, `implement`, `to-tickets`
- **Model-invoked 스킬**: 에이전트가 작업 상황에 맞으면 자동으로 적용할 수 있는 재사용 원칙이다. 예: `tdd`, `diagnosing-bugs`, `code-review`, `writing-for-agents`

저장소는 사용자 호출 스킬이 다른 사용자 호출 스킬을 직접 호출하지 않고, 공통 원칙을 담은 모델 호출 스킬을 조합하도록 구분한다.[3]

## 대표 작업 흐름

```text
요구·아이디어
  → grill-with-docs: 질문으로 의도·용어·결정 정렬
  → to-spec / to-tickets: 명세와 작업 단위화
  → implement: 구현 진행
      → tdd: 실패-통과 피드백 루프
      → diagnosing-bugs: 가설·계측·수정·회귀 테스트
      → code-review: 규칙 준수와 spec 충족을 별도 축으로 검토
  → retro: 작업 뒤 에이전트 환경·규칙·도구 개선 후보 탐색
```

이는 이 저장소의 `01-AI-네이티브-SDLC`에서 다루는 Intent → Spec → Plan → 구현·검증 흐름과 연결된다. 다만 이 저장소의 독특한 점은 문서를 늘리는 데 있지 않고, 각 단계의 판단과 검증 행동을 에이전트가 반복하도록 스킬화했다는 데 있다.

## 이 프로젝트에서 얻을 수 있는 기본 원칙

### 사실: 저장소가 강조하는 원칙

- 의도 불일치는 AI 시대에도 핵심 실패 원인이며, 질문을 통한 정렬이 필요하다.[3]
- 에이전트 품질은 정적 타입, 테스트, 브라우저 등 실행 피드백 루프의 품질에 좌우된다.[3]
- 빠른 AI 구현은 코드 복잡도와 구조적 부채도 빠르게 키울 수 있으므로, 코드 설계를 지속적으로 점검해야 한다.[3]
- 스킬·지침 문서는 항상 많이 넣기보다, 필요한 상황에 도달하도록 짧고 명확한 포인터와 점진적 공개 구조를 설계해야 한다.[4]

### 분석: 이 연구 노트에 적용할 때의 최소 해석

1. **스킬은 만능 프롬프트 모음이 아니다.** 반복되는 판단·검증 절차를 에이전트가 놓치지 않도록 만드는 작업 프로토콜이다.
2. **가장 먼저 도입할 것은 스킬 수가 아니라 검증 수단이다.** 테스트·빌드·린트·브라우저 확인이 없다면 여러 스킬을 추가해도 AI는 실행 결과를 충분히 알기 어렵다.
3. **`AGENTS.md` / `CLAUDE.md`는 모든 지식을 담는 곳이 아니다.** 매번 필요한 핵심 규칙만 두고, 작업 조건이 맞을 때 읽을 세부 가이드는 스킬·참조 문서로 분리하는 편이 낫다.[4]
4. **처음에는 전체 워크플로를 강제하지 말아야 한다.** 이 저장소의 전체 체계를 복제하기보다, 실제 병목 하나에 대응하는 스킬 하나를 선택하는 편이 안전하다. 요구사항 오해가 많으면 `grill-with-docs`, 회귀가 많으면 `tdd`, 구조 악화가 문제면 아키텍처 점검부터 시작할 수 있다.
5. **자동 호출은 권한 통제가 아니다.** 스킬의 자동·명시 호출 여부는 적용 시점을 제어할 뿐, 실제 변경·외부 실행 권한과 승인 정책은 별도로 설계해야 한다.

## Claude Code·Codex 연결

- Claude Code와 Codex 모두 스킬을 명시 호출하거나, 설명이 작업과 맞을 때 모델이 선택하도록 구성할 수 있다.[6][7]
- 이 저장소는 Claude Code·Codex용 플러그인 설치 경로를 제공한다. 제품별 설치·호출 방식은 [Claude Code 설정](../산출물/Claude-Code-설정.md) 및 [Codex 설정](../산출물/Codex-설정.md)에 정리한다.[3]
- 플러그인은 스킬뿐 아니라 서브에이전트·훅·MCP 서버를 함께 포함할 수 있으므로, 설치 전 구성 요소와 실행 권한을 확인해야 한다.[5][6][8]
