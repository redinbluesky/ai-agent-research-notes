# Claude Code 설정

## 범위와 근거

Claude Code의 공통 지침·경로별 규칙·스킬·훅·서브에이전트를 구성하는 방법을 정리한다. 출처별 사례와 공식 문서를 종합한 설정 가이드이며, 빈 템플릿이나 실제 설치된 설정 파일이 아니다.

- 반영 사례: [마일드코드 — CLAUDE.md 구성과 역할 분리](../사례/2026-09-27-마일드코드-CLAUDE.md-구성과-역할-분리.md)
- 공식 문서 확인일: 2026-10-07. 핵심 역할 구분을 비교하고 설정 적용 범위와 비동기 훅 주의사항을 보강했다. 세부 옵션 전체를 재검증한 것은 아니다.
- 검증 범위: 공식 문서에 근거한 구성 설명. 예시를 실제 Claude Code 환경에 설치하거나 실행 검증하지 않았다.
- 권한·샌드박스·MCP의 상세 설정은 현재 범위에 포함하지 않는다.

## 1. 설정의 기본 원칙

항상 필요한 공통 문맥은 `CLAUDE.md`, 조건별 규칙은 Rules, 재사용 지식·절차는 Skills, 이벤트 기반 실행 제어는 Hooks, 독립 작업은 Subagents로 구분한다.[6]

실무 적용 시에는 다음 원칙을 사용한다.

1. 파일 수보다 실제 로딩·실행 시점을 기준으로 분리한다.
2. 자연어 지침과 권한·차단 장치를 구분한다.
3. 작은 프로젝트에는 필요한 구성만 추가한다.
4. 개인 설정과 팀에 공유할 설정을 구분하고 비밀값을 지침 파일에 넣지 않는다.
5. 설정 변경도 대표 작업으로 검증하고, 에이전트의 자기 보고만으로 성공을 판단하지 않는다.

## 2. 전체 폴더 구조

### 설정의 적용 범위

| 적용 대상 | 대표 설정 위치 | 용도 |
|---|---|---|
| 내 모든 프로젝트 | `~/.claude/settings.json` | 개인 공통 설정 |
| 해당 프로젝트의 팀원 | `.claude/settings.json` | 저장소에서 공유할 설정 |
| 해당 프로젝트의 나만 | `.claude/settings.local.json` | 개인·환경별 설정 |
| 조직 전체 | 관리형 설정 | 조직 정책. 상세 설명은 생략 |

위 표는 설정 파일의 적용 범위다.[7] `CLAUDE.md` 같은 지침 파일의 로딩 규칙과는 구분한다.[2]

### 프로젝트 수준 구성 예시

아래는 공식 문서의 경로를 바탕으로 만든 **프로젝트 수준의 설명용 구조**다. 사용자 전체에 적용하는 개인 설정까지 포함한 구조는 아니다. 모든 프로젝트에 전부 만들 필요는 없고, 이 연구 저장소에 실행 설정으로 설치한 것도 아니다.[2][3][4]

```text
개발-프로젝트/
├─ CLAUDE.md                       # 항상 필요한 공통 문맥
└─ .claude/
   ├─ settings.json                # 훅 등의 실제 설정 등록
   ├─ rules/
   │  ├─ api.md                    # API 경로에 적용할 규칙
   │  └─ testing.md                # 테스트 경로에 적용할 규칙
   ├─ skills/
   │  └─ release-check/
   │     └─ SKILL.md               # 필요할 때 호출하는 릴리스 점검 절차
   ├─ hooks/
   │  └─ check-policy.py           # 임의로 정한 스크립트 위치; 설정에서 연결
   └─ agents/
      └─ test-runner.md            # 테스트 담당 서브에이전트 정의
```

`agents/`의 프로젝트 경로와 독립 컨텍스트 동작은 서브에이전트 문서에 근거한다.[5] 위 스크립트 이름·규칙 이름·스킬 이름은 설명을 위한 제안이며 예약된 이름이 아니다.

## 3. CLAUDE.md — 공통 지침

**역할·위치:** 프로젝트 루트의 `CLAUDE.md`에 프로젝트 소개, 공통 명령, 항상 필요한 작업 지침을 둔다. 프로젝트 지침은 세션의 공통 문맥으로 사용한다.[2]

공식 문서는 각 `CLAUDE.md`를 **200줄 미만으로 유지하는 것을 목표**로 제시한다. 긴 파일이 더 많은 컨텍스트를 사용하고 지침 준수에 불리할 수 있다는 설명이지, 200줄을 넘으면 나머지를 모두 읽지 않는다는 뜻이 아니다.[2][6]

**적용 제안:** 줄 수 자체보다 중복·모호한 지침·현재 작업과 무관한 절차를 줄인다. `CLAUDE.md`의 길이 권고와 자동 메모리의 로딩 한도는 다른 개념으로 취급한다.[2]

### 구성 예시

```markdown
# 프로젝트 개요
- 이 프로젝트의 목적과 주요 구성 요소

# 공통 명령
- 프로젝트에서 확인한 설치·빌드·테스트 명령

# 공통 작업 원칙
- 변경 범위를 벗어난 수정은 먼저 협의한다.
- 완료 보고에는 실행한 검증과 남은 한계를 적는다.
```

위 내용은 빈 실행 템플릿이 아니라 구성 설명이다. 실제 파일에는 확인된 명령과 프로젝트 고유 규칙을 넣는다. 승인 요청 같은 자연어 지침만으로 동작이 기술적으로 차단되는 것은 아니다.

## 4. Rules — 조건별 규칙

프로젝트의 규칙 파일은 `.claude/rules/`에 둔다. `paths` frontmatter가 없는 규칙은 시작할 때 로딩되며, `paths`를 지정한 규칙은 일치하는 파일을 다룰 때 적용된다.[2]

따라서 영상의 “파일 위에 경로를 적는다”는 설명은 일반 본문에 경로를 쓰는 것이 아니라, **YAML frontmatter의 `paths` 필드로 경로 패턴을 지정하는 것**으로 구체화해야 한다.[1][2]

또한 `CLAUDE.md`를 여러 파일로 나눈 뒤 `@path`로 전부 가져오면 정리에는 도움이 되지만, 가져온 내용도 시작 시 컨텍스트에 들어가므로 컨텍스트 절감과 같지 않다.[2]

### 구성 예시

다음은 공식 문서의 `paths` 형식을 이용한 설명용 예시다. 실제 저장소 경로에 맞게 패턴을 바꿔야 한다.[2]

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API 규칙
- 외부 입력을 검증한다.
- 프로젝트의 공통 오류 응답 형식을 따른다.
- 계약 변경에는 관련 테스트를 추가한다.
```

## 5. Skills — 재사용 절차와 지식

프로젝트 스킬은 `.claude/skills/<스킬명>/SKILL.md`로 구성한다. 스킬은 반복 절차와 참고 지식을 담을 수 있으며, 기본적으로 사용자가 명령으로 호출하거나 Claude가 관련성을 판단해 호출할 수 있다.[3]

기본적인 모델 호출 가능 스킬은 이름과 설명이 미리 제공되고, 호출 시 본문이 로딩된다. `disable-model-invocation: true`로 사용자 호출 전용으로 만들면 호출 전에는 설명도 컨텍스트에 들어가지 않는다. 따라서 “항상 설명 한 줄만 올라간다”는 표현은 로딩 방식을 쉽게 설명한 것이며, 모든 설정에 동일하게 적용되는 규칙은 아니다.[3][6]

**적용 제안:** 배포처럼 부작용이 있는 절차는 자동 호출 여부를 명시적으로 결정하고, 스킬의 호출 제한을 별도의 권한·승인 정책과 혼동하지 않는다.

### 구성 예시

사용자가 명시적으로 호출하는 스킬의 형식 예시다. `disable-model-invocation: true`는 자동 호출을 제한하는 설정이다.[3]

```markdown
---
name: release-check
description: 릴리스 전 변경 범위와 검증 결과를 점검한다.
disable-model-invocation: true
---

1. 변경 범위와 릴리스 대상 버전을 확인한다.
2. 프로젝트에 정의된 테스트와 빌드를 실행한다.
3. 실패 항목과 미검증 항목을 정리한다.
4. 점검 결과만 보고하고 실제 배포는 수행하지 않는다.
```

## 6. Hooks — 이벤트 기반 실행 제어

프로젝트 공유 훅은 `.claude/settings.json` 등의 설정에 등록한다. `.claude/hooks/`는 실행 스크립트를 두는 위치로 사용할 수 있지만, 그 폴더에 파일을 저장하는 것만으로 훅이 자동 등록되지는 않는다.[4]

도구 호출 전에 차단하려면 `PreToolUse`처럼 실행 전 이벤트에서 적용 대상과 검사 로직을 구성해야 한다. 공식 문서에는 `hookSpecificOutput.permissionDecision`을 `deny`로 반환해 호출을 막는 예가 있다.[4]

따라서 “훅은 어떤 동작이든 무조건 차단한다”가 아니라, **설정한 이벤트·매칭 조건·검사 결과가 적용되는 동작을 통제한다**고 이해해야 한다. `PostToolUse`의 사후 검사와 `PreToolUse`의 사전 제어는 같은 역할이 아니다.[4]

**보안상 권고:** 차단해야 할 경로·명령의 우회 가능성, 훅 실패 시 처리, 설정 변경 권한을 별도로 검토한다. 운영 환경은 훅 하나에 의존하지 말고 최소 권한·격리·승인 절차를 함께 둔다.

훅은 차단뿐 아니라 자동 검사·후처리에도 사용한다. **비동기 훅(`async: true`)은 동작을 차단할 수 없으므로**, 사전 차단 목적이라면 선택한 이벤트와 실행 방식의 차단 지원 여부를 확인한다.[10]

### 구성 방법

1. 차단·검사할 동작과 대상 도구를 정한다.
2. 사전 차단과 사후 검사 중 목적에 맞는 이벤트를 선택한다.
3. 검사 스크립트를 작성하고 프로젝트 설정의 `hooks`에 연결한다.
4. 허용·거부·검사 실패 사례를 구분해 검증한다.

위 순서는 적용 제안이다. 훅 스크립트와 등록 JSON은 실행 가능한 완성본으로 제공하지 않는다. 보호 대상과 실행 환경이 정해지지 않은 상태에서 범용 차단기를 안전하다고 제시할 수 없기 때문이다.

## 7. Agents — 독립 작업 위임

서브에이전트는 자체 컨텍스트에서 작업하고 결과를 돌려주므로 메인 대화에 긴 중간 출력을 쌓지 않는 데 유용하다. 사용자 정의 프로젝트 서브에이전트는 `.claude/agents/`의 Markdown 파일로 정의한다.[5]

서브에이전트도 별도로 모델 요청을 보내고 사용량을 소비한다. **메인 컨텍스트의 절약과 전체 토큰·비용의 감소는 같은 주장이 아니다.**[5]

**적용 제안:** 테스트 작업을 맡길 때는 “성공”이라는 요약만 받지 말고 실행 명령, 종료 코드, 실패 테스트, 확인 가능한 로그 위치를 반환하도록 한다. 별도 컨텍스트가 별도 파일시스템이나 안전한 샌드박스를 자동 보장한다고 가정하지 않는다.

### 테스트 담당 에이전트 구성 방향

`.claude/agents/test-runner.md`를 정의할 때 다음 내용을 명시하는 것을 권장한다. 아래는 완성된 설정 파일이 아니라 역할 설계 예시다.

| 항목 | 제안 내용 |
|---|---|
| 역할 | 지정된 범위의 테스트 실행과 실패 원인 요약 |
| 호출 조건 | 긴 테스트 출력이나 독립적인 검증 작업이 필요할 때 |
| 작업 범위 | 요청한 테스트만 실행하며 수정·배포는 별도 승인 |
| 권한 | 작업에 필요한 도구와 접근 범위만 허용 |
| 반환 결과 | 실행 명령, 종료 코드, 실패 항목, 로그 위치, 미검증 범위 |

## 8. 기존 CLAUDE.md의 내용 분리 기준

다음은 영상과 공식 기능 구분을 바탕으로 한 **실무 적용 제안**이다.[1][6]

| 기존 CLAUDE.md의 내용 | 옮길 곳 또는 유지 위치 | 판단 이유 |
|---|---|---|
| 프로젝트 목적, 공통 빌드·테스트 명령 | `CLAUDE.md` 유지 | 대부분의 작업에서 필요 |
| API 파일의 입력 검증·오류 형식 규칙 | `rules/api.md`와 `paths` | 해당 경로에서 적용할 지침 |
| 릴리스 준비·점검의 단계별 절차 | `skills/…/SKILL.md` | 특정 작업에서만 필요 |
| 보호 대상 변경을 실행 전에 거부 | 훅 설정과 검사 로직, 필요 시 권한·격리 정책 | 자연어 안내와 실행 통제를 분리 |
| 긴 테스트 실행·로그 분석 | 서브에이전트 위임 | 중간 출력을 메인 대화와 분리 |
| 모든 작업에서 필요한 짧은 공통 규칙 | `CLAUDE.md` 유지 가능 | 무조건 분리하면 오히려 찾기 어려움 |

## 9. 적용 순서와 검증 방법

이 절차는 연구자의 권고이며, 이 문서에서 실제 적용·테스트한 결과는 아니다.

1. **현재 지침을 분류한다.** 공통 사실·경로별 규칙·작업 절차·강제 정책·위임 작업을 표시한다.
2. **CLAUDE.md를 정리한다.** 중복과 모호한 문장을 제거하되, 실제 필요한 공통 문맥은 유지한다.
3. **경로별 규칙을 분리한다.** 경로 조건을 붙이고, 일치하는 파일과 일치하지 않는 파일에서 적용 차이를 확인한다.
4. **반복 절차를 스킬로 옮긴다.** 설명에 사용 시점을 적고 자동 호출과 사용자 호출을 구분한다.
5. **차단 정책을 별도로 구현한다.** 허용 사례와 거부 사례뿐 아니라 검사 오류·우회 경로를 검증한다.
6. **긴 독립 작업만 위임한다.** 범위·권한·반환 형식을 명시하고 결과 증거를 확인한다.
7. **변경 전후를 비교한다.** 지침 누락, 잘못된 호출, 작업 성공률, 지연과 사용량을 관찰한다. 파일 수가 늘었다는 이유만으로 개선됐다고 판단하지 않는다.
