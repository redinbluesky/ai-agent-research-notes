# 한 줄 요약

WebMCP는 웹사이트가 AI 에이전트에 기능을 구조화된 도구로 공개하여, 에이전트가 화면과 DOM을 해석해 클릭하는 대신 도구 계약을 직접 호출하도록 만드는 제안 단계의 웹 표준이다.

# 영상에서 확인한 핵심 내용

## 문제: 사람용 UI를 AI가 역으로 해석해야 한다

기존 브라우저 에이전트는 DOM, 접근성 트리, 화면 캡처를 분석하고 버튼·폼·메뉴를 찾아 조작한다. 이 방식은 가능하지만 다음 비용이 발생한다.

- 웹페이지 구조를 탐색하는 데 토큰과 시간이 든다.
- 화면·레이아웃·문구 변경에 취약하다.
- 다단계 클릭과 입력이 많아질수록 실패 가능성이 증가한다.
- 에이전트가 기능의 의미를 UI만 보고 추론해야 한다.

## WebMCP의 접근

웹페이지는 에이전트가 사용할 수 있는 기능을 도구로 정의한다.

- 도구 이름과 설명
- 입력값과 JSON Schema
- 실행할 웹 애플리케이션 로직
- 구조화된 실행 결과

에이전트는 페이지를 방문한 뒤 이 도구를 발견하고, 필요한 인자를 제공해 기능을 호출한다.

```text
기존: 화면/DOM 해석 → UI 탐색 → 클릭·입력 → 결과 읽기
WebMCP: 도구 발견 → 구조화된 인자 전달 → 사이트 기능 호출 → 결과 수신
```

## 항공권 데모

영상의 가상 항공권 페이지는 항공편 목록 조회, 검색, 필터 설정, 필터 초기화 같은 기능을 WebMCP 도구로 등록한다. 에이전트는 뉴욕 출발·런던 도착·날짜·직항·가격 조건을 조합해, UI 요소를 순차적으로 탐색하지 않고 검색과 필터 작업을 수행한다.

# WebMCP와 일반 MCP의 관계

| 구분 | 일반 MCP | WebMCP |
|---|---|---|
| 도구 제공 위치 | 로컬 또는 원격 MCP 서버 | 방문한 웹페이지 |
| 주 용도 | 외부 서비스·DB·파일·사내 시스템 연결 | 현재 페이지 기능을 에이전트에 노출 |
| 페이지 상태 | 웹페이지와 독립적으로 동작 가능 | 열린 페이지·로그인 세션·UI 상태와 밀접 |
| 적합한 기능 | GitHub, Slack, DB, 사내 API | 검색, 필터, 예약, 장바구니, 대시보드 조작 |

영상의 “중간 서버가 없다”는 설명은 **별도 MCP 서버가 필수는 아니다**라는 뜻으로 해석해야 한다. WebMCP 도구는 웹페이지의 클라이언트 코드에 등록되지만, 실제 기능은 기존 백엔드 API나 서버 로직을 호출할 수 있다.

# 구현 방식

## 선언형 API

기존 HTML 폼에 도구 이름과 설명 같은 주석 정보를 부여하여 에이전트가 폼을 도구로 인식하게 한다.

- 적합: 검색, 필터, 예약, 표준 입력 폼
- 장점: 기존 HTML 구조를 활용해 빠르게 도입 가능

## 명령형 API

JavaScript에서 도구 이름, 설명, 입력 스키마, 실행 함수를 직접 등록한다.

- 적합: 복잡한 상태 관리, 다단계 비즈니스 로직, 복합 액션
- 장점: 기존 프론트엔드 함수·API와 세밀하게 연결 가능

# 영상의 전략적 프레임

```text
SEO: 검색 엔진에서 발견되도록 최적화
→ AEO: AI 답변 엔진이 정보를 인용·활용하도록 최적화
→ WebMCP: AI 에이전트가 사이트 기능을 실제 수행하도록 최적화
```

이 프레임은 에이전트 친화적 웹의 방향성을 설명하는 데 유용하다. 다만 SEO·AEO·WebMCP가 공식적으로 정해진 단계적 성숙 모델이라는 뜻은 아니며, WebMCP가 검색 순위를 높이거나 AEO를 대체한다는 의미도 아니다.

# 공식 문서로 교차 확인한 사항

Chrome 개발자 문서는 WebMCP를 AI 에이전트를 위해 구조화된 도구를 노출하는 **제안(proposed) 웹 표준**으로 설명한다.

- 선언형 HTML API와 명령형 JavaScript API를 제공한다.
- 도구는 이름, 설명, JSON Schema, 실행 로직을 가진다.
- 브라우저가 도구를 WebMCP 인식 에이전트에 노출한다.
- 에이전트는 구조화된 인자를 넣어 도구를 호출한다.
- 목적은 화면 수준 UI 조작보다 높은 성능과 신뢰성을 얻는 것이다.
- 아직 확정된 범용 웹 표준이 아니라 실험·도입 초기 단계다.

# 실무 적용 판단

## 우선 적용하기 좋은 기능

- 검색·필터·조회처럼 읽기 중심인 기능
- 입력과 결과가 명확한 기능
- 이미 안정적인 API 또는 프론트엔드 함수가 있는 기능
- 사용자 확인 없이 실행되어도 부작용이 작거나 없는 기능

## 신중해야 할 기능

- 결제, 주문 확정, 예약 확정
- 계정 삭제, 권한 변경
- 개인정보 수정·공유
- 대규모 데이터 변경

상태 변경 기능은 명시적 사용자 확인, 최소 권한, 서버 측 권한 검증, 감사 로그를 전제로 설계해야 한다.

# 보안·운영 체크리스트

- [ ] 읽기 전용 도구와 상태 변경 도구를 구분한다.
- [ ] 입력 JSON Schema에 값 형식과 허용 범위를 명확히 정의한다.
- [ ] 고위험 기능에는 사용자 재확인을 요구한다.
- [ ] 서버에서 로그인 상태와 권한을 다시 검증한다.
- [ ] 도구 호출 이력, 입력, 결과를 감사 로그로 남긴다.
- [ ] 속도 제한, 중복 실행 방지, 멱등성을 설계한다.
- [ ] 프롬프트 인젝션에 따른 부적절한 도구 호출을 전제로 방어한다.

# AI 네이티브 SDLC와의 연결

AI 네이티브 SDLC가 개발 조직 내부의 계획·설계·구현·테스트·운영을 AI 중심으로 재구성하는 방법이라면, WebMCP는 서비스 외부에서 AI 에이전트가 웹 기능을 안전하고 구조적으로 사용할 수 있게 하는 인터페이스다.

WebMCP 도입 자체도 AI 네이티브 SDLC 방식으로 다룰 수 있다.

```text
Intent: 에이전트가 조건에 맞는 상품을 검색·비교할 수 있게 한다.
Spec: 검색과 필터를 WebMCP 도구로 노출하고, 쓰기 기능은 사용자 확인을 요구한다.
Plan: 기존 API 연결, 입력 스키마·권한 검사·감사 로그·E2E 테스트를 구현한다.
Eval: 조건 해석 오류와 권한 없는 상태 변경 시도를 검증한다.
```

# 결론

WebMCP는 AI가 사람용 UI를 흉내 내는 방식에서 벗어나, 웹사이트가 AI에 기능 계약을 제공하게 하려는 기술이다. 표준과 지원 생태계는 아직 초기이므로, 검색·조회·필터처럼 제한된 읽기 기능부터 실험하고 권한·감사·확인 절차를 검증한 후 적용 범위를 넓히는 접근이 적절하다.
