## 한 문장 결론

REA는 AI가 앱의 겉모습을 보고 추측해 구현하는 대신, 로컬 대상의 정적·런타임 관찰 결과와 한계를 증거로 받아 분석·설명·유사 기능 구현을 이어가게 하는 CLI·MCP 도구다. 따라서 핵심 가치는 “자동 복제”가 아니라 **근거가 남는 분석 보조**에 있으며, 대상 권한과 사람 검수가 전제되어야 한다.[1][2]

## 영상 요약

### 영상이 말하는 REA의 정체

영상은 REA를 “Reverse Engineer Anything”의 약자로 소개하며, 소스 코드를 갖고 있지 않은 이미 배포된 소프트웨어의 작동 원리를 AI 에이전트가 분석하도록 돕는 공개 도구라고 설명한다.[1] 발표의 중심 메시지는 과거에는 전문 리버스 엔지니어가 다루던 분석 도구와 절차를 Claude Code 같은 에이전트가 호출할 수 있게 연결한다는 것이다.[1]

영상 속 흐름은 다음처럼 단순화할 수 있다.

1. 사용자가 분석할 앱 또는 기능과 질문을 정한다.
2. 에이전트가 MCP를 통해 REA 분석 도구를 호출한다.
3. REA가 대상의 코드·문자열·함수 관계·실행 관찰 등에서 단서를 수집한다.
4. 에이전트가 그 결과를 근거와 함께 설명하고, 필요하면 별도 프로젝트에서 유사 기능을 구현·시험한다.[1]

### 영상이 제시한 의미

영상은 이 흐름이 상용 앱이나 게임 기능을 다시 만드는 진입 장벽을 낮춘다고 본다.[1] 다만 영상도 분석 대상은 본인이 소유하거나 분석 허가를 받은 소프트웨어, 학습·연구 맥락에 한정해야 한다고 경고한다.[1]

## GitHub 저장소로 보강한 사실

### REA는 ‘하나의 만능 디컴파일러’보다 에이전트용 조사 인터페이스에 가깝다

공식 README는 REA를 네이티브 바이너리, JavaScript·Electron 앱, .NET 어셈블리, 웹사이트 등을 검사하기 위해 에이전트에 연결하는 도구라고 설명한다.[2] 같은 분석 흐름을 터미널 CLI와 MCP 양쪽에서 쓸 수 있으며, 네이티브 바이너리 분석에는 Hopper·Ghidra·IDA 같은 별도 분석 엔진이 필요할 수 있다.[2]

즉 REA의 역할은 분석 엔진을 대체하는 것보다, 여러 분석 수단의 결과를 에이전트가 질문·후속 조사에 활용할 수 있는 작업 흐름으로 묶는 데 있다. 공식 문서의 예에서도 REA는 분석 단계(대상 열기, 문자열·함수 검색, 참조·호출 그래프 추적, 의사 코드 확인)를 맡고, 실제 프로젝트에 기능을 작성하고 테스트하는 일은 에이전트의 일반 개발 도구가 맡는다.[2]

### ‘근거 포함 결과’가 일반 코드 생성과 구별되는 지점이다

MCP 계약 문서는 분석 도구가 정규화된 결과와 `Evidence` 레코드를 함께 반환하도록 정의한다. 이 레코드는 결과의 식별자, 분석 프로필, 관찰 범위·한계를 남기며, 일부 결과는 세션 번들로 유지하거나 내보낼 수 있다.[6] 또한 정적 산출물의 동일성이 런타임 동작의 동일성을 뜻하지 않으며, 관찰 범위가 불완전할 때는 불확실성을 유지하도록 명시한다.[6]

이는 “AI가 원본과 똑같이 만들었다”는 결론을 바로 허용하지 않는 설계다. 실무에서는 다음 세 층을 구분해야 한다.

| 층 | 답하려는 질문 | REA 결과의 적절한 용도 |
|---|---|---|
| 관찰 | 실제로 무엇이 발견됐는가? | 문자열, 모듈, 호출 관계, 네트워크·브라우저 관찰 확인 |
| 해석 | 발견한 단서가 기능과 어떻게 연결되는가? | 에이전트의 설명·가설과 추가 조사 계획 |
| 재구현 | 우리 제품에서 어떤 방식으로 만들 것인가? | 요구사항에 맞는 독립 구현·테스트·검수 |

표의 마지막 단계는 원본 코드를 그대로 얻는 일이 아니라, 관찰한 동작을 참고해 자신의 스택·요구사항에 맞는 구현을 만드는 별도 개발 작업이다. 이는 영상의 “AI가 대신 분석한다”는 표현을 과도한 자동 복제 주장으로 읽지 않게 해 준다.[1][2]

### Windows에서의 기대 범위는 특히 좁게 잡아야 한다

사용 환경이 Windows라면 공식 문서는 Ghidra 기반 네이티브 분석을 실험적 P0 경계로 설명한다. 지원 대상·사전 조건·읽기 전용 작업 수가 제한되어 있으며, 일반적인 Windows 기능 동등성을 보장하지 않는다고 명시한다.[4] 반면 정적 JavaScript 및 .NET 검사는 네이티브 분석 엔진 없이도 가능한 범위가 있다.[2]

따라서 Windows에서 REA를 처음 평가할 때에는 복잡한 상용 데스크톱 바이너리 전체보다, **권한이 있는 JavaScript/Electron 앱 또는 작고 정적인 표본**으로 ‘근거를 포함한 분석 결과가 실제로 유용한가’를 먼저 확인하는 편이 현실적이다. 이것은 저장소 기능 범위에 근거한 도입 제안이다.[2][4]

## 분석: 이 도구가 에이전트 네이티브인 이유

### 1. 자연어 요청을 조사 작업으로 바꾼다

일반 LLM은 “이 앱의 검색 기능을 만들어 달라”는 요청을 받으면 보통 일반적인 검색 패턴에 기초해 답한다. REA가 연결되면 요청은 대상 확인, 관련 문자열·모듈 탐색, 호출 관계 추적, 관찰 결과 확인이라는 조사 작업으로 분해된다.[2] 에이전트가 단순 답변기가 아니라 **도구를 선택하고 증거를 회수하는 실행자**가 되는 지점이다.

### 2. 분석 결과의 불확실성을 함께 전달한다

리버스 엔지니어링의 산출물은 원본 소스와 같지 않으며, 디컴파일·휴리스틱·AI 해석은 불완전하거나 틀릴 수 있다. REA의 책임 있는 사용 문서도 결과의 정확성·완전성·호환성·법적 적합성을 보장하지 않으며, 근거를 검토하고 중요한 결론은 별도로 검증하라고 명시한다.[5] 따라서 좋은 워크플로는 ‘분석 완료’가 아니라 ‘가설과 증거를 확보함’에서 다음 검증 단계로 넘어간다.

### 3. 로컬 분석은 데이터 경로를 줄이지만 권한 문제를 없애지 않는다

REA는 분석을 지원되는 로컬 호스트에서 수행한다고 설명한다.[2] 하지만 그 사실만으로 대상 프로그램 실행, 브라우저·네트워크 관찰, 디바이스 연결, 캡처 데이터 보관이 자동으로 허용되는 것은 아니다. 프로젝트 고지는 런타임·네트워크·기기 관련 작업이 앱 상태, 파일, 계정, 기기, 서비스에 영향을 줄 수 있으며, 분석 허가는 실행·상호작용·가로채기 허가와 다를 수 있다고 밝힌다.[5]

## 도입 판단: 깊게 들어가지 않는 최소 기준

| 확인 항목 | 채택 신호 | 보류 신호 |
|---|---|---|
| 대상 권한 | 자사 프로그램·명시적 허가·재현 가능한 연구 표본 | 타사 상용 앱, 게임, 계정·개인정보가 있는 대상 |
| 질문의 명확성 | “검색 결과 정렬은 어디서 결정되는가?”처럼 기능 단위 질문 | “앱을 똑같이 만들어라”처럼 범위·권한이 불명확한 요청 |
| 결과 검증 | Evidence와 원본 관찰을 사람이 확인하고 독립 테스트를 계획 | 에이전트 설명이나 디컴파일 결과만으로 배포 결정 |
| 실행 영향 | 정적 분석부터 시작, 별도 격리 환경에서 런타임 관찰 | 운영 계정·실서비스·신뢰할 수 없는 실행 파일을 바로 실행 |
| 환경 준비 | Node.js, 필요한 분석 엔진, 대상 유형별 사전 조건을 확인 | 설치 한 줄만 실행하면 모든 플랫폼·형식을 처리할 것이라 기대 |

공식 설치 절차는 에이전트 설정 변경과 선택적 분석 엔진 설치 전에 변경 경로와 계획을 보여 주고 승인을 요구한다.[3] 이 특성은 조직 도입 시에도 유지할 만하다. 즉 에이전트 설정, 외부 도구 설치, 대상 실행을 각각 별도 승인 단계로 관리하는 것이 적절하다.

## 한계와 안전 경계

- REA의 MIT 라이선스는 REA 자체 코드의 사용 조건이며, 분석 대상 소프트웨어나 연결된 상용 분석 도구의 이용 권한을 부여하지 않는다.[2][5]
- 프로젝트는 DRM·라이선스 검사·안티치트 우회, 인증·접근 통제 우회, 독점 소프트웨어의 보호 코드·자산 복제를 지원하지 않는다고 명시한다.[5]
- 런타임 캡처나 브라우저·네트워크 관찰은 정적 분석보다 부작용과 개인정보 위험이 크므로, 격리·자격 증명 분리·캡처물 보관 정책이 필요하다.[5]
- 이 사례는 저장소 문서와 정적 구조를 확인한 분석이며, 특정 대상에 대해 REA가 정확한 결과를 내는지 또는 영상의 개별 데모를 재현했는지는 검증하지 않았다.

## 이 프로젝트에서의 위치

이 사례의 핵심은 리버스 엔지니어링 기법 자체가 아니라, **에이전트가 MCP·CLI를 통해 조사 도구를 호출하고, 증거와 한계를 다음 개발 작업에 넘기는 인터페이스**다. 그래서 `05-에이전트-네이티브-도구`에 둔다. 실제 설치·에이전트별 MCP 등록 방식은 `03-에이전트-설정`의 범위로 분리하는 편이 적절하다.
